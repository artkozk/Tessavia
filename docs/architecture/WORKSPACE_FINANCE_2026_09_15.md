# Финансы команды и явное подключение источника — 15.09.2026

## Причина и граница изменения

Пользователь добавил финансовый раздел в команду, но увидел личный регистр.
Это несовместимо с ожидаемым назначением командного пространства: новый
раздел должен начинаться с собственных пустых финансов, а чужие источники
должны подключаться явно. Личные суммы, счета, проценты и имена отправителей
нельзя автоматически переносить в команду либо раскрывать её участникам.

Предыдущие [личные финансы](PERSONAL_FINANCE_2026_09_12.md) и
[расходы](FINANCE_EXPENSES_2026_09_14.md) остаются отдельным владельческим
регистром. Их исторические описания сохранены. Этот документ расширяет
платформу командным регистром и не отменяет прежние требования приватности.

## Что является источником данных

Каждый командный проект (`workspaces.kind = team`) имеет собственный
независимый финансовый регистр. Он существует логически с момента создания
проекта, но чтение не создаёт ни счетов, ни источников дохода, ни операций,
ни строки настройки. Личные категории пользователя не являются шаблоном.

У финансового раздела есть источник:

- По умолчанию — собственные финансы текущего командного проекта.
- После явной настройки — собственный регистр выбранного другого проекта.
- Возврат к собственным финансам снова показывает прежние собственные строки.
  Подключение не удаляет и не заменяет их.

Связь с другой командой представляет живое чтение исходного регистра.
Копирования, объединения остатков, создания дубликатов и банковских переводов
при подключении не происходит. Изменение источника выполняется только в общем
центре настроек. Сам финансовый экран показывает название исходного проекта
и состояние просмотра; это позволяет понимать, какие деньги сейчас открыты.

Связь всегда указывает прямо на собственный регистр указанного проекта.
Сервер не следует цепочкам ссылок. При создании нельзя выбрать проект, который
в этот момент сам показывает подключённый регистр: нужно выбрать оригинал.
Если у исходного проекта позже поменяют представление, уже существующая ссылка
сохраняет прежний смысл — его собственный регистр. Данные никогда не начинают
поступать из третьей команды автоматически.

## Права и повторная проверка

Для текущего и исходного проекта требуется активное членство в проекте и,
если он принадлежит команде, активное членство в этой команде. Архивный проект,
удалённая команда и приостановленное членство исключаются.

| Действие | Необходимые права |
| --- | --- |
| Просмотр собственных финансов проекта | Активный участник проекта и команды |
| Доход, расход, справочник, изменение, отмена операции | Владелец или администратор текущего проекта |
| Настройка подключения другого проекта | Владелец или администратор назначения и источника |
| Просмотр подключённого регистра | Собственное активное членство и в назначении, и в источнике |
| Изменение подключённого регистра из другого проекта | Запрещено; нужно открыть исходный проект |
| Возврат к собственному регистру | Владелец или администратор назначения; доступ к утраченному источнику не нужен |

Подключение не выдаёт прав участникам принимающей команды. Например,
администратор имеет доступ к A и B и подключает A в B. Участник только B
увидит сообщение о недоступности, а не финансовые строки A. После получения
доступа к A он сможет открыть их. После отзыва членства чтение снова
запрещено, даже если ссылка сохранена.

Проверка прав, чтение настройки и работа с финансовыми строками выполняются
в одной SQL-транзакции. Между отдельно проверенным разрешением и записью
нет окна для изменения подключения. В приложении один SQLite connection;
параллельные записи сериализуются, а ревизии защищают от устаревших форм.

При недоступности источника `GET settings` сохраняет возможность восстановить
свой регистр, но не возвращает имя недоступного проекта. Ответ данных
финансов при этом — 403; личный регистр не используется как запасной вариант.

## API

Личный API `/api/personal/finance` остаётся прежним: владелец определяется
из сессии. Произвольный `X-Workspace-ID`, owner ID или одинаковое название
счёта не меняют владельца и не делают личные деньги общими.

Командный API `/api/workspace/finance` требует явный `X-Workspace-ID`.
Пустой заголовок отклоняется с 400, личный либо недоступный проект — с 403.
Все ответы финансовых обработчиков имеют `Cache-Control: no-store`.

| Метод и путь после `/api/workspace/finance` | Результат |
| --- | --- |
| `GET /` (без завершающего слеша в фактическом URL) | Прежняя структура отчёта плюс `scope` |
| `GET /settings` | `{scope, options}` |
| `PUT /settings` | Сохранение `{sourceWorkspaceId, expectedRevision}`, ответ `{scope, options}` |
| `POST /buckets`, `PUT /buckets/{id}` | Счета и их архивирование |
| `POST /sources`, `PUT /sources/{id}` | Источники дохода и правила распределения |
| `POST /counterparties`, `PUT /counterparties/{id}` | Справочник отправителей |
| `POST /entries`, `PUT /entries/{id}` | Доходы |
| `PATCH /entries/{id}/transfers`, `PATCH /entries/{id}/void` | Отметки перечисления, отмена и восстановление |
| `POST /expenses`, `GET /expenses/{id}`, `PUT /expenses/{id}` | Расходы и чтение актуальной версии вне текущего периода |
| `PATCH /expenses/{id}/void` | Отмена и восстановление расхода |

`scope` содержит `kind: team`, `workspaceId`, `workspaceName`,
`sourceWorkspaceId`, `sourceWorkspaceName`, `sourceAvailable`, `linked`,
`canWrite`, `canConfigure`, `revision`. Ревизия 0 означает ещё не сохранённую
настройку собственных финансов. Любое сохранение увеличивает ревизию, включая
возврат к тому же идентификатору после временного подключения другого источника.
`options` — массив `{workspaceId, workspaceName}` только доступных проектов,
где пользователь имеет права владельца или администратора. Обычному участнику
варианты настройки не выдаются.

Каждый командный запрос изменения финансов несёт два обязательных заголовка:
`X-Finance-Source` и `X-Finance-Revision` из открытого отчёта. Если источник либо
ревизия изменились, сервер отвечает 409 до записи. Для чтения отдельного расхода
заголовки необязательны, но при передаче также проверяются. Это защищает форму,
которая открылась до смены настройки другим администратором; локальной проверки
выбранного проекта в браузере для этого недостаточно. `GET` полного отчёта и
`GET/PUT settings` используют собственный контракт актуальности.

Суммы, даты, предел 5000 операций выбранного вида за период, точное распределение
копеек, снимки имён, `clientRequestId`, ревизии операций и правила расходов
совпадают с личным модулем. Повтор создания одним или другим администратором
с тем же ключом и содержимым возвращает ту же операцию. Такой же ключ в другом
проекте относится к другому регистру. Исправление и отмена не стирают историю.

## Хранение и миграция

`073_workspace_finance.sql` добавляет восемь пустых таблиц:
`workspace_finance_buckets`, `workspace_finance_sources`,
`workspace_finance_entries`, `workspace_finance_requests`,
`workspace_finance_counterparties`, `workspace_finance_expenses`,
`workspace_finance_expense_requests`, `workspace_finance_settings`.

В командных таблицах область задаётся `workspace_id TEXT REFERENCES workspaces`.
Составные FK удерживают источник дохода, счёт расхода и квитанции повторов
в одном проекте. Ссылка на отправителя дополнительно защищена парой триггеров
при вставке и обновлении. Настройка содержит исходный проект, ревизию,
`updated_by` и время сохранения. Прежние 130 таблиц и их строки не переписываются.
Миграция 066/067/069 не редактируется. Переименование либо перенос личных строк
в командные таблицы не выполняются.

Общий расчётный код работает через `financeTx` в `workspace_finance.go`.
Для личного запроса SQL остаётся исходным и ключом остаётся ID пользователя.
Для командного запроса сервер подставляет строковый ID проверенного источника
и жёстко заданное соответствие семи имён таблиц и поля области. Пользователь
не передаёт SQL, имя таблицы, выражение связи или произвольный владелец.
Это сохраняет один алгоритм округления и расходов, не смешивая хранилища.

## Проверка и ограничения

`workspace_finance_test.go` проверяет пустой командный регистр при существующих
личных доходах, независимые остатки и квитанции, все 13 маршрутов изменения,
обычного участника и понижение администратора, недоступный и архивный источник,
приостановку членства, запрет личных/чужих ID, составные SQL-ссылки, соединение
только при правах администратора, запрет цепочки при настройке, возврат к своим
неизменным строкам, защиту старых форм и конкурентные повторы создания.

Отдельный миграционный тест действительно применяет миграции 001–072,
создаёт синтетические личные доходы, расходы и существующую команду,
сохраняет строки **всех** прежних таблиц и описание схемы, применяет 073 и
побайтно по значениям сравнивает старые данные/схему. Все новые таблицы должны
остаться пустыми; прежний ключ повторного дохода продолжает возвращать старую
операцию. Проверки проводят только на синтетических данных.

Это точный учёт поступлений и расходов с разграничением доступа, а не банковская
интеграция, бухгалтерская отчётность для подачи государству или автоматический
прогноз возможностей бизнеса. Отдельные финансовые роли помимо администратора
пока не добавлены. У операций пока нет пользовательского журнала авторов каждого
изменения; ревизия и снимок операции не объявляются полноценным аудиторским
журналом. Командные финансы не добавляются в общий поиск, граф, AI или обычный
экспорт проекта автоматически. Перенос строк личного регистра через наборы
также не реализуется этим изменением.

Фактические результаты команд, браузерной приёмки и выпуска добавляются после
их выполнения в операционную документацию; описание API само по себе не
означает публикацию на сервере.
