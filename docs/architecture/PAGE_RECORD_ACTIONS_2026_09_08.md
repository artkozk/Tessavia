# SC-79: переносимые действия над полями записей

## Зачем этот этап

Прочитана актуальная задача26c54f79aa1c9110536670ae8371a868. Формы SC-77 создают данные, SC-78 защищает повтор создания, но пользователь ещё не мог сам собрать кнопку изменения существующей записи. Зарегистрирована дочерняя **b73efad20925509be8828c2862eb95dd**, «P0 · Настраивать переносимые действия над полями записей», in_progress до выпуска. Квитанция RECORD_ACTIONS_TASK_2026_09_08.json.

Действие теперь задаётся внутри блока списка записей: собственная подпись, целевое пользовательское поле и конкретное новое значение. Например, перевести обращение на канал «Чат», отметить проверку чекбоксом или установить оценку часов. Пользователь создаёт сценарий через конструктор; такой сценарий должен переноситься набором вместе со схемой, а не требовать скрытого кода разработчика.

## Настройка и выполнение

В свойствах списка есть раскрываемая группа «Действия с записью», до8действий. Можно добавить, переименовать, сменить поле/значение и убрать действие. Ввод значения использует существующие типизированные элементы платформы. Смена поля меняет тип ввода и предлагает исходное значение новой схемы; старое значение другого типа не переносится молча. Ноль и false сохраняются. Конфигурация входит в обычный черновик страницы и защищается ревизией при сохранении.

В каждой строке список действий раскрывается отдельно, кнопки не вложены в кнопку открытия карточки. Перед выполнением открывается диалог: название действия, запись, поле, «Сейчас» и «После подтверждения». Отмена ничего не сохраняет. Изменение выполняется отдельной кнопкой. При конфликте подтверждение блокируется; пользователь явно обновляет предпросмотр и повторно проверяет результат. Сетевой сбой не вызывает автоматического выполнения. Повтор со старой версией после уже состоявшегося сохранения получает409; новый предпросмотр показывает фактический результат.

Предпросмотр набора перечисляет подписи настроенных действий. Установка сама не выполняет их. В описании сохранения набора явно указано, что формы и действия входят в его состав.

## Серверный контракт

POST /api/workspace/pages/{id}/app/action принимает blockId/actionId/recordId, expectedRevision и expectedUpdatedAt. Без apply возвращает предпросмотр. При apply:true дополнительно нужен schemaHash из предпросмотра. Клиент не передаёт исполняемое значение: сервер берёт его из сохранённого действия страницы. Проверяются доступ к пространству/странице/записи, editPolicy, принадлежность записи доске, видимость блока, наличие действия, активность источника и поля, тип/варианты/обязательность. Архивные записи не изменяются. X-Outbox-Owner защищает смену авторизованного аккаунта между открытием и отправкой.

При подтверждении первым SQL-запросом захватывается блокировка записи через UPDATE page_app_definitions SET revision=revision с условием ожидаемой ревизии и активной страницы текущего пространства. Это не увеличивает ревизию, но исключает изменение конфигурации между проверкой и commit. Схема читается той же транзакцией; hash включает актуальное поле, обязательность и варианты. Финальный UPDATE records проверяет expectedUpdatedAt, пространство, доску и отсутствие архива. Изменение поля и история фиксируются атомарно; конфликт/ошибка откатывает всю транзакцию. История custom_fields_updated содержит страницу/действие/поле и значения до/после.

Действие устанавливает одно конкретное значение переносимого пользовательского поля. Поддерживаются text, long_text, number, money, date, datetime, select, multi_select, checkbox, url, email, phone. Ссылки user/relation требуют отдельного контекста и пока недоступны в этих действиях. Статусы/исполнители/сроки основных задач, условия, вычисления, прибавление к значению и цепочки действий этим этапом не реализованы; существующий жизненный цикл задач не обходится. Это не завершение универсального конструктора или полной читалки.

## Перенос набора

В конфигурации действия хранятся стабильный ID, подпись, fieldId и типизированное JSON-значение. При снимке набора проверяются схема и действия. При установке fieldId переводится в новый ID, select и multi_select — в новые IDs вариантов, включая несколько вариантов и пустые значения. Проверка и установка находятся в одной транзакции со страницей и схемами; повреждённый набор не оставляет частично созданных досок. Исходные бизнес-записи, история выполнения и личные черновики не копируются.

Миграций нет, схема065 и117таблиц сохраняются. До cutover штатный dry run должен сравнить все строки/схемы117таблиц без исключений. Старые конфигурации без actions сохраняют прежнее поведение.
