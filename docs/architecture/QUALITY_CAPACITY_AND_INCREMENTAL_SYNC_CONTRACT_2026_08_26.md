# Контракт качества, ёмкости и инкрементальной синхронизации

Дата: 26 августа 2026 года.

## 1. Миграция данных

Миграция `014_productivity_and_quality.sql` создаёт таблицу `user_work_capacity`:

- `user_id` — один набор настроек на участника, внешний ключ на `users`;
- `weekly_minutes` — целое число от 0 до 10080;
- `updated_at` — время последнего изменения.

Также добавлены индексы по `records.updated_at` и `activity.created_at`. Они нужны для фоновой выдачи изменений. Настройки ёмкости входят в полный JSON-экспорт, версия схемы экспорта повышена до `10`.

## 2. Права

`PUT /api/users/{id}/capacity` разрешён только самому пользователю. Проверка выполняется до записи. Значение `0` означает, что ёмкость не задана, а не отсутствие права работать.

Все авторизованные участники могут читать `GET /api/team/capacity`, потому что распределение общей работы должно быть прозрачно для обоих основателей.

Изменение записывается в неизменяемую историю действием `capacity_updated`. Клиент отображает его как «изменил доступное время» и показывает значение в понятном формате часов и минут.

## 3. Расчёт недели

Границы недели вычисляются в `Europe/Moscow`. При недоступности системной базы часовых поясов используется фиксированный UTC+3, соответствующий текущему московскому времени.

Начало — понедельник 00:00 по Москве, конец — следующий понедельник 00:00. В SQL передаются UTC-границы, поэтому сравнение с `due_at` остаётся однозначным.

В расчёт включаются активные исполнимые типы: задачи, исследования, разногласия, группы вопросов, встречи, риски, гипотезы и эксперименты. Статусы `completed`, `cancelled`, `archived` и `rejected` исключаются.

`scheduledMinutes` и `dueThisWeek` учитывают только сроки внутри недели. `unscheduledMinutes` и `unscheduledRecords` учитывают активную работу без срока. `utilizationPercent` вычисляется только при положительной ёмкости.

## 4. Отчёт качества

`GET /api/quality` читает неархивные записи и возвращает:

```json
{
  "generatedAt": "RFC3339Nano",
  "counts": { "total": 0, "critical": 0, "warning": 0, "info": 0 },
  "issues": []
}
```

Каждый `issue` содержит код правила, серьёзность, идентификатор, публичный тип, заголовок и понятное сообщение. Публичный тип учитывает `business_kind`, `question_set` и `meeting`, поэтому frontend открывает правильное досье.

Алгоритм не изменяет данные. Проверка дубликатов нормализует регистр и пробелы, но не выполняет нечёткое сравнение. Цикл родителей проверяется проходом вверх от каждой записи с локальным множеством посещённых идентификаторов.

## 5. Инкрементальная синхронизация

`GET /api/sync` принимает `recordsSince` и `activitySince` в RFC3339Nano. Некорректный курсор возвращает `400`.

Выдача карточек включает:

- записи, обновлённые не раньше курсора;
- источник зависимости `depends_on`, если после курсора обновился её target, чтобы состояние блокера обновилось без полной загрузки;
- вычисленные активные блокеры.

Выдача событий ограничена 200 строками, карточек — 500 строками. События выдаются от старых к новым, поэтому при большой пачке курсор проходит её последовательными порциями и не перескакивает через промежуточную историю; клиент разворачивает новую порцию только для показа свежего события сверху. Сравнение выполняется через `julianday`, а граница включена. Это сознательное перекрытие исключает потерю события при переменной точности строк RFC3339Nano и ограниченной точности SQLite. Клиент удаляет повторные события по `id` и сравнивает карточки по `updatedAt` и блокерам.

Ответ содержит `syncedAt`, сформированный после чтения данных. Клиент не использует его как единственный следующий курсор: курсор карточек и истории продвигается по максимальному фактическому времени соответствующей коллекции. Так зависимости двух потоков не смешиваются.

## 6. Клиентское состояние

После первого `loadData` сохраняются два курсора. `syncProjectChanges`:

1. получает изменения карточек и истории;
2. параллельно обновляет уведомления, ожидающие вопросы и потоки чата;
3. выполняет upsert карточек по `id`;
4. очищает detail cache только для реально обновлённой карточки;
5. удаляет повторы истории по `id`;
6. инвалидирует отчёт качества и загрузку команды при предметных изменениях;
7. не перерисовывает активный ввод или открытый overlay.

После мутаций карточки используется тот же механизм вместо полной повторной загрузки всех записей. Полная загрузка остаётся для bootstrap, смены логина и изменения глобальных шаблонов, где меняется широкий набор зависимых данных.

## 7. Инварианты

1. Сигнал качества никогда не удаляет и не переписывает запись.
2. Чужую недельную ёмкость изменить нельзя.
3. Работа без срока не маскируется внутри недельной загрузки.
4. Граница курсора может вернуть повтор, но не должна пропустить изменение.
5. Повтор события не появляется в UI.
6. Изменение target зависимости обновляет источник с вычисляемым блокером.
7. История изменения ёмкости экспортируется вместе с остальной историей.

## 8. Тестовое покрытие

`productivity_test.go` проверяет личные права, расчёт планового и незапланированного времени, профиль, сигналы качества, полный и последующий инкрементальный sync, некорректный курсор и московскую границу недели. `assets_test.go` защищает новый пункт меню, экран качества, форму ёмкости, sync-маршрут, адаптивные стили и версию клиентских ресурсов.
