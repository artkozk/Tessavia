# Домашняя история зашифрованных копий — 14.09.2026

Этот выпуск добавляет независимое хранение подготовленных резервных архивов
Tessavie на домашнем сервере владельца. Рабочее приложение, SQLite и uploads
остаются на VPS. Домашняя машина сама забирает недостающие архивы; её отключение
или недоступность не входит в путь пользовательского запроса и не останавливает
создание локальной копии на VPS.

Документ дополняет, не заменяя историю,
[аудит ресурсов](SERVER_CAPACITY_AND_STORAGE_AUDIT_2026_09_13.md),
[результат очистки и варианты хранения](SERVER_STORAGE_CLEANUP_AND_BACKUP_OPTIONS_2026_09_14.md)
и [прежний контракт доступа](PRODUCTION_ACCESS_2026_09_06.md).

## Поток данных и состав копии

1. На VPS `159.194.231.150` существующий `business-control-backup.service`
   делает снимок SQLite через её backup API, проверяет целостность, копирует
   uploads, собирает контрольные суммы, архивирует и шифрует результат.
2. Скрипт расшифровывает свой результат в приватном временном каталоге,
   проверяет контрольные суммы содержимого и SQLite integrity check.
3. Полностью подготовленный encrypted-файл публикуется в
   `/var/backups/business-control`. После успешного основного шага служба
   запускает локальный экспорт через `ExecStartPost`.
4. Экспортёр создаёт отдельные копии encrypted-файлов и JSON-манифест в
   `/var/spool/tessavie-backup-export`. Только эта область доступна читателю SSH.
5. Домашний клиент получает список, проверяет все имена и ограничения,
   скачивает только недостающие файлы, сверяет размер и SHA-256 и публикует
   каждую копию в домашнем хранилище без перезаписи существующего имени.
6. Исчезновение файла из списка VPS не удаляет домашнюю историю.

После успешного фактического прогона production-службы 14.09.2026 в
05:21:46 UTC исходный набор составил **40 архивов, 59 586 064 байта**,
около 56,83 MiB. Число включает имеющиеся архивы, а не обещание ровно одной
копии на календарный день. Экспорт занимает дополнительное место такого же
порядка: около 52–57 MiB на измеренных наборах этого этапа. Это расход на
удаляемые при обновлении экспорта дубликаты готовых архивов, а не размещение
рабочей базы в ещё одном каталоге. Во время публикации нужен запас для нового
набора до удаления устаревших экспортных дубликатов.

Штатная локальная политика хранения остаётся прежней: скрипт использует
`BUSINESS_BACKUP_RETENTION_DAYS`, по умолчанию 30, с существующим условием
`find -mtime +N`. Её точная граница зависит от полных прошедших суток;
она не означает гарантированно ровно 30 файлов. Предрелизные резервные копии
в `/var/lib/business-control/backups` этой схемой не изменяются.

## Почему изменена публикация основного архива

Раньше финальное имя создавалось обычным копированием через `install`.
Параллельный читатель мог увидеть это имя до окончания копирования.
Теперь `deploy/business-control-backup.sh` после проверки устанавливает
права `0600` и создаёт жёсткую ссылку на готовый файл через `ln`.

Приватный временный каталог создаётся внутри того же backup-каталога,
поэтому публикация проходит в одной файловой системе. Финальное имя появляется
сразу для полного файла. Совпадение timestamp приводит к ошибке вместо замены
предыдущей копии. Очистка временного каталога снимает временную ссылку,
сохраняя опубликованный файл. Эта правка нужна для корректного параллельного
экспорта и не меняет формат или содержимое архивов.

## Файлы, пользователи и права

| Узел и путь | Назначение и права |
| --- | --- |
| VPS `/usr/local/sbin/business-control-backup` | Основной скрипт из `deploy/business-control-backup.sh`, root, исполняемый |
| VPS `/var/backups/business-control` | Исходные архивы; каталог root `0700`, архивы `0600` |
| VPS `/etc/business-control-backup.key` | Прежний ключ шифрования; остаётся закрытым на VPS |
| VPS `/usr/local/libexec/tessavie-backup-export` | `deploy/tessavie_backup_export.py`, root, исполняемый; режимы `export` и `read` |
| VPS `/var/spool/tessavie-backup-export` | root:`tessavie-backup-reader`, `0750`; архивы и манифест root:reader `0440` |
| VPS `.export.lock` в экспортном каталоге | Блокировка публикации, root, `0600` |
| VPS drop-in `business-control-backup.service` | Содержимое `deploy/tessavie-backup-export.conf`: `ExecStartPost` и разрешённый путь записи экспорта |
| Дом `/usr/local/libexec/tessavie-backup-pull` | `deploy/tessavie_backup_pull.py`, root, исполняемый |
| Дом `/etc/tessavie-backup-pull.json` | Конфигурация root, доступна для чтения службе; без записи группе/остальным |
| Дом `/var/lib/tessavie-backup-client` | Состояние и материалы SSH клиента, владелец `tessavie-backup`, `0700` |
| Дом `/var/lib/tessavie-backup-client/status.json` | Последний результат и дата успешного прохода, `0600` |
| Дом `/var/lib/tessavie-backup-client/pull.lock` | Блокировка одновременного запуска клиента |
| Дом `/var/lib/tessavie-backup-vault` | История encrypted-архивов, владелец `tessavie-backup`, каталог `0700`, файлы `0600` |

На VPS создан отдельный непривилегированный пользователь
`tessavie-backup-reader` с заблокированным паролем. Его каталог авторизации
и `authorized_keys` контролирует root: читатель не может подменять свои
разрешённые ключи или программу обработки команды. Оболочка `/bin/sh` нужна
для запуска forced command средствами sshd; произвольная команда клиента
не становится разрешённой оболочкой.

Запись публичного ключа использует ограничения `restrict` и forced command
`/usr/local/libexec/tessavie-backup-export read`. Обработчик принимает только
`list-v1` либо `get-v1` с одним строгим именем
`business-control-YYYYMMDD-HHMMSS.tar.gz.enc`. Пути, подстановки оболочки,
дополнительные аргументы, SFTP и иные команды не входят в протокол. Выдача
файла требует его присутствия в действующем манифесте. Экспортёр отвергает
символические ссылки и проверяет неизменность файлов при чтении.

На домашнем узле приватный SSH-ключ создаётся для `tessavie-backup` и остаётся
там; на VPS передаётся только публичная часть. Это не ключ root и не ключ
расшифровки архивов. Поля `identity_file` и `known_hosts` в действующей
конфигурации определяют точные имена файлов. Ключ хоста VPS закрепляется по
проверенному каналу администрирования, а не слепым принятием ответа первого
сетевого подключения.

SSH-клиент использует `-F /dev/null`, пакетную авторизацию без запроса пароля,
строгую проверку ключа хоста и только заданный ключ. Агент, X11, терминал
и перенаправления соединений отключены. Входящие порты дома для этой передачи
не нужны; пробросы 2000–2100 не изменяются.

## Ограничения ресурсов и расписание

| Ограничение | Текущее значение и поведение |
| --- | --- |
| Экспорт: число файлов | 1–128, пустой или чрезмерный набор отвергается |
| Экспорт: один файл | Не более 512 MiB |
| Экспорт: суммарный исходный набор | Не более 1 GiB |
| Экспорт: свободный резерв | Не менее 512 MiB плюс требуемое место под отсутствующие экспортные копии |
| Дом: архивная квота | 2 GiB; учитываются также неизвестные обычные файлы и оставшиеся partial |
| Дом: свободный резерв | 2 GiB после планируемой загрузки; повторная проверка перед каждым файлом |
| Дом: возраст источника | Не более 48 часов по UTC timestamp самого нового имени архива |
| SSH | Установка соединения до 10 секунд; каждый вызов не более 300 секунд |
| Домашняя служба | Весь запуск до 15 минут, память до 128 MiB, CPU quota 25% одного CPU, Nice 10, низкий приоритет I/O |

При нынешнем локальном хранении примерно месяца архивов лимит экспорта
1 GiB станет заметен уже при среднем полном архиве около 32–34 MiB, а не
только при достижении предела одного файла 512 MiB. Это предохранитель
маленького VPS. Увеличение домашнего диска до 32 или 512 GiB автоматически
не снимает ни этот предел, ни домашнюю квоту 2 GiB. Их пересматривают вместе
с реальной потребностью в истории и ресурсами VPS.

Production-таймер создаёт копию ежедневно в **02:15 UTC** с задержкой
0–5 минут. Для Москвы это 05:15–05:20. Домашний
`tessavie-backup-pull.timer` проверяет новые архивы каждый час, также с
задержкой 0–5 минут. Оба таймера имеют `Persistent=true`: после пропущенного
запуска будет проверка при возвращении машины/таймера. Это не восстановление
копий за каждый час или день простоя.

Домашняя служба работает без root, с закрытой для записи системой и явным
доступом на запись только к состоянию и хранилищу. Используются
`NoNewPrivileges`, отдельный временный каталог, запрет устройств и ограничение
семейств адресов. Minecraft и приложение ради установки не перезапускаются.

Недоступность домашнего узла не мешает локальному production-backup.
Ошибка локального экспорта отмечает неуспех всего backup-unit через
`ExecStartPost`, но успешно созданный перед этим локальный архив сохраняется.
При разборе такой ошибки нужно различать создание копии и публикацию экспорта.

## Порядок установки и повторной проверки

Это воспроизводимый порядок обслуживания. Он не означает, что команды нужно
повторять поверх работающей установки без предварительной сверки состояния.

1. На обоих узлах сверить действующие службы, свободный диск, каталоги и права.
   На VPS убедиться, что основной backup сейчас не выполняется; действующий
   backup не прерывать ради замены скрипта. Проверить public health приложения
   и состояние Minecraft для сравнения после работ.
2. Сверить исходные файлы и их SHA-256, выполнить изолированные тесты на Linux.
   Перед заменой установленного скрипта сохранить прежнюю версию как
   операционный артефакт с закрытым доступом. Не переносить туда ключ или env.
3. На VPS создать выделенного читателя, группу, контролируемую root область
   SSH-авторизации и экспортный каталог с правами из таблицы. Установить
   экспортёр и исправленный основной backup-скрипт из соответствующих файлов
   `deploy`; не выдавать читателю доступ к исходному backup-каталогу.
4. На домашнем узле создать `tessavie-backup`, приватные каталоги состояния
   и истории. Создать его SSH-ключ на этом узле. Закрепить проверенный ключ
   хоста VPS в выделенном known_hosts. Передать публичный ключ на VPS
   с forced command и `restrict`; проверить владельцев и права.
5. Установить конфигурацию домашнего клиента. Источник фиксирован:
   `source_host=159.194.231.150`, `source_port=22`,
   `source_user=tessavie-backup-reader`; пути `identity_file`, `known_hosts`,
   `vault_dir` и `state_path` должны быть абсолютными, без symlink и `..`.
   Квоты и свежесть берутся из описанных значений по умолчанию, если явные
   допустимые значения не заданы в конфигурации.
6. На VPS установить drop-in из `deploy/tessavie-backup-export.conf` и
   перечитать unit-файлы через `systemctl daemon-reload`. На домашнем узле
   установить `tessavie-backup-pull.service` и `.timer` в
   `/etc/systemd/system`, затем также перечитать unit-файлы. Проверить
   их синтаксис и фактическое слияние drop-in с основной службой.
7. На VPS выполнить штатную backup-службу и убедиться в успешной публикации
   манифеста. На домашнем узле сначала выполнить один ручной запуск службы.
   Сверить число, размеры и SHA-256 доставленных файлов с экспортом.
8. Повторить домашний запуск: новых загрузок быть не должно, прежние файлы
   должны сохраниться. Проверить отказ произвольной команды, попыток получить
   сторонний путь, SFTP и перенаправления порта с этим ключом.
9. Только после успешного прохода включить домашний таймер:
   `systemctl enable --now tessavie-backup-pull.timer`. Проверить следующий
   запуск, состояние обеих backup-служб, health приложения, Minecraft,
   свободный диск и применённые ресурсные ограничения.
10. Добавить фактические результаты и идентификаторы проверок в заключительный
    раздел этого отчёта. Наличие файлов в Git не является подтверждением
    установки, а наличие encrypted-файла — проверкой восстановления дома.

## Контроль работы и разбор отказов

На домашнем узле используются `systemctl status tessavie-backup-pull.service`,
`systemctl list-timers tessavie-backup-pull.timer`, журнал этой службы и
`/var/lib/tessavie-backup-client/status.json`. Для завершившейся oneshot-службы
состояние `inactive` нормально; важны результат последнего запуска, таймер
и содержимое status. На VPS проверяют `business-control-backup.service`,
его таймер и свежесть экспортного манифеста.

`last_success_at` сохраняет время последнего успешного прохода. При ошибке
передачи оно не заменяется текущим временем. `source_age_seconds` и
`source_fresh` вычисляются по самому свежему имени архива. Если оно старше
48 часов, клиент сохраняет уже скачанные файлы, но завершает проход ошибкой
`source_archive_stale`. Успешное ежечасное соединение само по себе не должно
скрывать остановку создания новых копий на VPS.

Оповещения в почту, мессенджер или внешний мониторинг этим выпуском не
подключены: ошибки видны в systemd и status. При выключенном домашнем узле
он сам не может сообщить о собственном простое. Отдельный внешний контроль
следует подключать как отдельное действие с выбранным каналом уведомления.

| Отказ | Проверка и восстановление |
| --- | --- |
| `ssh_failed` / `ssh_timeout` | Связность с VPS, доступность sshd, ограниченный ключ и закреплённый host key; строгую проверку ключа не отключать |
| `source_archive_stale` | Production-таймер и журнал создания/экспорта; исправить источник и повторить клиент |
| `vault_budget_exceeded` / `free_space_reserve` | Измерить диск и содержимое vault; увеличить том/осознанно изменить квоту либо отдельно утвердить хранение; автоматически историю не удалять |
| `existing_archive_conflict` | Зафиксировать размеры и SHA обеих сторон; существующий файл не заменять. Проверить происхождение расхождения до ручных действий |
| Ошибка манифеста, symlink, неожиданный объект | Осмотреть владельцев и конкретный путь. Не обходить валидацию и не расширять доступ читателю |
| `already_running` | Найти активный запуск и дождаться его завершения. Удаление lock-файла не является корректным снятием блокировки |
| Неуспех export после успешного backup | Локальный архив проверить отдельно; восстановить публикацию и запустить экспорт, не удаляя оригинал |

Обычное исключение или обработанный SIGTERM очищает собственный незавершённый
файл клиента. Жёсткое завершение процесса или отключение питания может оставить
`.pull-*.partial`; такие файлы учитываются в квоте. Экспортёр при обычной ошибке
тоже убирает свой временный файл, но оставшийся после аварии `.export-*.partial`
намеренно блокирует последующий экспорт как неожиданный объект.

Для восстановления после такой аварии сначала остановить соответствующий
таймер и дождаться завершения действующей службы. Если обслуживается VPS,
не прерывать основной backup: дождаться его окончания, исключить параллельный
ручной экспорт и удерживать `.export.lock` при очистке. Для домашней стороны
исключить активную службу и удерживать `pull.lock`. Затем проверить конкретные
имена, `lstat`, владельца, отсутствие symlink и принадлежность пути ровно
соответствующему каталогу. Допустимо убрать только подтверждённый собственный
незавершённый temporary-файл; финальные `.tar.gz.enc`, исходные архивы,
манифест и посторонние файлы этим порядком не удаляются. Не применять
рекурсивную очистку каталога или широкий шаблон для всех файлов. После
проверки выполнить один ручной проход, убедиться в успехе и вернуть таймер.

## Что означает проверка копии и что требуется для восстановления

Совпадение SHA-256 подтверждает, что на домашний диск доставлен тот же
encrypted-файл, который опубликован VPS. Оно не доказывает доступность
ключа после потери VPS, возможность запуска приложения из архива и защиту
от подмены одновременно архива и контрольной суммы на скомпрометированном
источнике. Домашнее расшифрование и запуск восстановленной базы этим этапом
не подтверждены.

Ключ `/etc/business-control-backup.key` остаётся на VPS; он не копируется
рядом с домашними архивами. **Владельцу нужна доступная независимая копия этого
ключа вне VPS, отдельно от истории архивов.** Без неё потеря VPS может сделать
домашние encrypted-файлы непригодными для восстановления. Ключ не следует
включать в Git, журнал команд, отчёт или отправлять открытым текстом в чат.
Факт создания такой независимой копии нельзя считать выполненным по наличию
этой рекомендации.

Payload ежедневной копии содержит SQLite, uploads и манифест файлов.
Он не является образом всей машины и не включает
`/etc/business-control.env`, приложение, конфигурацию веб-сервера и всю
операционную конфигурацию. Для восстановления отдельно нужны совместимая
версия приложения из Git/релиза, необходимые настройки и секреты. Проверочный
прогон должен расшифровать выбранную копию в изолированном приватном каталоге,
проверить манифест и SQLite, затем проверить совместимое приложение без
подключения восстановленной тестовой копии вместо рабочей базы.

## Откат без удаления истории

1. На домашнем узле отключить таймер
   `systemctl disable --now tessavie-backup-pull.timer`. Если служба ещё
   выполняется, дождаться её завершения либо остановить её штатным SIGTERM
   через systemd. Сохранить `status.json`, журнал и все готовые архивы.
2. На VPS после завершения активного backup отключить только добавленный
   drop-in экспорта, сохранив его как операционный артефакт вне набора
   загружаемых `.conf`, и выполнить `systemctl daemon-reload`. Убедиться,
   что прежние backup-service и daily timer продолжают действовать.
3. При необходимости закрыть доступ домашнего ключа: сохранить и отключить
   именно его ограниченную запись в `authorized_keys` читателя. Не заменять
   настройки root SSH, не удалять посторонние ключи и не открывать оболочку
   читателю для обхода проблемы.
4. Сохранить исходные backup, домашний vault, экспортные дубликаты, пользователей
   и конфигурацию для расследования и возможного возврата. Их физическая
   очистка не входит в остановку копирования. Полезную атомарную публикацию
   основного backup можно оставить: она не зависит от работающего клиента.
5. Повторно проверить локальную копию и public health. Перезапуск приложения
   или Minecraft, перенос рабочей базы и откат пользовательских данных
   для отключения внешней истории не требуются.

## Проверки этого этапа и граница подтверждения

По результатам установки переданы следующие подтверждения: на VPS установлены
выделенный читатель, экспортёр, атомарная публикация основного backup и drop-in;
на домашней стороне — клиент и unit-файлы. Фактический production-backup
выполнился успешно, набор из 40 архивов указан выше.

В изолированной Linux-среде прошли **11 тестов экспортёра, 14 тестов клиента
и 3 проверки публикации основного backup**. Они проверяют отказ опасных команд
и путей, границы объёма, неизменность исходников, отсутствие перезаписи,
прерывание передачи, неверные размер/SHA, сохранение домашней истории,
состояние при ошибке и просроченном источнике. Проверки публикации отдельно
проверяют завершённый архив и поведение при конфликте имени.

Первая передача проверяется на реальных установленных службах. Итоговые числа,
SHA программ, результаты запретов SSH, повторного прохода, состояние таймеров,
здоровье приложения и Minecraft и измерения после установки добавляются
следующим разделом по фактическому receipt. До такого дополнения этот текст
не объявляет весь эксплуатационный этап завершённым и не утверждает, что
проверено восстановление приложения на домашнем сервере.

## Воспроизведение Linux-проверок

Проверки выполняются из приватной копии перечисленных файлов deploy,
с тестовыми данными и без production env. Для тестов экспорта указать TMPDIR
на файловой системе с запасом более 512 MiB. Первая попытка использовать
маленький VPS tmpfs закономерно получила отказ по свободному резерву;
после переноса тестового каталога на корневой диск все 11 проверок прошли.
Это не требовало уменьшать рабочий предохранитель.

```bash
TMPDIR=/var/log/business-control-maintenance/home-backup-20260914/tests-tmp \
  python3 /var/log/business-control-maintenance/home-backup-20260914/tessavie_backup_export_test.py
python3 /var/log/business-control-maintenance/home-backup-20260914/tessavie_backup_pull_test.py
python3 /var/log/business-control-maintenance/home-backup-20260914/business_control_backup_publication_test.py
```

Каталог TMPDIR должен уже существовать и иметь права root 0700. Последний
тест требует Linux/root, sqlite3, tar и OpenSSL: он создаёт временные SQLite,
вложение и отдельный случайный тестовый ключ, проверяет расшифрование,
целостность и отказ от перезаписи, затем удаляет только свой тестовый каталог.
Приватные исходные данные приложения и его ключ в этом тесте не используются.
Клиентские 14 проверок дополнительно прошли на самом домашнем Ubuntu 24.04.
