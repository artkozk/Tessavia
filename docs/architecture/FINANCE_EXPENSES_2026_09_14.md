# Личные расходы и остатки направлений — 14.09.2026

## Основание и сохранение прежнего контракта

Пользователь описал ежедневный сценарий: деньги распределены по направлениям,
затем часть потрачена на покупку или перечислена внешнему получателю. Ранее
финансы учитывали поступления и отметки распределения. Эти отметки не отвечали
на вопрос, сколько средств осталось после фактических трат. Новый этап добавляет
самостоятельный регистр расходов и накопительные остатки. Функция доступна
любому владельцу аккаунта в его личном пространстве, без команды.

Исторический контракт `PERSONAL_FINANCE_2026_09_12.md` остаётся без удаления.
Там «остаток» в разделе переводов обозначает сумму, ещё не отмеченную переводом.
Здесь «остаток направления» имеет новое, отдельное определение: все выделенные
в него средства минус все записанные расходы до выбранной даты включительно.
Интерфейс должен различать эти показатели.

Направление (`bucket`) — это конверт бюджета с произвольным названием и
назначением. Оно не подтверждает остаток в банке. Перевод между собственными
банковскими счетами не уменьшает бюджет. Покупка, оплата услуги или перечисление
денег внешнему получателю записывается расходом выбранного направления.
Автоматического выполнения банковского перевода нет.

`paidMinor` старых поступлений остаётся исключительно отметкой распределения.
Миграция не превращает такие отметки в расходы: по сохранённым данным нельзя
достоверно определить, был ли перевод внутренним или внешним. Это предотвращает
повторное списание уже учтённых пользователем денег и неверное изменение истории.

## Хранение

Миграция `069_personal_finance_expenses.sql` добавляет две таблицы:

| Таблица | Назначение |
| --- | --- |
| `personal_finance_expenses` | Расход, направление, сохранённое имя направления, дата, сумма, получатель, заметка, ревизия и признак отмены |
| `personal_finance_expense_requests` | Ключ создания и хеш запроса, чтобы повтор после обрыва связи не записывал расход второй раз |

Существующие таблицы, строки поступлений, схемы распределения, отметки переводов
и их квитанции не изменяются. Составные внешние ключи связывают расход и
направление одного владельца, а квитанцию — с расходом того же владельца.
На `owner_id,date,id` есть индекс журнала.

Удаления расхода нет. Отмена сохраняет строку в истории, исключая её из итогов;
восстановление возвращает влияние на остаток. Ревизия и дата последней правки
обновляются при каждом успешном изменении. Это не отдельная бухгалтерская книга
неизменяемых проводок: полная история каждой промежуточной редакции в данном
этапе не вводится.

## API расходов

Все маршруты находятся под `/api/personal/finance`. Они берут владельца только
из действующей сессии, игнорируют команду и переданные `ownerId`, не публикуют
данные в командной активности или уведомлениях. Ответы имеют `Cache-Control:
no-store`. Чужой ID расхода или направления не раскрывается и получает 404.

### Создание

`POST /expenses`:

```json
{
  "clientRequestId": "unique-expense-request",
  "bucketId": "own-bucket-id",
  "expectedBucketRevision": 1,
  "date": "2026-09-14",
  "amountMinor": 120050,
  "payee": "Магазин",
  "note": "Покупка"
}
```

`clientRequestId` обязателен, длина 8–128 байт, без пробелов по краям.
`expectedRevision` при создании должен отсутствовать или равняться нулю.
Направление должно быть действующим и принадлежать владельцу.
`expectedBucketRevision` должен совпасть с текущей ревизией выбранного
направления, чтобы устаревшая форма не сохранила непроверенный выбор.

Сумма — положительное целое число копеек не более `1_000_000_000_000`.
Даты допускаются с `1900-01-01` по `9998-12-31`; день должен существовать
в календаре. Получатель необязателен, до 120 символов; заметка необязательна,
до 2000 символов. Имена получателя и заметки обрезаются по краям перед
канонизацией запроса и сохранением.

Первый успешный запрос возвращает 201. Повтор того же ключа и содержимого
возвращает 200 и актуальную ранее созданную запись, включая последующие
исправления/отмену. Повтор ключа с другим содержимым возвращает 409.
Запись расхода и квитанция создаются одной транзакцией.

### Чтение, исправление, отмена

`GET /expenses/{id}` возвращает актуальную запись. Маршрут нужен для открытия
и восстановления после конфликта: другая вкладка могла изменить дату, из-за
чего расход больше не входит в текущий период журнала.

`PUT /expenses/{id}` принимает те же поля без ключа создания, а также
обязательную совпадающую `expectedRevision`. При смене направления нужна
актуальная `expectedBucketRevision` нового действующего направления.
При правке в том же направлении прежнее имя-снимок сохраняется; архивирование
направления не мешает исправить уже существующую запись. Отменённый расход
сначала нужно восстановить, иначе возвращается 409.

`PATCH /expenses/{id}/void` принимает:

```json
{"expectedRevision": 2, "voided": true}
```

Значение `false` восстанавливает расход. Поле `voided` обязательно: отсутствие
не трактуется как команда восстановления. Устаревшая ревизия возвращает 409.
Операции используют проверку ревизии и в SQL-условии обновления.

Ответ расхода: `id`, `bucketId`, `bucketName`, `date`, `amountMinor`, `payee`,
`note`, `revision`, `voided`, `createdAt`, `updatedAt`.

## Итоги и границы периода

`GET /api/personal/finance?from=YYYY-MM-DD&to=YYYY-MM-DD` сохраняет прежние
`currency`, `buckets`, `sources`, `counterparties`, `entries` и добавляет:

| Поле | Значение |
| --- | --- |
| `expenses` | Расходы выбранного периода, включая отменённые, от новых к старым |
| `balanceThrough` | Дата `to`, до которой рассчитаны остатки включительно |
| `balances` | Итог каждого направления владельца, включая архивные и пока пустые |

Каждый элемент `balances` содержит:

| Поле | Расчёт |
| --- | --- |
| `bucketId` | ID направления |
| `allocatedMinor` | Все распределённые средства неотменённых доходов с датой ≤ `to` |
| `spentMinor` | Все неотменённые расходы направления с датой ≤ `to` |
| `balanceMinor` | `allocatedMinor - spentMinor` |
| `periodAllocatedMinor` | Распределено в диапазоне `from..to` |
| `periodSpentMinor` | Потрачено в диапазоне `from..to` |
| `openingMinor` | Распределено до `from` минус потрачено до `from` |

Распределение читается из сохранённых снимков поступлений. Изменение нынешних
процентов источника не пересчитывает прошлое. Оплата работников уже вычтена
из базы поступления и не списывается второй раз как расход направления.

Журнал ограничен 5000 доходами и отдельно 5000 расходами выбранного периода.
Если превышен один из пределов, ответ 422 предлагает сузить период; усечённый
массив не выдаётся за полный. Накопительные итоги рассчитываются отдельным
чтением всей истории до `to`, независимо от начальной даты и предела журнала.
Пустой день поэтому показывает правильный перенос остатка прошлого месяца.

Отрицательный остаток допустим. Фактическая трата должна сохраниться и при
неполной истории доходов; запрет записи скрыл бы реальное движение денег.
Такой остаток не исправляется автоматически и не ограничивается нулём.

Арифметика ведётся в целых копейках. Общие накопительные выделения и расходы,
а также итоги по направлениям проверяются на точный диапазон JSON-чисел
браузера: до `9_007_199_254_740_991` копеек. Переполнение даёт явный 422,
не округляет отчёт и не меняет сохранённые записи. Разница двух неотрицательных
ограниченных сумм и начальный остаток остаются в том же точном диапазоне.

## Проверки и остающиеся ограничения

Backend-проверки находятся в `personal_finance_expenses_test.go`. Они проходят
через HTTP настоящего тестового сервера и временную SQLite, без реальных
денежных данных. Проверяются:

1. Перенос между месяцами, расход текущего дня, внешняя регулярная выплата,
   исключение будущего периода и сохранение перевода между своими счетами.
2. Исправление суммы и направления, устаревшая ревизия, отмена/восстановление,
   отрицательный остаток и сохранённое имя архивного направления.
3. Чужой аккаунт, администратор общей команды, неавторизованный доступ,
   составные внешние ключи и отсутствие расходов в общих API.
4. Десять конкурентных повторов создают один расход и одну квитанцию;
   две конкурентные правки одной ревизии дают один успех и один конфликт.
5. 5001 историческое поступление и 5001 исторический расход участвуют
   в переносе, хотя каждый журнал за прежний день превышает свой предел.
6. Сохранность старых `allocations_json`, `paidMinor` и хеша квитанции при
   миграции; отсутствие автоматически созданных расходов.
7. Чтение актуального расхода после переноса в другой месяц и защита точности.

Фактические команды, результаты, браузерная проверка и выпуск дополняются
операционным отчётом; наличие этого контракта само по себе не означает деплой.
Банковский импорт, обмен валют, кредитные долги, полноценные счета с проводками
между ними и автоматические регулярные расходы остаются отдельными задачами.
Конструктор произвольных финансовых приложений не объявляется завершённым
появлением данного общего модуля.

## Защита миграции и отката общего выпуска 069/070

Выпуск объединяет расходы 069 и библиотеку собственных блоков 070. Скрипт
`deploy/verify-finance-expenses-migration.py` самостоятельно открывает переданные
БД только через SQLite URI `mode=ro`. Он не создаёт отсутствующую БД и не меняет
production-файлы. Проверяются 123 прежние таблицы и 127 таблиц после обновления.

Для исходной схемы проверены два независимых источника: синтетическая `audit.db`
до обновления и новое воспроизведение миграций 001–068. Их отпечатки объектов
схемы совпали. Хеш содержит только определения SQL, без строк и личных данных.
В скрипт также встроены точные тексты 069/070; тест сравнивает их с репозиторием,
чтобы изменение миграции не оставило устаревший проверяющий код.

При сравнении до/после сверяются все строки прежних таблиц, включая дубликаты,
типы SQLite, NULL и BLOB. В `schema_migrations` допустимы только две новые
квитанции; прежние даты квитанций сохраняются. На копии схемы воспроизводится
точный SQL новых миграций и сравниваются таблицы, индексы, триггеры, ограничения
и внешние ключи. Четыре новые таблицы должны быть пустыми. Дополнительно
выполняются integrity и foreign-key проверки.

Режим `--rollback-safe DB` допускает только точную исходную схему 068 либо
полную схему 070 с пустыми таблицами расходов, квитанций расходов, компонентов
и установок компонентов. Любая запись в этих таблицах блокирует откат, даже
если расход отменён. Частичная миграция, неизвестная версия, дополнительная
таблица/индекс, изменённое ограничение или повреждение данных также блокируют
откат. Старый бинарник не должен скрыть от пользователя новые данные или
переписать неподдерживаемое состояние.

`deploy/verify_finance_expenses_migration_test.py` содержит 18 синтетических
проверок. Все прошли за 4,403 секунды: точный перенос, защита старых переводов
и квитанций, блокировка по новым данным, частичной/изменённой схеме и чужим
внешним ключам, неизменность файлов при чтении, запрет создания отсутствующей
БД. Скрипт в ошибке выводит только общий результат, без пользовательских
значений и текста повреждённых данных.
