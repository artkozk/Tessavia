## Автор, координатор и исполнитель

Автор (`authorId`) определяется аккаунтом, от которого выполнено создание через
API. Поэтому карточки создаются от явно указанного пользователем автора;
административную настройку схемы выполняет оператор с существующими правами.
Переданная в произвольном JSON подпись автора сама по себе не заменяет этот шаг.

Текущая модель требует зарегистрированного системного владельца (`ownerId`):
пустой ID подставляет текущий аккаунт. Пользователь разрешил временно указать
создателя координатором. Это техническое ограничение не превращает его в
исполнителя каждой исходной задачи. Распределение хранится отдельным редактируемым
полем **«Исполнитель»**: два имени из таблицы и «Не назначен» для пустых назначений.
Оригинальный снимок назначения также остаётся в описании для проверки происхождения.

Общая страница задач показывает фактического исполнителя и не добавляет
системного владельца в карточку канбана. Однако стандартное полное досье,
общий фильтр «Моя работа» и расчёт загрузки пока используют `ownerId`.
Их нельзя выдавать за персональную очередь незарегистрированного исполнителя.
В материалах доски это ограничение объяснено. После регистрации участников
аккаунты необходимо сопоставить вручную, сверив личность; совпадение имени
не служит основанием для выдачи доступа или автоматического назначения.

## Представление для команды

- Существующая доска получает исходные состояния: «Не начато», «Ожидает ответа»,
  «В работе», «Готово». Настройка изменяет только эту первоначально пустую доску.
- Общая страница **«Задачи форума»** отбирает только задачи этой доски, показывает
  все четыре состояния, сроки, исполнителя и блок. Это представление тех же
  карточек, а не второй набор данных.
- Общая страница **«Материалы форума»** показывает отдельный документ с программой,
  рабочими ссылками, оговорками о датах и инструкцией по назначениям и зависимостям.
  Документ не увеличивает счётчик задач: предусмотрено 81 задача и один документ.
- Девять необязательных полей сохраняют происхождение. Только исполнитель и блок
  включены в краткую карточку, чтобы длинная таблица не превратила канбан в анкету.
- Дата из Excel переносится как плановый срок до конца дня UTC+3. Это явное
  соглашение представления даты, а не новое время встречи. Предварительный характер
  дат и отсутствие автоматического пересчёта указаны в описании.

Создание ожидающей задачи непосредственно в активном этапе перезаписывает её
статус на `in_progress`. Поэтому такие задачи сначала создаются как `blocked`,
затем прикрепляются к выбранному этапу штатным API с проверкой ревизии.
Документ аналогично сохраняет `draft`. Готовая задача переносится готовой по
источнику; время создания в платформе не объявляется фактической датой выполнения.

## Порядок применения и восстановления

Переносчик `deploy/import-task-workbook-plan.py` принимает отдельный проверенный
JSON-план, а не исполняет инструкции или макросы из книги. Перед записью требуется
проверить SHA256 плана, идентичность команды, доски, автора, координатора, доступ
оператора и текущую версию приложения. Изменения карточек и схемы выполняются API.
Краткоживущие сессии используются только во время обслуживания и удаляются после
работы; токены не выводятся и не записываются в документацию.

До бизнес-изменений создаётся согласованная SQLite-копия на том же VPS. Повторный
запуск использует стабильные ключи создания и маркеры происхождения, проверяет
уже созданные поля, страницы и связи. Он не должен молча перезаписывать правки
пользователей или создавать второй комплект после потерянного ответа.
Если перенос прервался, сначала перечитываются созданные записи и журнал,
продолжение выполняется тем же планом. Полный откат живой БД поверх последующей
работы команды автоматически не выполняется.
