## Правило исторической связи

Архивирование проекта, цели или родительского дела не должно лишать человека
возможности завершить уже сохранённое дело и не должно незаметно отрывать его
от истории. Поэтому валидатор получает два разных значения: подготовленное
изменение и предыдущий объект, прочитанный в той же транзакции с проверкой
владельца. Предыдущее состояние не берётся из клиентского тела.

Для каждой непосредственной связи действуют правила:

| Связь | Результат |
| --- | --- |
| Своя доступная неархивная сущность | Можно выбрать или сохранить |
| Своя архивная сущность, тот же ID уже сохранён в изменяемом объекте | Можно сохранить прежнюю связь |
| Своя архивная сущность, которой не было в изменяемом объекте | Новая привязка отклоняется |
| Чужая или отсутствующая сущность | Отклоняется, даже если ошибочный ID уже был сохранён раньше |
| Явно убранная или заменённая недопустимая ссылка | Можно исправить при соблюдении остальных проверок |

Отсутствующая ссылка и чужой ID не раскрывают заголовок и владельца. Ошибки
предлагают убрать связь или выбрать другую сущность. Уже существующие ошибочные
строки не очищаются массово; пользователь может исправить конкретное дело.
Проверка `expectedUpdatedAt` и атомарная запись всех полей сохраняются.

Цель может наследовать свой проект в дело, когда у дела проект не задан.
Проверка проекта теперь выполняется **после** этого наследования: активная цель
архивного проекта не даёт создать новую архивную связь обходным путём.
Существующая прежняя согласованная пара проекта и цели сохраняется.

Если саму цель позднее перенесли в другой проект, сохранённое дело может иметь
старую несогласованную пару. Прежняя проверка соответствия оставлена: нужно
выбрать согласованную пару или убрать цель. Этот выпуск не переносит связанные
дела вслед за целью и не переопределяет правило её перемещения; такой сценарий
редактора цели и общего экрана остаётся отдельным направлением.

## Родительская цепочка

Владелец и состояние непосредственного родителя проверяются и при создании,
и при PATCH. Выполненный свой родитель остаётся допустимым, поскольку выполнение
не означает архивирование. Прежний свой архивный родитель остаётся исторической
связью, но выбрать его впервые нельзя.

Рекурсивный CTE обходит только узлы текущего владельца, включая архивных предков.
`UNION` вместо `UNION ALL` устраняет повторное посещение пары `(id,parent_id)`.
Поэтому цикл `B → C → B` завершается и отклоняется, даже когда изменяемое дело A
в этот цикл ещё не входит. Архивирование B также не скрывает цикл от проверки.

Корректная цепочка должна закончиться единственным своим корнем без родителя
и не содержать изменяемое дело. Обрыв на чужом или отсутствующем предке не
считается корректным корнем. Привязать ещё одно дело к повреждённой цепочке нельзя;
ошибка не раскрывает сведения о чужом предке. HTTP-регрессия циклов использует
ограниченное время клиента, чтобы зависание было явным провалом проверки.

## Повторяющиеся дела

Повторение уже настроенной серии продолжает прежнюю работу; оно отличается
от ручного выбора новой архивной сущности. Для будущего экземпляра доверенным
предыдущим объектом служит сохранённый шаблон этой серии, прочитанный по владельцу.
Владение каждой сущностью всё равно проверяется заново.

Один валидатор используется в следующих местах:

1. Создание личного дела: предыдущего объекта нет.
2. PATCH существующего дела и пропуск экземпляра: предыдущая строка дела.
3. Изменение всей серии: предыдущий выбранный экземпляр, затем отдельно
   предыдущий шаблон и каждый изменяемый сохранённый экземпляр.
4. Сохранение шаблона: предыдущий шаблон этой же серии.
5. Создание следующего экземпляра после завершения или пропуска: предыдущий
   шаблон; проверка есть непосредственно перед INSERT экземпляра.
6. Материализация будущего повторения из календаря: предыдущий шаблон и та же
   проверка вставки. Повтор уже материализованной даты возвращает прежний ID.

Таким образом, свои архивные project/goal/parent продолжают переходить в
экземпляры той серии, где эти связи уже сохранены. Новая ручная серия с такими
архивными ссылками отклоняется. Если только единичное исключение успело получить
родителя до его архива, это не разрешает впервые скопировать архивную связь
из исключения во весь шаблон. Само исключение можно завершить с прежней связью;
следующее дело получит исходные связи серии.

Повреждённый шаблон с чужим родителем отклоняет завершение со следующим
экземпляром, пропуск и новую материализацию. Изменение текущего дела, запись
следующего экземпляра и его отображения в таблице экземпляров откатываются
вместе. Пользователь получает исправляемую ошибку 400, а не частично выполненную
операцию. Явное исправление шаблона через редактирование серии восстанавливает
обычное продолжение. Автоматическая очистка шаблона не выполняется.

Если обновление серии пытается добавить недопустимую ссылку хотя бы одному из
её экземпляров, вся операция откатывается, включая новую версию правила и
шаблона. Ошибки целостности ссылок выделены в отдельный тип, чтобы показывать
конкретную исправляемую причину; непредвиденные ошибки хранилища остаются 500.

## Приватные подписи прежних связей

`GET /api/personal/overview` дополнен полем:

```json
{
  "historicalReferences": {
    "projects": [{"id": "...", "title": "..."}],
    "goals": [{"id": "...", "title": "..."}],
    "parents": [{"id": "...", "title": "..."}]
  }
}
```

Все три массива присутствуют, в том числе когда пусты. Запрос отбирает только
собственные архивные сущности, на которые реально ссылаются свои неархивные
дела текущего пользователя. Ни чужая сущность с ошибочно сохранённым ID, ни
несвязанный личный архив в это поле не попадают. В ответе нет заметок, содержимого
и других полей архивных объектов. После явного снятия последней такой связи
подпись исчезает из этого списка.

Основные `projects`, `goals` и `plans` сохраняют прежнюю семантику и не расширяются
архивами. Интерфейс может добавить в селектор лишь прежнюю архивную ссылку
редактируемого дела, а не использовать исторический список как новые варианты.
Неизвестный прежний ID получает нейтральное описание без чужого заголовка.
Ответ обзора помечен `Cache-Control: private, no-store`.
Клиентский контракт и проверки отдельно описаны в
[PERSONAL_PLAN_REFERENCES_UI_2026_09_14.md](PERSONAL_PLAN_REFERENCES_UI_2026_09_14.md).

- наследование проекта, циклы через архив, уже существующий сторонний цикл
  и чужой предок;
- завершение → следующий экземпляр, правка серии, будущая материализация и
  повтор той же даты, пропуск → следующий экземпляр, чужой аккаунт и stale CAS;

  строк, затем явное исправление и успешное продолжение;
- отказ распространить новую архивную связь единичного исключения на шаблон
  серии, сохранность версии/шаблона и независимость следующего экземпляра.

## Хранение и откат

Новых миграций, колонок и таблиц нет: схема остаётся на миграции 070. Запуск
приложения не исправляет старые связи фоновым SQL и не удаляет архивные сущности.
Сохранённые ID и история продолжают использовать существующие таблицы.

При откате к e881e41 прежний бинарник прочитает эти данные, но вернутся прежние
поведенческие дефекты: чужой родитель может быть принят при PATCH, а изменение
дела с архивным проектом/целью снова может получить отказ. Поэтому одинаковая
схема не означает сохранения новых гарантий старым бинарником. Откат сохраняет
последнюю БД и новые пользовательские изменения; обратной миграции и очистки
исторических ссылок не предусмотрено.
