# Справочник плательщиков и расчётные листы — подготовка выпуска 13.09.2026

## Назначение и статус

Выпуск развивает два ограниченных сценария: повторное использование частного
справочника плательщиков в личных финансах и создание пользователем собственного
расчётного листа в конструкторе. Лист задаёт подписи, исходные числа, константы
и формулы со ссылками на другие результаты; настроенная схема переносится
набором без личного ввода.

Этот документ фиксирует подготовку и уже выполненные проверки. Он **не является
подтверждением завершённого production-деплоя**. Оператор дополняет его после
финальной сборки, commit/push, серверного dry run, переключения службы и записи
результатов задач. Исторические записи не удаляются.

Контракты:

- [личные финансы](../architecture/PERSONAL_FINANCE_2026_09_12.md);
- [расчётный лист](../architecture/PAGE_SHEETS_2026_09_13.md), включая коррекцию
  сохранения неактивного ввода и запрет кеширования личных чисел;
- [предыдущий выпуск](PERSONAL_FINANCE_2026_09_12.md).

Универсальный конструктор остаётся большим направлением. Этот выпуск не
подключает банки, не превращает браузерные формулы в денежные проводки,
не реализует произвольный исполняемый код и не завершает всю платформу.

## Изменения БД и защита данных

Миграция 067 добавляет таблицу `personal_finance_counterparties`, индекс
`personal_finance_counterparties_owner_name`, nullable-столбец `payer_id`
в `personal_finance_entries` и два триггера:
`personal_finance_payer_owner_insert`, `personal_finance_payer_owner_update`.
Триггеры запрещают ссылку на плательщика другого владельца. Историческое поле
`payer`, суммы, ревизии, снимки распределения и квитанции операций не
переписываются; старый `payer_id` остаётся NULL. Имена не сопоставляются
автоматически, справочник после миграции пуст.

Миграция 068 добавляет `page_app_sheet_values` с первичным ключом
`(page_id,block_id,user_id)`. Начальных значений нет. Сохранение схемы, GET
страницы и установка набора не создают личных снимков. Обычный участник
изменяет собственные числа; даже администратор не получает чужой ввод.

Ожидаемый результат обеих миграций — 123 таблицы. Все прежние строки должны
совпасть при проекции прежних столбцов. Для схемы допускаются только точные
изменения SQL 067 и 068; нельзя ограничиваться проверкой количества таблиц
или наличия одного столбца.

При изменении структуры расчётного листа неактивные личные числа сохраняются.
PUT заменяет только активные input-строки, а не весь скрытый снимок. Например,
сохранение оставшейся строки после временного переключения соседней в
константу не стирает старый ввод; при возвращении того же ключа он снова
доступен владельцу. Обе версии — схемы и личного снимка — проверяются в
транзакции. API возвращает `Cache-Control: private, no-store`.

Кандидат сначала запускается на серверной копии БД, с отключёнными напоминаниями
и отдельным каталогом uploads. Затем проверяются миграции, HTTP-ресурсы и
границы авторизации. Пробный запуск предыдущего бинарника выполняется только
на этой копии после проверки отсутствия использования новых функций.
Production-БД на данном шаге не изменяется и не скачивается.

После переключения предусмотрены локальный и публичный HTTP/HTTPS smoke,
health, nginx, active service, integrity/FK, обе строки миграций и 123 таблицы.
Пять ресурсов главной страницы — основной JS и четыре CSS, включая
`page-sheets.css`; новый `page-sheets.js` импортируется из page-apps и включён
в service worker. Проверяются также новые закрытые маршруты sheet PUT и
counterparties POST, а прежние календарь, чат, конструктор и читалка сохраняют
положительные проверки.

Незавершённый `conversion-preview` и вмешательство service worker через
`client.navigate(` запрещены отрицательными проверками. Незавершённая смена
типов полей остаётся вне выпуска. Проверка staged-ресурсов и итогового
бинарника обязательна: рабочий `web/app.js` может сохранять отдельно
незавершённые изменения, которые не должны попасть в кандидат.

## Точная сверка миграций и откат

Verifier сравнивает до/после только на серверных копиях. В памяти того же
сервера он воспроизводит точный включённый SQL 067 и 068 на копии исходной БД,
затем сопоставляет все объекты схемы с фактической мигрированной БД. Так
проверяется и содержимое новых триггеров, и точное изменение SQLite CREATE
TABLE после ALTER TABLE. В вывод попадают только общие результаты и названия
служебных таблиц, без финансовых строк или содержимого пользовательских схем.

Дополнительно проверяются:

1. Исходные 121 таблица, отсутствие новых таблиц и наличие миграции 066.
2. Ровно две новые таблицы и две новые квитанции миграций.
3. Все прежние строки в проекции прежних столбцов, включая даты прежних
   миграций, без изменений.
4. NULL во всех старых `payer_id`, пустота обеих новых таблиц.
5. Integrity и отсутствие нарушений внешних ключей.

Режим `--rollback-safe DB` запрещает старый бинарник, если уже существуют:

- строки нового справочника, включая архивные;
- связанные `payer_id`;
- любые строки личных значений расчётного листа, даже с пустым объектом;
- `kind:"sheet"`, свойство `sheet` (в том числе null или неактивное) в блоке
  страницы либо набора;
- новые ключи оформления sheetLabel/sheetValue/sheetUnit;
- схема, которую невозможно безопасно разобрать.

Причина: прежний бинарник может открыть БД, но при последующей записи потерять
новые свойства схемы или связи. Простая совместимость запуска не доказывает
безопасность использования старой версии после ввода новых данных.

Автоматический откат при ошибке выпуска останавливает службу и проверяет
последнюю production-БД. Если guard разрешает откат, меняется только бинарник,
данные сохраняются. Если guard запрещает откат, кандидат и все данные остаются
на месте, служба запускается обратно; скрипт возвращает ошибку и сообщение о
необходимости совместимого исправляющего выпуска. Новые данные не удаляются
ради прохождения проверки. Восстановление старой БД вместо текущей также
не является автоматической процедурой данного скрипта.

## Выполненная браузерная приёмка и оставшиеся шаги

По фактической проверке основного исполнителя:

- Создание плательщика прямо из формы дохода с общей заметкой сохраняет
  заполненные сумму, дату и пометку дохода.
- Два синтетических дохода объединяются в отчёте по выбранному плательщику;
  сумма и количество соответствуют исходным операциям. Нажатие на строку
  отчёта фильтрует сводку, распределение и список операций согласованно.
- При ширине 320 px финансовый диалог имел ширину 314 px и scrollWidth
  314 px; длинное название в раскрывающемся списке переносилось.
- Новая пустая страница → добавление расчётного листа → переименование строк
  → формула из поля ввода и константы → проверка расчёта → сохранение схемы:
  проверочные числа предпросмотра не стали личными значениями.
- Ввод личного числа, сохранение и перезагрузка восстановили ввод и результат.
- Пользователь вручную добавил третью вычисляемую строку со ссылкой на
  результат второй; после сохранения результат пересчитался без потери
  исходного личного числа.
- После выхода и входа под другим синтетическим аккаунтом тот же общий лист
  оказался пустым; новый личный ввод дал независимые результаты.
- При ширине 320 px расчётный лист полностью помещался, формы адаптировались.

Проверки арифметики проведены на синтетических значениях, без публикации
личных финансовых настроек пользователя. На одном из шагов финансовой
проверки после выбора в списке при 320 px зависла управляемая вкладка CUA.
Это не считается ни доказательством завершённой проверки, ни автоматически
доказанным дефектом приложения; восстановление вкладки и продолжение сценария
нужны отдельно. Физические телефоны пока не проверялись.

До итогового принятия остаются:

1. Проверка окончательного исправления локализованного числового ввода с
   запятой и связанной валидации конструктора.
2. Завершение прерванного узкого финансового сценария и повтор после
   окончательной сборки, если затронуты соответствующие файлы.
3. Общие Go/Node/vet, сравнение build inputs, commit/push и подготовка
   Linux-бинарника с окончательным SHA256.
4. Штатный серверный dry run и deploy с новой резервной копией.
5. Итоговые HTTP/HTTPS, сервисные проверки и запись доказательств в задачи.
