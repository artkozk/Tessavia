# Канонический GitHub-репозиторий и Wiki — 14.09.2026

## Назначение и решение пользователя

Пользователь создал отдельный GitHub-репозиторий `artkozk/Tessavia` и попросил
отправить туда Tessavie, поддерживать код и документацию актуальными, включая
GitHub Wiki. Этот документ фиксирует точную границу переноса, причину выбранной
схемы, порядок проверки и восстановления. Исторический remote
`artkozk/buisness-control` не удаляется: он сохраняется как `legacy`, чтобы
перенос не уничтожал доступ к прежнему месту публикации и не требовал force-push.

Канонической веткой нового репозитория является `main`. Рабочая папка остаётся
`C:\prog\Progects\Tessavia`; пустая папка `BizFlow` и родительский репозиторий
`C:\prog` не относятся к переносу. Это ограничение необходимо, потому что в
родительском Git находятся другие проекты и их незавершённые изменения.

## Что публикуется

В `artkozk/Tessavia` отправляется полная достижимая история `main` вместе с
текущим исходным кодом, тестами, deploy-процедурами и документацией Tessavie.
Временные сборки, рабочие базы, release-каталоги и локальные артефакты остаются
за пределами Git согласно `.gitignore`. Локальные ветки прежних этапов уже
включены в `main`; переносить их как отдельные активные ветки не требуется,
поскольку это создало бы ложное впечатление незавершённой параллельной работы.

Перед первой отправкой проверяются:

1. точный Git root и список изменений;
2. отсутствие незамерженных локальных веток;
3. целостность объектов `git fsck` и отсутствие объекта больше лимита GitHub;
4. подозрительные имена файлов и высокоточные шаблоны секретов в рабочем дереве
   и достижимой истории;
5. Go-, Node- и профильные Python-тесты текущего выпуска.

Секреты, рабочая SQLite-база, пользовательские вложения, серверные backup и
ключи резервного шифрования не публикуются. Документы могут описывать имена
переменных и безопасную процедуру, но не содержат их значений.

## Почему Wiki генерируется из репозитория

GitHub Wiki является отдельным Git-репозиторием. Если поддерживать её вручную,
README, архитектурные контракты и отчёты выпуска неизбежно расходятся. Поэтому
источником истины остаются `README.md` и все Markdown-файлы под `docs/`, а
`.github/workflows/sync-wiki.yml` после документальных изменений в `main`:

1. запускает `tools/build_wiki_test.py`;
2. строит Wiki во временном каталоге командой `tools/build_wiki.py`;
3. клонирует `artkozk/Tessavia.wiki.git` через ограниченный `GITHUB_TOKEN`;
4. поверх существующих страниц записывает сгенерированные версии;
5. коммитит и отправляет результат только при наличии отличий.

Каждая исходная Markdown-страница получает самостоятельное имя с префиксом
раздела. Это не даёт одинаковым именам из `architecture`, `product` и
`operations` перезаписать друг друга. Относительные ссылки на другие Markdown-
документы преобразуются в ссылки Wiki, а изображения, JSON и остальные файлы —
в ссылки на каноническую ветку основного репозитория. Сборка останавливается при
коллизии имён, вместо тихой потери одной из страниц.

`Home`, `Documentation`, `_Sidebar` и `_Footer` создаются автоматически. Индексы
архитектуры, продукта, эксплуатации, дизайна и проверки перечисляют фактические
источники. В главной странице и подвале фиксируется commit основного репозитория,
поэтому читатель может проверить, какой версии соответствует Wiki.

Исторические страницы Wiki не удаляются автоматикой. Это намеренное продолжение
правила проекта не стирать прежнюю документацию: изменившийся источник обновляет
свою текущую страницу, а исчезнувшая или переименованная страница не уничтожается
скрыто. Если когда-либо понадобится явная уборка Wiki, она оформляется отдельным
решением с перечнем страниц и проверяемым backup.

## Первая инициализация

Пустая GitHub Wiki не имеет Git-репозитория, поэтому до первого запуска workflow
в веб-интерфейсе создаётся одна стартовая страница. После этого первая ручная
синхронизация публикует полный сгенерированный набор. Созданный вручную текст не
является вторым источником истины: он заменяется сгенерированным `Home.md`.

Если GitHub Actions не получит доступ на запись, основной push остаётся валидным,
но Wiki не объявляется актуальной. Исправление ограничивается разрешением
`contents: write` для этого workflow или ручным push той же сборки; постоянный
персональный токен в репозиторий не добавляется.

## Локальная проверка и ручное восстановление

Без публикации страницы можно собрать так:

```powershell
python -m unittest discover -s tools -p 'build_wiki_test.py'
$wikiPreview = Join-Path ([System.IO.Path]::GetTempPath()) 'tessavie-wiki-preview'
python tools/build_wiki.py --output $wikiPreview --source-commit local-check
```

Выходной каталог обязан находиться вне рабочего дерева: генератор отклоняет
попытку записать сотни производных страниц внутрь репозитория. После сборки
проверяются количество страниц, наличие `Home.md`, навигации, копии README и
профильного документа этого выпуска.

Ручное восстановление Wiki использует тот же сгенерированный каталог и обычный
Git push в `https://github.com/artkozk/Tessavia.wiki.git`. Force-push не нужен.
Существующая история Wiki остаётся доступной средствами GitHub.

## Граница деплоя приложения

Перенос GitHub-репозитория и добавление синхронизации Wiki сами по себе не меняют
production runtime. Однако в рабочем дереве на момент переноса находится уже
подготовленный прикладной выпуск мобильных жестов и привычек «Сегодня». Его код,
проверки, commit, backup, deploy и production-приёмка выполняются по отдельной
процедуре `MOBILE_GESTURES_TODAY_RELEASE_2026_09_14.md`. Статус GitHub/Wiki и
статус приложения нельзя подменять друг другом.

## Критерии завершения

- `origin` указывает на `https://github.com/artkozk/Tessavia.git`, старый remote
  доступен как `legacy`;
- `main` нового репозитория совпадает с локальным `main`, без force-push;
- GitHub Wiki открывается и содержит сгенерированные Home, навигацию, README и
  все Markdown-источники;
- workflow следующего документального push либо обновляет Wiki, либо корректно
  завершает работу без нового commit, если содержимое уже совпадает;
- в документации записаны фактические commit, проверки и ограничения после
  завершения публикации; заранее они не выдаются за состоявшийся результат.
