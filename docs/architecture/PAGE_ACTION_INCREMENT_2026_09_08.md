# SC-81: вычисляемое изменение счётчика

## Причина и задача

Родительская задача 26c54f79aa1c9110536670ae8371a868 требует вручную собираемых сценариев с данными, формами и действиями, переносимых набором. После чтения живой карточки зарегистрирована узкая P0 e3462bb4cf8717ae77cb7f01f38c6103 — «Изменять счётчики действиями конструктора». ACTION_INCREMENT_TASK_2026_09_08.json фиксирует регистрацию.

Статическая установка значения SC-79 и условие SC-80 не позволяли сделать кнопку «Прочитана ещё глава» или «Увеличить оценку на час»: пользователь должен был каждый раз редактировать запись. Теперь он выбирает «Прибавить к текущему», задаёт числовой шаг и свою подпись. Отрицательный шаг вычитает. Обычная установка значения остаётся доступной; переход между способами явно меняет форму настроек.

## Конфигурация и поведение

В действии сохраняется необязательное operation: пустое значение или set означает прежнюю установку; add означает сумму текущего значения целевого поля и настроенного value. Новый способ доступен для number и money. Пользовательские ссылки и основные статусы/исполнители/сроки не включены в этот этап. Произвольный JavaScript не исполняется.

При выборе прибавления предлагается шаг 1. При переходе к установке значение очищается для явного ввода. Смена целевого поля возвращает установку и начальное значение нового поля. Независимое условие сохраняется; новое условие для add по умолчанию проверяет заполненность поля, для set — отличие от устанавливаемого значения. Всё входит в прежний локальный черновик и ревизию страницы.

Пустое поле, строка или логическое значение не превращаются автоматически в ноль. Предпросмотр сообщает, что поле нужно заполнить; для нового счётчика пользователь может задать 0 в начальном значении доски. Шаг 0 допустим и показывает неизменившееся значение. Для запрета нежелательного шага пользователь может задать условие SC-80.

Сервер вычисляет результат по актуальной записи при предпросмотре и повторно при подтверждении. Клиент не присылает готовое значение. Сохраняются права записи/пространства, активность страницы/поля, условие, ревизии страницы/записи, hash схемы и атомарность изменения с историей. Устаревшее подтверждение и повтор уже успешного запроса дают 409 без дополнительного прибавления. Новый предпросмотр после конфликта требует отдельного решения пользователя; автоматического повтора записи нет.

Числа остаются в существующей модели полей float64. Для сложения используются десятичные представления операндов через big.Rat, затем результат возвращается в модель поля: 0.1 + 0.2 даёт 0.3. Модуль исходного значения, шага и результата ограничен 9 007 199 254 740 991. Бесконечности, переполнение и шаг, полностью потерянный из-за точности числа, отклоняются. Это не бухгалтерская модель произвольной точности и не новая система округления денежных полей.

## Наборы и обратная совместимость

Операция входит в сохранённое действие набора; установка remap целевого поля и условия уже выполняется общим механизмом. Новая копия получает отдельную доску/поля, исходные записи не копируются и действия не выполняются при установке. Старые действия без operation сохраняют прежний смысл. Неизвестные операции, add у нечислового поля и некорректный шаг запрещены при сохранении/снимке/установке.

Миграций нет: схема 065, 117 таблиц. Старый SC-80 проигнорирует operation и ошибочно выполнит установку шага вместо суммы. Поэтому новый сценарий деплоя запрещает откат на SC-80 при наличии сохранённых нестандартных операций в страницах или наборах. Перед проверкой служба останавливается, чтобы исключить сохранение операции между проверкой и переключением; если откат запрещён, текущая служба запускается снова. История старых сценариев деплоя не переписывается. Данные из backup автоматически не восстанавливаются.

## Проверки

Полный Go internal/app 62.460 s, web 0.997 s, vet и 252 Node 919.611 ms прошли. После добавления проверки пустой записи целевые Go-тесты прошли за 0.819 s. Первые запуски выявили ошибку тестовой подготовки defaults: начальное значение задаётся PATCH после чтения актуальной схемы, а не POST создания поля; тест приведён к реальному контракту.

TestPageActionNumberResults проверяет 0, отрицательный шаг, дроби, пустое/строку/false, null, диапазон, потерю точности и допустимость операций. TestPageActionIncrementVersionsConditionAndKit проверяет начальный 0 из схемы, 0→1→2, отказ повторного подтверждения, ограничение условием, количество истории, независимую установку и применение, неизвестную операцию и пустую запись без истории. Существующие тесты прав, версий страницы/схемы и изоляции продолжают проходить.

Локальный сценарий собран через UI на синтетической странице SC-80: действие переименовано в «Добавить час на проверку», выбран add 1 и снято прежнее условие. Черновик закрыт, после reload явно восстановлен, режим и шаг сохранились. При открытом предпросмотре 0→1 второй редактор через локальный API изменил значение на 2. Старое подтверждение отклонено; явное обновление показало 2→3, подтверждение сохранило 3.

Через UI сохранён приватный набор SC-81 «Счётчики рабочего процесса», установлен пустой независимой страницей. Создана запись с длинным названием и исходными 2 часами; перенесённое действие увеличило до 3. В копии настроен шаг -0.5 и подпись «Убрать полчаса проверки»: отмена не изменила 3, новое подтверждение сохранило 2.5, reload подтвердил результат. SQL подтвердил разные доски/поля, по одной записи источника и копии, значения 3 и 2.5; ACTION_INCREMENT_LOCAL_2026_09_08.json. Сохранённый набор остался с исходным add 1.

Предпросмотр до/после, длинное название, настройки режима и отрицательный шаг просмотрены при 320×800 и обычной ширине. Кнопки и подписи доступны, базовая палитра сохранена; физических телефонов в проверке не было. Viewport сброшен после проверки.

## Границы и следующий критерий

Завершён только один вид вычисляемого действия над одним пользовательским полем. Выражения из нескольких полей, AND/OR, цепочки, условия произвольных элементов, динамические ссылки и полная читалка остаются открытыми. Следующая проверяемая возможность — действие копирования значения другого совместимого поля записи, с переносом обоих полей и проверкой версии их схем; затем выражения с понятной настройкой. Родительское направление не закрывается этим выпуском.

Фактическая квитанция выпуска записывается после backup, dry run и проверки production. Все исходные пользовательские данные и исторические разделы документации сохраняются.
