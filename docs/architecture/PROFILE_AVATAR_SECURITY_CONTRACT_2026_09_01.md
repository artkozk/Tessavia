# Контракт хранения и доступа к аватарам BizFlow от 1 сентября 2026 года

## Данные пользователя

Миграция `017_profile_avatars.sql` добавляет в `users` четыре служебных поля:

- `avatar_stored_name` — внутренний относительный путь, не исходное имя пользователя;
- `avatar_content_type` — только проверенный `image/jpeg` или `image/png`;
- `avatar_size_bytes` — фактический размер записанного файла;
- `avatar_updated_at` — версия изображения и источник cache-busting URL.

Исходное имя не сохраняется, потому что для аватара оно не несёт продуктовой ценности и может содержать лишние персональные сведения. Сам бинарный файл не хранится в SQLite: это не раздувает резервную копию основной базы и соответствует существующему файловому хранилищу вложений.

## HTTP-контракт

- `POST /api/me/avatar` — только текущий пользователь; multipart-поле `file`; успешный ответ возвращает обновлённый публичный `User`.
- `DELETE /api/me/avatar` — идемпотентное удаление собственного фото; повторный вызов также возвращает 204.
- `GET /api/users/{id}/avatar` — выдача только после проверки общей активной membership.

URL публикуется в `User.avatarUrl` только при непустом `avatar_stored_name`. В URL входит `avatar_updated_at`, поэтому после замены ссылка меняется. Файл отдаётся как `inline`, с проверенным MIME, точным `Content-Length`, приватным кэшем и ETag.

## Проверка доступа

Функция `canViewUserProfile` разрешает доступ, если:

1. запрошен собственный профиль; или
2. существует workspace, в котором viewer и target имеют `status = active`.

Эта же проверка применяется к публичному профилю и бинарному аватару. Каталог пользователей использует эквивалентный SQL-фильтр. Проверка не опирается на знание логина, наличие чата или авторство карточки.

## Валидация файла

Запрос ограничивается через `http.MaxBytesReader`. После чтения применяется дополнительный `io.LimitReader`, чтобы ограничение сохранялось независимо от поведения multipart-парсера. Формат определяется через `http.DetectContentType`, затем JPEG или PNG декодируется до конфигурации размеров.

Файл не принимается, если:

- размер равен нулю или превышает 5 МБ;
- содержимое не является JPEG/PNG;
- декодер не может прочитать заголовок;
- любая сторона меньше 64 или больше 6000 пикселей.

## Атомарность замены

1. Создаётся каталог `<uploadPath>/avatars` с правами `0750`.
2. Новый файл записывается с правами `0640` под именем `<userID>-<randomID>.<ext>` сначала во временный путь.
3. Временный файл переименовывается в финальный внутри одного каталога.
4. Начинается SQL-транзакция, обновляется профиль и добавляется событие `avatar_updated`.
5. После успешного commit удаляется прежний файл.

При ошибке до commit новый файл удаляется. Старый файл и старые поля профиля не затрагиваются. При удалении фото порядок обратный: сначала транзакционно очищаются поля и пишется `avatar_removed`, затем удаляется бинарный файл.

## Аудит и резервное копирование

Аудит хранит только формат и размер новой версии. Бинарное содержимое и исходное имя в историю не попадают. Production backup перед миграцией должен включать SQLite и каталог uploads; rollback версии приложения без отката миграции допустим, потому что добавленные поля имеют безопасные значения по умолчанию и старый код их игнорирует.

## Граница следующего этапа

Текущий контракт умеет определить общую membership, но проектные карточки пока принадлежат одному историческому командному контуру. Перед выпуском нескольких CRM-команд все проектные сущности, файлы, чат, поиск, граф, activity и AI-контекст должны получить явный `workspace_id` и проверку membership. Переключатель команд до этого изменения запрещён как вводящий пользователя в заблуждение и создающий риск смешения данных.
