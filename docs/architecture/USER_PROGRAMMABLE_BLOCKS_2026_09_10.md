## 1. Почему пользователь упирается в готовые блоки

Окно со скриншота действительно ограничено каталогом разработчика. В `web/app.js` функция `workspaceWidgetCatalog()` перечисляет мини-календарь, расписание и несколько личных или командных виджетов. `openWidgetLibrary()` показывает только этот массив. Собственного определения блока, редактора его внутреннего дерева или установки пользовательского компонента в этом пути нет. Ограничение не связано с тем, что человек не нашёл нужную кнопку.

Параллельно существует другой конструктор: `web/page-apps.js`. Он умеет создавать свои страницы из девяти типов: группа, заголовок, текст, пункты и отметки, прогресс, кнопка перехода, список записей, форма записи, данные и действия. Серверный `validatePageApp()` в `internal/app/page_apps.go` явно разрешает те же девять типов. Даже здесь человек собирает композицию предусмотренных примитивов, но не регистрирует свой переиспользуемый тип блока.

| Область | Что реализовано | Где остаётся разрыв |
| --- | --- | --- |
| Встроенная страница | `pageLayoutCatalog()` сопоставляет части готового DOM с ключами. `PageLayout` хранит порядок, скрытие и оформление в пользовательском профиле | Программируемое дерево страницы отсутствует; добавление ограничено `workspaceWidgetCatalog()`. Перерисовка встроенной страницы и повторное применение настроек — отдельные стадии |
| Своя страница | `PageAppDefinition`, стабильные ID, дерево через `ParentID`, общий просмотр и редактор | `PageAppBlock` — растущий набор специальных свойств; нет типа «экземпляр компонента» и параметров экземпляра |
| Группы | `blockSubtree()`, копирование дерева, перенос внутренних ссылок, скрытие, восстановление | Копия группы не является библиотечным компонентом. Изменение общей заготовки, параметры и версия не определены |
| Повторяемая карточка | SC-93: до 48 частей, поля/заголовок/подпись/текст, ширина, стили | Внутри нельзя произвольно разместить другие блоки, вложенный повторитель или свою кнопку. Это специализированная структура тела записи |
| Данные | Пользовательские доски, схемы, формы; `PageDataConfig` для привычек, планов, работы, чтения | Динамические источники и отображаемые свойства имеют закрытые списки. Нет общего контекста текущего элемента повторителя, параметров и локального состояния |
| Привязки | `PageTextBinding` связывает `title`/`subtitle` карточки с полем; SC-92 добавляет числовые операции | Другие свойства, текст произвольного узла, выбранный пользователь и состояние формы не входят в общий механизм |
| Условия | Прогресс другого трекера управляет видимостью блока; условия кнопки проверяют поля | Две отдельные модели условий. Нет общей типизированной модели для видимости, доступности, цвета, формулы и действия |
| Действия | До восьми изменений одной записи, предпросмотр и транзакция | Изменения читают исходный снимок. `PageRecordAction` применим только к списку записей; результат шага нельзя выбрать источником следующего |
| Наборы | `page_app_templates` хранит переносимую страницу; установка создаёт независимые схемы, без записей и личных отметок автора | Нет библиотечной единицы «компонент», параметров, закреплённых версий и управляемого обновления экземпляров. `interface_presets` представляет другой тип набора |

## 2. Продуктовый принцип

Собственный блок — это состав, данные и поведение, которые пользователь может назвать, сохранить и повторно использовать. «Учебное занятие», «Карточка клиента» или «Контроль оплаты» должны быть пользовательскими компонентами из общих возможностей. Добавление каждого предметного сценария в код платформы не должно оставаться обязательным условием.

Расширяемость означает возможность создавать новые сочетания данных, представлений и действий. Она не означает обещание бесконечной нагрузки или поддержки любого внешнего оборудования. Для конкретного сценария должно быть видно, какая часть уже собирается, а какой общей операции ещё не хватает. Новый общий примитив расширяет множество сценариев сразу.

Продуктовая рекомендация [TESSAVIE_POSITIONING_AND_FIRST_USERS_2026_09_09.md](../product/TESSAVIE_POSITIONING_AND_FIRST_USERS_2026_09_09.md) выделяет продолжающееся личное дело с материалами как гипотезу первого использования. Это полезный критерий приёмки конструктора, но не основание снова ограничить каталог фиксированным личным виджетом. Проверять вторым примером командный реестр с другой схемой. Пользователь сам собирает свой набор; тестовый утренний экран в его аккаунте не создавать.

## 3. Предлагаемая общая модель

Развивать один декларативный документ и один механизм исполнения. Документ описывает дерево элементов, свойства, источники, состояние и события; редактор меняет этот документ. Предпросмотр и рабочая страница исполняют одинаковое описание. Для встроенных страниц вводить адаптеры существующих функций, а не создавать третий несовместимый конструктор.

```text
Набор страницы
  ├─ Дерево страницы
  │    ├─ Встроенный элемент через адаптер
  │    └─ Экземпляр пользовательского компонента
  │          ├─ Параметры и собственные изменения экземпляра
  │          └─ Дерево элементов выбранной версии компонента
  ├─ Схемы данных и разрешённые источники
  └─ Зависимости компонентов по закреплённым версиям

Текущая сессия → данные и личное состояние → вычисление свойств → отображение
Событие пользователя → план действий → результат → новое отображение
```

### 3.1. Элемент и компонент

У узла должны быть стабильный `id`, `type`, типизированные `props`, дочерние узлы или именованные места вставки `slots`, привязки и обработчики событий. Начальные общие элементы: контейнер/сетка, текст, кнопка, изображение или материал, ввод, выбор, флажок, показатель прогресса, повторитель. Существующие девять блоков остаются совместимыми: сначала адаптируются как составные элементы, затем их внутренности открываются общему редактору.

Определение компонента содержит ID, версию, имя, описание, дерево и открытые параметры. Параметр имеет имя, тип, значение по умолчанию и понятную подпись. Например, автор «Показателя с действием» открывает параметры «Заголовок», «Источник», «Поле результата», «Цвет» и «Действие кнопки». Получатель меняет эти пять значений без необходимости разбирать весь внутренний состав.

Экземпляр содержит ссылку на конкретную версию определения и собственные значения параметров. Изменение одного экземпляра не меняет соседний. «Изменить общий компонент» должно быть отдельным явно названным действием. Обновление общей версии не переписывает установленные экземпляры молча; сначала показываются изменения и конфликты локальных настроек. Преобразование экземпляра в независимую группу сохраняет текущее дерево и обрывает связь с обновлениями.

Первый механизм библиотеки может вставлять независимую копию композиции, используя текущий перенос ID. Однако интерфейс и документ должны называть её копией: наличие библиотеки копий ещё не означает связанные экземпляры или обновляемые компоненты.

### 3.2. Любое применимое свойство: значение либо выражение

Описание типа элемента должно определять доступные свойства и их типы. Тогда панель свойств строится по схеме, а не по очередной ветке `if` для каждого виджета. Для текста, цвета, размера, видимости, доступности, выбранного значения и фильтра предусмотрены два режима: постоянное значение и «Из данных».

Контексты выражения: параметры компонента, текущая запись, родительская запись повторителя, текущее значение формы, состояние экземпляра, текущий пользователь, выбранная дата и часовой пояс. Ссылки используют стабильные идентификаторы. Переименование пользовательского поля не должно ломать выражение; удаление источника показывает конкретное место несовместимости и оставляет последнюю сохранённую конфигурацию доступной для исправления.

Единое дерево выражений должно поддержать литералы, ссылки, арифметику, сравнения, `all`/`any`, условный выбор, объединение текста, даты, длину и агрегаты коллекции. Пользователь начинает с визуального выбора «Поле → сравнение → значение». Расширенный текстовый редактор формулы, если добавляется, компилирует тот же формат и даёт те же результаты. Отдельный язык для цвета, другой для фильтра и третий для кнопки повторит нынешнюю проблему несовместимых механизмов.

`null`, ноль, `false`, пустая строка, загрузка и ошибка имеют разный смысл. Например, `0` на шкале должен отображаться нулём, а отсутствие числового источника — объяснимой заменой. Сервер и браузер проверяются на общем наборе примеров выражений; изменение записи всегда повторно вычисляется сервером по актуальным данным.

### 3.3. Источник, повторитель и состояние

Источник объявляет тип результата, параметры выборки, доступные поля и действия. Нужны адаптеры пользовательских коллекций, личных материалов/планов/привычек, проектных записей и документов/разделов. Отображение списка, сетки, календаря или дерева следует отделять от источника. Выбор «Личное / Проект» и «Месяц / Расписание» меняет данные или представление, сохраняя стабильную идентичность настроенного контейнера.

Повторитель принимает коллекцию и рисует пользовательское дерево для каждой записи. Вложенный повторитель получает явно выбранную связь с родительской записью. ID экземпляра строки строится по ключу записи, а не по её индексу: фильтрация и сортировка не должны переносить отметку или раскрытое состояние на другую строку. Запросы используют постраничную загрузку; пределы и ошибки показываются там, где они возникли.

Состояние необходимо разделить по назначению:

| Состояние | Пример | Срок и область |
| --- | --- | --- |
| Настройки компонента | Цвет и выбранные поля | Версия документа страницы/экземпляра |
| Временное состояние | Раскрытая глава, текст поиска, выбранная строка | Экземпляр и текущая сессия; не меняет шаблон |
| Личное сохранённое состояние | Место чтения, отметка раздела | Пользователь + экземпляр + устойчивый ключ записи |
| Общие данные | Статус заявки, ответственный | Существующая сущность и её права/история |

Личная отметка одного читателя не должна превращаться в общую отметку всей команды. Набор переносит схему состояния и значения по умолчанию, но не результаты автора. Постоянное удаление визуального узла отличается от удаления данных: редактор показывает ссылки на узел и последствия, позволяет отменить изменение до сохранения. Скрытие остаётся удобной обратимой командой, но не единственным способом убрать элемент из своей композиции.

### 3.4. События и цепочки действий

Каждый интерактивный элемент объявляет события: нажатие, изменение значения, отправка формы, успешное выполнение. Обработчик — последовательность шагов со стабильными ID. Шаг получает данные из текущего контекста или явно из результата предыдущего шага. Пример: «Создать запись → взять ID созданной записи → добавить связь → открыть созданную запись». Это невозможно выразить текущим набором независимых изменений одного исходного снимка.

Начальный набор общих команд: установить состояние, открыть материал/запись, перейти к элементу или странице, создать/изменить запись, создать связь, записать личную отметку. Условия и вычисления используют общий формат выражений. Редактор показывает имя источника результата, ожидаемый тип и последовательность. Ссылка на будущий или удалённый шаг диагностируется до сохранения.

Для операций одной базы применяется общий план и транзакция; ошибка позднего шага не оставляет половину изменений. Preview показывает вычисленные изменения, включая зависимости. Повторная отправка использует ключ операции, сохранённый результат не исполняется второй раз. Последующая интеграция внешних действий потребует очереди и отдельного статуса каждого шага; не выдавать такие действия за одну транзакцию базы. Существующие set/add/copy продолжают исполняться в прежней семантике до явного перевода пользователем на цепочку.

### 3.5. Наборы и совместимость

Сохранять назначение набора: настроенная страница, которой можно пользоваться после установки. Расширить существующую упаковку страницы манифестом компонентов и схем, а не делать новую изолированную систему обмена. В одном каталоге можно различать «Страницы», «Блоки» и «Оформление», сохраняя честное объяснение каждого типа.

Манифест закрепляет версии зависимостей и отличает ссылку на существующий источник от создаваемой схемы. Установка сначала проверяет все ссылки, затем транзакционно создаёт независимую композицию и необходимые схемы. Переносятся ссылки во всех скрытых элементах, выражениях и действиях, как уже требуется для SC-93. Внутренние ссылки сохраняются; внешняя ссылка на источник вне компонента становится объявленным параметром либо явным требованием установки. Нельзя оставить в библиотеке незаметную ссылку на рабочую доску автора.

Авторское учебное содержание, например собственные главы, должно добавляться в набор отдельным явно выбранным ресурсом. Это отличается от личных заметок, читательского прогресса и записей клиентов; они по умолчанию не являются содержимым набора. Действующий SC-82 умеет читать определённое издание Библии через специальный источник и командную модель. Универсальная читалка требует собственного источника документов/разделов, общего отображения материала и личного состояния, а затем маршрутов и групповых правил.

Версию документа повышать вместе с явной миграцией и проверкой старых клиентов. Новые поля и узлы не должны молча исчезать при сохранении старым редактором. Несовместимую версию открывать для чтения с объяснением, сохраняя оригинал. Существующие `expectedRevision`, контроль схем и защита отката остаются основой.

## 4. Как это должно выглядеть для человека

Везде одно понятное действие «Добавить блок». В окне: поиск, готовые элементы, «Мои блоки» и заметная команда «Создать свой блок». Начать можно пустым или из выделенной группы. Системный календарь и пользовательская страница не должны отправлять человека в разные каталоги без объяснения.

Обычный режим показывает холст и несколько параметров выбранного элемента. Дополнительно раскрываются «Данные», «Поведение», «Состав». Привязка отмечается рядом с конкретным свойством; нажатие открывает источник и пример результата. Полное дерево и текстовое представление формулы доступны по запросу. Большой граф событий не должен быть обязательным первым экраном для изменения цвета кнопки.

Автор компонента выбирает, какие параметры будут видны человеку, вставившему блок. Получателю доступно «Настроить» для параметров и «Изменить состав» для углубления. Предпросмотр показывает актуальные данные синтетической записи/собственного выбранного контекста и объясняет, почему скрыта кнопка или не вычислилось значение. Ошибка в одном блоке оставляет остальную страницу рабочей.

## 5. Очерёдность и критерии готовности

Это предложенные этапы, не новые карточки на сервере. Родительские направления из подтверждённых исторических контрактов: `b8a99823ccf3f3a9f39093fe3c1af2bf` (элементы), `26c54f79aa1c9110536670ae8371a868` (композиция/данные), `2ad192a4298615883945e23a87d8ecd2` (привязки), `f4dd60e96ccb69635a2faa05a60fd058` (цепочки). Перед созданием дочерних задач перечитать живые карточки; их текущий статус не устанавливался этим локальным аудитом.

**Минимальный осмысленный следующий срез после аварийного исправления — библиотека собственного составного блока, доступная из текущего окна «Добавить блок».** Только ссылка на уже существующий конструктор страницы не выполняет этот результат. Только новые названия готовых виджетов также не выполняют его. За первым срезом должны следовать параметры и общий контекст; иначе получится обмен статическими группами с прежним потолком поведения.

В приёмке каждого среза использовать личный сценарий продолжающегося дела и независимый бизнес-реестр, а не копию одного примера с другой подписью. Проверять заполненные записи, длинные тексты, два экземпляра, две роли/учётные записи, отмену, черновик, сохранение/reload, переходы, меню, 320 px и отдельную мобильную раскладку. Физические устройства отмечать проверенными только после работы на них. Готовность конструктора определяется самостоятельной сборкой сценария через доступный пользователю интерфейс, а не числом новых свойств или тестов.

## 6. Следующий технический шаг без переписывания всей платформы

1. Зафиксировать воспроизводимый тест сброса оформления встроенного календаря и восстановить жизненный цикл его профиля. Общая архитектура не заменяет исправление текущего дефекта.
2. Выделить интерфейс реестра типов: схема свойств, редактор, renderer, допустимые события, сериализация и версия. Подключить существующие блоки адаптерами; валидаторы backend остаются источником допустимого формата.
3. Ввести библиотечную запись композиции и общий сценарий вставки. Переиспользовать `blockSubtree` и перенос схем/ссылок из установки наборов. Определить внешние зависимости группы до публикации.
4. Встроить host составного блока в пользовательскую раскладку системной страницы. У host должен быть устойчивый instance ID; его данные, черновик и представление не зависят от поиска DOM по заголовку. Перерисовка страницы повторно монтирует тот же сохранённый экземпляр.
5. Добавить параметры и общий формат привязок, затем переносить прежние `RecordBindings`, `Visibility` и условия действий через совместимые адаптеры. Только после этого расширять внутреннее дерево повторителя и формы.

Этот порядок использует уже выпущенные группы, схемы, права, предпросмотр и наборы. Он устраняет конкретный разрыв, показанный пользователем, и создаёт основу для поведения, которое автор страницы сможет задавать сам.
