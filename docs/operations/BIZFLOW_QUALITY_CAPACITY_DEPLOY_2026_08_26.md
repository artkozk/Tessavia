# Развёртывание качества базы, ёмкости и синхронизации

Дата: 26 августа 2026 года.

## 1. Единственный допустимый production-контур

Приложение, SQLite, вложения и резервные копии остаются только на `159.194.231.150`. Развёртывание на других серверах запрещено требованием конфиденциальности. Доступ пользователей выполняется через `https://control.e-rd.ru`.

## 2. Предварительные проверки

Перед переключением выполняются:

1. `node --check web/app.js`;
2. `gofmt` изменённых Go-файлов;
3. `go test ./...`;
4. `go vet ./...`;
5. `git diff --check`;
6. браузерная проверка desktop и viewport 390 × 844;
7. проверка отсутствия ошибок и предупреждений в консоли браузера.

## 3. Порядок переключения

1. Снять резервную копию текущей SQLite и каталога вложений на том же production-хосте.
2. Проверить SQLite через `PRAGMA integrity_check` на копии.
3. Собрать Linux amd64 binary из зафиксированного commit.
4. Создать новый каталог `/opt/business-control/releases/<release-id>` без изменения активного каталога.
5. Передать binary и закрытый набор клиентских ресурсов на основной сервер.
6. Выполнить миграции при первом запуске новой версии.
7. Переключить символьную ссылку `current` атомарно и перезапустить сервис.
8. Проверить health, домен, версию клиентских ресурсов и новые авторизованные API.

## 4. Обязательный production smoke

- `GET /healthz` возвращает успешный статус;
- `GET /api/team/capacity` возвращает обоих основателей и не изменяет данные;
- изменение собственной ёмкости разрешено, чужой — запрещено;
- `GET /api/quality` возвращает счётчики и открываемые идентификаторы карточек;
- `GET /api/sync` принимает валидные курсоры и отклоняет повреждённый;
- главная страница содержит asset marker `20260826-quality-capacity-sync-1`;
- существующие исследования, решения, чат и карта остаются доступны;
- `PRAGMA integrity_check` после миграции возвращает `ok`.

## 5. Откат

При ошибке health, миграции или smoke символьная ссылка возвращается на предыдущий release, сервис перезапускается, затем повторяется health. Миграция 014 только добавляет таблицу и индексы; старый binary игнорирует их. Поэтому откат binary не требует удаления новой таблицы и не уничтожает введённую ёмкость.

## 6. Фактический результат

Этот раздел заполняется после production-переключения. Исходный план выше не удаляется и остаётся частью аудита развёртывания.
