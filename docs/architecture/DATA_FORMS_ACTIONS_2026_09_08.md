## Обнаруженная предпосылка безопасных форм — SC-75

PUT /api/records/{id}/custom-fields сохранял значения без expectedUpdatedAt, хотя обычная карточка и схема имеют защиту версий. В изолированной fixture воспроизведено: два редактора прочитали одну версию, первый сохранил3, второй устаревший7; обе операции200, первое значение потерялось. Временный аудит-тест завершился0.752s и удалён: он фиксировал дефект, а не корректный желаемый результат. Регрессионный тест должен ожидать409 и сохранность первой правки.

Общий bindWorkingDraft восстанавливает значения. Без хранения исходной версии старый черновик при повторном открытии мог бы получить актуальную версию и обойти защиту. Поэтому исправление включает форму, черновик и сравнение, а не только WHERE в SQL. Зарегистрирован дочерний P0 e45e995dbc1b20bb00c578ae89ae2558, «P0 · Защитить поля от перезаписи устаревшей формой».

## Контракт SC-75

API требует expectedUpdatedAt. Отсутствующая или устаревшая версия возвращает409 без изменения данных. Финальный UPDATE records использует id и старую updated_at в одной транзакции с полями и историей; при гонке нулевое число строк приводит к rollback. Валидация типов/обязательности и права проекта сохраняются.

Форма хранит скрытые expectedUpdatedAt и исходные значения вместе с черновиком. Восстановленный старый черновик без метаданных не получает актуальную версию автоматически. При409 загрузка свежей карточки даёт сравнение: нетронутые пользователем поля берутся из свежей версии, независимые его изменения переносятся, спорные по умолчанию остаются серверными. «Использовать моё значение» — явный выбор для каждого спорного поля. «Перенести выбранное в форму» не сохраняет на сервер: пользователь проверяет форму и нажимает обычное сохранение. Повторная гонка снова409. Если пользователь изменил ввод после появления сравнения, сравнение пересчитывается, не затирая новый ввод молча.

Для эквивалентности учитываются пустые значения, false, порядок multi_select и равные моменты datetime с разными часовыми поясами. Форматирование сравнения использует существующее представление поля и экранирование. Старые внешние клиенты без версии получают409; UI обновляется согласованной версией ресурсов. Схема БД не меняется.

## После SC-75: конкретная последовательность

1. Связанный блок списка с явным collectionId и разрешёнными полями. Серверная проверка принадлежности коллекции и полей пространству; скрытие поля не меняет права. Переход открывает существующую запись с историей.
2. Блок формы создания/редактирования: порядок/подписи/видимость полей, настройки обязательности и значений по умолчанию из схемы. Скрытое обязательное поле без источника значения — ошибка настройки до публикации. Название может вводиться или вычисляться по явно выбранному полю; нельзя незаметно создавать сотни безымянных записей.
3. Декларативное действие изменения записи: выбранное поле/значение, разрешённый контекст записи, предпросмотр последствий и серверная проверка версии. Изменение статуса задачи проходит существующий жизненный цикл, чтобы не вернуть регресс SC-72.
4. Перенос зависимостей набора: снимок схемы/вариантов/действий, стабильные внутренние ключи и таблица соответствия новым IDs при установке. Не копировать клиентские записи, участников и приватные ссылки. Установка всей структуры атомарна; недоступные внешние ссылки требуют явной настройки.
5. Приёмка: человек с пустого проекта создаёт учебный журнал и реестр обращений через UI, сохраняет набор, второй проект устанавливает и использует независимую копию. Готовая читалка с группами/дневником/рейтингом и настройка всех встроенных элементов остаются отдельной частью общего требования.

Этот документ не объявляет пункты1–5 реализованными. Большая задача данных/форм остаётся открытой; SC-75 только устраняет подтверждённую потерю изменений в используемой основе.
