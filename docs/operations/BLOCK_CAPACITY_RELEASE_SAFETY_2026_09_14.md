## Порядок публикации

1. Проверить точные Git blobs будущего коммита, собрать Windows и Linux из них,
   выполнить Node, Go, vet и проверки в интерфейсе с синтетическими данными.
2. Зафиксировать и отправить изменения, сравнить каждый сборочный файл с Git.
3. На действующем сервере сохранить БД, uploads и конфигурацию. Запустить кандидат
   на копии с отключённым worker; сравнить все значения всех 127 таблиц, объекты
   схемы 070 и квитанции миграций. Никаких переносов пользовательской БД на ПК.
4. Проверить предыдущий бинарник на той же копии. Остановить службу, сделать
   дополнительный backup на момент переключения, заменить ссылку release и
   запустить службу. Проверить nginx, локальный и публичный health, ресурсы,
   отсутствие доступа без авторизации, integrity и внешние ключи.
5. Добавить проверяемый результат в дочернюю задачу через API; родителю добавить
   только доказательство, сохранив статус направления.

## Почему одной схемы 070 недостаточно для отката

Старый бинарник не знает резервирования идентификаторов блоков в корзине.
Поэтому после первого невосстановленного удаления нельзя считать его полностью
совместимым лишь из-за одинаковых таблиц. Проверка `--rollback-safe` дополнительно
требует отсутствия таких записей. Если они уже есть, процедура сохраняет кандидат
и последнюю БД для совместимого исправления. Старый backup поверх новых данных
не восстанавливается. Обычная проверка после публикации разрешает корзину: работа
пользователя во время проверки не должна ошибочно запускать откат.

Исторические инструкции прежнего выпуска не изменены; этот раздел уточняет
новое ограничение, появившееся с восстанавливаемым удалением блоков.
