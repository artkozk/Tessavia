# Проверки выпуска финансового конструктора — 15.09.2026

## Основание и статус подготовки

Этот документ дополняет предыдущий выпуск командных финансов и медиа. Его
история остаётся в `TEAM_FINANCE_MEDIA_RELEASE_2026_09_15.md`; прежние валидаторы
и генераторы не заменяются. Новая схема добавляет необязательные группы и связи
операций, а финансовый блок конструктора показывает уже существующий учёт.

Подготовка генератора сама по себе не является размещением. Этот документ
фиксирует локально проверенные ограничения. Фактические release, SHA бинарника,
резервная копия и результаты публичной проверки регистрируются руководящим
агентом после штатного выпуска. Производственная база и копии на компьютер
для этих тестов не скачивались; использованы синтетические SQLite-данные.

Предыдущая рабочая версия:

- SHA-256 бинарника:
  `47d9015b40a1ed95615ace3c7e4bcd88a797d85d2623503770e92bd653774317`.
- Последняя миграция `074_page_media.sql`, 139 обычных таблиц.
- Кэш `20260915-team-finance-media-1`.

Новый генератор `deploy/build-finance-constructor-deploy-20260915.py` разрешает
release с префиксом `20260915-finance-constructor-`, кэш
`20260915-finance-constructor-1` и резервную копию с префиксом
`pre-finance-constructor-`. Сценарий и manifest создаются в локальном каталоге
`.artifacts/finance-constructor-20260915`; генератор не подключается к серверу
и не запускает деплой.

Разрешена только миграция `075_finance_organization.sql`: четыре пустые таблицы
`personal_finance_categories`, `personal_finance_organization`,
`workspace_finance_categories`, `workspace_finance_organization`.
После перехода — 143 таблицы. `ALTER`, начальные пользовательские категории,
перенос денег или заполнение прежних операций не допускаются.

Проверенные хеши получены из репозиторных миграций, не из рабочей базы:

| Объект | SHA-256 |
|---|---|
| Схема 074 | `4e59edce63b4362cbd6fc1b7c6d41a94bfca7cf3197c03b0d454e2d6ee4ee1d3` |
| SQL 075, UTF-8 с переводами строк LF | `23996e34871bfd5e38760287a601ca0648173b470e536b44a7699695a6225dee` |
| Новые объекты схемы 075 | `264f8da57a4363797b60b153672c379863b3d447701d09469c965876f55d0c25` |

Нормализация LF нужна, чтобы Windows CRLF не менял результат проверки
идентичного SQL. Генератор останавливается, если содержимое миграции отличается
от проверенного хеша. Новые индексы и триггеры входят в хеш схемы: удалённая
проверка принадлежности операции не считается совместимой миграцией.

## Сохранность данных

`deploy/verify-finance-constructor-database.py` открывает SQLite только для
чтения. Проверяются точный набор миграций, схема старых и новых объектов,
`integrity_check`, внешние ключи, количество таблиц и архивы конструктора.

При сравнении 074 → 075 все значения прежних 139 таблиц должны совпасть,
включая суммы доходов/расходов, владельцев, назначения, историю, grant-данные,
файлы, migration receipts и внутреннюю `sqlite_sequence`. У новой миграции
должна быть собственная непустая отметка применения. Все четыре новые таблицы
обязаны быть пустыми непосредственно после миграции.

При сравнении 075 → 075 должны совпасть все 143 таблицы и все receipts.
Так проверяется запуск прежнего бинарника на копии уже обновлённой базы:
группы, связи и новые архивы нельзя потерять или очистить при откате.

## Архив финансового блока

Новый тип `finance` добавляется к уже разрешённому `media` узко, с сохранением
проверок идентичности, дерева, позиций, receipt, восстановления и резервирования
ID удалённых блоков. Неизвестные типы и произвольные поля не разрешаются.

В необязательном объекте `finance` допустимы только:

- `showTotal`, `showAccounts`, `showRecent`, `showActions`: boolean;
- `recentLimit`: целое 0–10, включая совместимое значение 0 по умолчанию;
- `display`: пустая строка, `cards` либо `compact`;
- `totalLabel`, `accountsLabel`, `recentLabel`, `openLabel`, `incomeLabel`,
  `expenseLabel`: строки не длиннее 80 Unicode-символов, без краевых пробелов.

Отсутствующий объект и пустой `{}` допустимы. Канонический snapshot не содержит
`finance: null`. Денежные суммы, ID счетов, команда-источник и произвольные
дополнительные поля отвергаются. При смене типа блока его неактивная финансовая
конфигурация может оставаться, как конфигурация таблицы; валидатор проверяет её
на любом известном типе, не уничтожая настройки пользователя.

## Порядок выпуска и возврата

Генератор сохраняет предшествующий штатный порядок: сверка пути и SHA предыдущего
бинарника, резервная копия, изолированный пробный запуск кандидата без фоновой
доставки, сравнение данных, HTTP-проверки, пробный запуск предыдущего бинарника
на копии схемы 075, повторное сравнение данных, отдельная копия непосредственно
перед переключением, запуск службы и публичная проверка.

К прежним HTTP-проверкам добавлены финансовый блок, его CSS, регистрация в
конструкторе и service worker, функции групп/связей, событие обновления финансов
и защита контекста формы. Анонимные обращения к поиску связей и созданию групп
личного/командного учёта должны возвращать 401. Все прежние проверки финансов,
медиа, умных списков, чата, виджетов, push и конструктора остаются.

Возврат предыдущего бинарника сохраняет актуальную базу 075 и uploads.
Старая база из резервной копии автоматически не восстанавливается. Предыдущая
версия продолжает прежний личный/командный учёт и медиа, но не предоставляет
новый финансовый блок, группы и связи. Это ограничение явно выводится при
проверке отката. Если актуальная база не проходит проверку, возврат блокируется
с сохранением данных и необходимостью совместимого исправления.

На сервер необходимо загрузить всю цепочку read-only валидаторов в `/tmp`:

1. `verify-finance-constructor-database.py`.
2. `verify-team-finance-media-database.py`.
3. `verify-android-widget-database.py`.
4. `verify-mobile-gestures-today-database.py`.

Manifest перечисляет каждый локальный/серверный путь и хеш файла. Генераторы
предыдущих этапов нужны локально при подготовке, сервер их не импортирует.
