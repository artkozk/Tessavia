# Развёртывание 12-недельного календаря

Дата документа: 31 августа 2026 года.

## Область

Релиз добавляет общие циклы планирования, годовой календарь по кварталам, 12-недельную сетку, недельный показатель исполнения, перенос сроков и усиленную защиту рабочих окон.

Production BizFlow разворачивается только на разрешённом основном хосте `159.194.231.150` и доступен по `https://control.e-rd.ru`. Использование других серверов запрещено требованием конфиденциальности.

## Резервирование

Перед переключением релиза создаются:

- копия SQLite через безопасный backup-механизм;
- копия каталога вложений либо подтверждение его неизменности;
- манифест релиза и контрольные суммы;
- ссылка на предыдущий release-каталог для атомарного rollback.

Backup остаётся на основном сервере. Он не передаётся на сторонний хост.

## Миграция

При старте новый бинарный файл применяет `015_planning_cycles.sql`. Миграция только добавляет таблицу и индексы; существующие записи, сроки и связи не переписываются.

Перед production-переключением миграция выполняется на копии БД. После неё проверяются:

- `PRAGMA integrity_check`;
- `PRAGMA foreign_key_check`;
- существование `planning_cycles`;
- существование частичного уникального индекса;
- сохранность числа пользователей и записей.

## Атомарное переключение

1. Собирается Linux AMD64 binary.
2. Создаётся новый release-каталог.
3. Binary и необходимые файлы загружаются в него.
4. Временный сервис проходит health-check на копии БД.
5. Symlink `current` переключается на новый release.
6. Основной сервис перезапускается.
7. Проверяются локальный и публичный health endpoint.

## Production smoke

Обязательные проверки после переключения:

- `GET /api/health` локально и через домен возвращает успешный ответ;
- HTML содержит версию ресурсов календарного релиза;
- неавторизованный `GET /api/planning/cycles` получает 401;
- авторизованный основатель может открыть календарь;
- пустой проект показывает настройку цикла, а существующие сроки не теряются;
- SQLite проходит integrity и foreign-key проверки;
- журнал сервиса не содержит panic, migration error или циклических перезапусков.

## Rollback

Если smoke-проверка не проходит:

1. symlink возвращается на предыдущий release;
2. сервис перезапускается;
3. проверяется public health;
4. БД сохраняется, потому что добавленная таблица обратно совместима с предыдущим binary;
5. восстановление backup выполняется только при доказанном повреждении данных.

Удалять `planning_cycles` при обычном rollback нельзя: это уничтожит уже созданную пользователями историю циклов.

Первый автоматический smoke после переключения завершился кодом ошибки `curl` из-за конструкции `curl | grep -q`: `grep` закончил чтение сразу после совпадения, а `curl` сообщил о закрытом принимающем потоке. Это была ошибка проверочного конвейера, не приложения. Повторная проверка сначала сохраняла HTML в файл и прошла полностью.
