# Простой учёт командного бюджета — 15.09.2026

## Зачем нужен этот этап

Пользователь хочет учитывать, сколько участники вложили в общий проект,
сколько денег поступило от работы и на что они потрачены. Для начала такого
учёта не должны требоваться счета накоплений, проценты и схемы распределения.
Прежний командный API из `WORKSPACE_FINANCE_2026_09_15.md` обеспечивал
независимый регистр, но первая операция требовала предварительно создать
счёт и источник с распределением. Два отдельных запроса настройки также могли
оставить лишние справочники после обрыва или повторного нажатия.

Этот этап добавляет один атомарный сценарий первого поступления и первого
расхода. Он использует прежний финансовый регистр и точный расчёт копеек.
Личные доходы, назначения процентов, исторические командные операции и их
снимки не переписываются. Прежний расширенный учёт остаётся доступным.

Задача платформы: `26e949d20d9e18b96819c000d1f420d1`. Настройка меню имеет
отдельную задачу `4c262b5f62a29ef17162809ec83fc1d7`; backend бюджета сам не
создаёт пунктов навигации и не выбирает за пользователя набор страниц.

## Понятные пользователю сущности

- **Вложение** — внесённые участником деньги. Это не выручка проекта.
- **Доход** — поступление, которое пользователь сам отнёс к результатам работы.
- **Другое поступление** — деньги, для которых не подходит выбранная категория.
- **Расход** — записанная трата с необязательной группой, получателем,
  пояснением и связями с работой.
- **Остаток** — разница записанных поступлений и выбывших денег. Он может быть
  отрицательным и не объявляется прибылью, суммой в банке или прогнозом.

В пустом регистре первая успешно сохранённая операция создаёт один счёт
«Бюджет проекта». Просмотр финансов ничего не создаёт. Если действующий счёт
один, можно не выбирать его вручную. Если счетов несколько, запрос без выбора
отклоняется: деньги нельзя молча направлять в первый попавшийся счёт.
Архивные счета не восстанавливаются автоматически. При отсутствии действующих
счетов создаётся новый, а прежние суммы остаются у прежнего идентификатора.

Вклад либо доход можно связать с задачей или целью команды через существующее
поле `links`. Расход использует тот же механизм. Связи указывают контекст
операции; они не означают распределение её полной суммы между всеми связанными
карточками. Итог по карточкам без отдельной модели долей не рассчитывается,
чтобы одна трата не учитывалась несколько раз.

## API простого поступления

Командная область, права администратора, заголовки `X-Workspace-ID`,
`X-Finance-Source`, `X-Finance-Revision`, запрет записи в подключённый регистр
и повторная проверка доступа остаются прежними.

| Метод | Путь | Результат |
| --- | --- | --- |
| POST | `/api/workspace/finance/receipts` | Создание, 201; точный повтор, 200 |
| GET | `/api/workspace/finance/receipts/{id}` | Актуальное поступление, в том числе вне открытого месяца |
| PUT | `/api/workspace/finance/receipts/{id}` | Изменение с ожидаемой ревизией |
| PATCH | `/api/workspace/finance/entries/{id}/void` | Прежняя отмена и восстановление, вид поступления сохраняется |

Тело создания:

```json
{
  "clientRequestId": "устойчивый-ключ-создания",
  "receiptKind": "contribution",
  "bucketId": "",
  "date": "2026-09-15",
  "grossMinor": 100000,
  "payer": "Участник команды",
  "note": "Вложение в подготовку проекта"
}
```

`receiptKind` допускает `contribution`, `revenue`, `other`. При явном выборе
счёта передаются `bucketId` и `expectedBucketRevision`. Справочный отправитель
использует прежние `payerId` и `expectedPayerRevision`. Группа и связи используют
`categoryId`, `expectedCategoryRevision`, `links` из финансового конструктора.
Для изменения ключ создания не передаётся, а `expectedRevision` обязателен
по прежней проверке ревизии. Сумма положительная, в копейках, в прежних пределах.
Удержаний работникам и пользовательской схемы процентов в этой форме нет.

Ответ — прежняя структура `financeEntry` с дополнительным `receiptKind`.
Распределение содержит один счёт на всю сумму; отметка банковского перечисления
не устанавливается. Процент 100% — внутренний совместимый формат хранения,
а не обязательное действие или настройка для пользователя.

Первый запрос в одной транзакции проверяет права и контекст, ищет квитанцию
повтора, выбирает либо создаёт счёт, создаёт служебный источник, проверяет
сумму, отправителя, группу и связи, сохраняет операцию и квитанцию. Любая ошибка
откатывает также новые справочники. Конкурентные первые запросы используют один
счёт и один подходящий служебный источник. Ключ повторного запроса проверяется
до выбора счёта, поэтому поздний повтор не требует вновь существующего
справочника и не создаёт второй доход.

Квитанция использует прежнюю таблицу запросов командных доходов, но отдельную
версию смыслового хеша `workspace-receipt-v1`. Один ключ с другим содержимым
либо с прежней семантикой `/entries` вызывает 409. Личный регистр и другая
команда имеют независимые области ключей.

`PUT /entries/{id}` не преобразует простое поступление в расчётную схему:
для него возвращается 409 с предложением открыть форму поступления заново.
Обратное неявное преобразование исторического распределения через `/receipts`
тоже запрещено. Это сохраняет прежние удержания, снимки и отметки переводов.
Изменение существующего простого поступления в том же виде и на том же счёте
сохраняет прежний снимок названия и распределения, даже если справочник
впоследствии архивирован. Создание и смена назначения требуют действующего счёта.

## Первый расход

Командный `POST /api/workspace/finance/expenses` теперь допускает пустой
`bucketId`. Правило выбора счёта такое же: ноль — создать, один — использовать,
несколько — попросить явный выбор. Подготовка счёта входит в транзакцию расхода
после проверки квитанции повтора. Неверная сумма, связь или другая ошибка
не оставляют новый счёт. Расход первым действием может дать отрицательный
остаток; сервер не придумывает компенсирующее вложение.

Личные расходы по-прежнему требуют явный личный счёт. Изменение прежнего
расхода, отмена, восстановление и защита ревизии не меняются.

## Сводка и исторические данные

Командный отчёт возвращает `teamSummary`:

| Поле | Содержание |
| --- | --- |
| `contributionMinor` | Записанные вложения |
| `revenueMinor` | Записанные доходы |
| `otherMinor` | Другие поступления |
| `unclassifiedMinor` | Прежние поступления без нового вида |
| `spentMinor` | Расходы |
| `workerMinor` | Удержания работникам из прежнего расширенного учёта |
| `balanceMinor` | Все поступления минус удержания и расходы |

Это **все записанные операции**, независимо от месяца журнала и его лимита
строк. Учитываются также введённые будущие даты; интерфейс должен прямо
подписывать этот смысл, а не называть его банковским остатком на сегодня.
Отменённые строки не входят в суммы. Предыдущие балансы счетов на конец
выбранного периода (`balances`, `balanceThrough`) сохраняют прежнее значение.
Нельзя смешивать два горизонта и выдавать месячные строки за весь бюджет.

Вид исторического поступления не угадывается по названию источника, имени
отправителя, группе либо слову «Вложение». Такие поступления остаются отдельно
показанными прежними поступлениями. Если у них были удержания работникам,
они вычитаются ровно один раз. Отметка перечисления `paidMinor` не является
расходом и второй раз остаток не уменьшает. Все агрегаты проверяются на точный
целочисленный диапазон JavaScript; превышение возвращает 422 вместо округления.

## Служебные источники и совместимость

Для каждого вида и выбранного счёта создаётся либо повторно используется
служебный источник с одним распределением. Принадлежность определяется явной
метаданной, а не именем. Ручной источник «Вложения» с тем же названием остаётся
пользовательским и не скрывается. Служебные источники отчёта имеют
`source.receiptKind`; интерфейс отделяет их от расширенных правил пользователя.
Если прежний интерфейс изменил правило служебного источника, оно больше не
считается подходящим для простого поступления и не получает этот флаг в отчёте;
новая операция получает корректный источник без переписывания старого.

Миграция `077_workspace_cashbook.sql` добавляет только две пустые таблицы:

- `workspace_finance_receipts`: явный вид поступления;
- `workspace_finance_cashbook_sources`: происхождение служебного источника
  и его назначенный счёт.

Количество прикладных таблиц увеличивается с 148 до 150. Составные внешние
ключи ограничивают метаданные тем же регистром. ALTER существующих таблиц,
автоматического backfill и изменения личных строк нет. Код чтения допускает
прежнюю схему в миграционных проверках, где новый сервер намеренно запускается
поверх старой БД; вид прежних записей при этом не придумывается.

Откат на runtime до этого этапа допустим только до появления строк в обеих
новых таблицах. После первого простого поступления прежний runtime не понимает
его вид и способен изменить его как обычное распределение. Поэтому защитный
порядок выпуска должен остановить такой откат, сохранив текущие данные.

## Проверка и границы результата

Проверки выполняются на синтетических аккаунтах и данных. Для backend нужны:
пустое чтение, первая операция и отказ без частичных справочников, точный повтор,
изменённый повтор, конкуренция первых операций, первый расход, несколько счетов,
приватность личного и другой команды, недоступный источник, устаревшая форма,
группы и связи задач/целей, исправление и отмена, сохранение исторического
снимка архивного справочника, точные полные суммы за пределами месяца.

Миграционная проверка должна сравнить значения и описание схемы всех 148
прежних таблиц, проверить две пустые новые таблицы и повтор старого ключа дохода.
Браузерная приёмка мобильной формы, навигация и фактический деплой фиксируются
отдельно в `docs/operations/TEAM_ACCOUNTING_RELEASE_2026_09_15.md`.

Этот этап не добавляет налоговую бухгалтерию, банковскую интеграцию, прибыль,
займы с графиком погашения, полноценный аудит авторов каждого исправления либо
распределение суммы траты между несколькими задачами. Он делает простой
командный учёт доступным без предварительного конструирования процентов.

`go test ./internal/app -run '^Test(WorkspaceCashbook|WorkspaceFinance|PersonalFinance|FinanceOrganization|PageFinance)' -count=1`
прошёл: **44 теста**, 30,063 секунды. В том числе восемь новых проверок

полные суммы с прежними удержаниями, исправление/отмена, доступ и связи,
конкурентный первый ввод, сохранение снимков архивного справочника, предел
точного агрегата за пределами открытого месяца и неизменность всех 148 таблиц
при миграции. Некоторые тесты объединяют несколько шагов одного сценария.
`go vet ./internal/app` также прошёл. Это синтетическая backend-проверка;
она не подменяет приёмку интерфейса или подтверждение публикации.

### Совместимость отметок перевода после независимого ревью

Проверка интеграции обнаружила отдельный обход: старый открытый интерфейс мог
направить `/entries/{id}/transfers` для нового простого поступления. Если
ненулевая отметка сохранялась, прежняя защита `financeHasPaid` запрещала отмену,
а обычный интерфейс простого учёта не показывал такую отметку. Это не расход
и не основание автоматически списывать деньги.

Теперь положительная отметка перевода для записи с `receiptKind` возвращает 409
без изменения суммы и ревизии. В сообщении предлагается записать расход.
Снятие отметки до нуля остаётся разрешённым: так можно исправить состояние,
которое сохранил прежний runtime, и затем штатно отменить поступление.
Правила переводов для личного и прежнего расширенного учёта не меняются.
Дополнительный регрессионный сценарий проверяет создание через API, отказ
устаревшему интерфейсу, неизменность ревизии и нормальную отмену; затем
синтетически воспроизводит прежнюю сохранённую отметку и проверяет восстановление
через обнуление и отмену без изменения вида либо суммы поступления.

После этой правки повтор всей финансовой выборки прошёл: **45 тестов**, включая
девять тестов простого командного учёта, 35,052 секунды. `go vet ./internal/app`
также прошёл. Предыдущий результат 44 тестов выше сохранён как история проверки
до найденного ограничения совместимости.
