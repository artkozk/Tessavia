# Контракт рабочих пространств и CRM-конструктора BizFlow

Дата: 2 сентября 2026 года.

## Цель контракта

Контракт определяет границы командных данных и модель настраиваемых досок. Он нужен, чтобы будущие функции не вернули глобальные списки пользователей и карточек и не превратили первую CRM в специальный код, который невозможно повторно использовать.

Продуктовое поведение описано в `docs/product/BIZFLOW_CONFIGURABLE_CRM_RELEASE_2026_09_02.md`.

## Контекст рабочего пространства

1. Авторизованный запрос может передать `X-Workspace-ID`.
2. Сервер проверяет активную запись пользователя в `workspace_members`.
3. При отсутствии заголовка выбирается доступная команда с приоритетом исторического `bizflow-team`.
4. Проверенный `workspaceAccess` сохраняется в `request.Context`.
5. Все новые записи получают `workspace_id` из контекста, а не из тела клиента.
6. Клиент не может подменить команду полем JSON.
7. Роль `owner` или `admin` требуется для изменения схемы доски.

Этот порядок оставляет один механизм авторизации для веб-интерфейса и будущих мобильных клиентов.

## Модель данных

Миграция: `internal/app/migrations/018_workspace_crm_constructor.sql`.

### `workspaces`

Добавлено описание команды. Существующие строки сохраняются без изменений и получают пустое описание.

### `records`

Добавлены:

- `workspace_id` — обязательная граница данных;
- `collection_id` — необязательная принадлежность доске;
- `stage_id` — необязательный этап доски.

Обычные карточки BizFlow могут не относиться к доске, но всегда относятся к рабочему пространству. Это сохраняет существующие цели, исследования и решения и не заставляет превращать весь продукт в kanban.

### `workspace_collections`

Хранит доску, описание, пользовательское название карточки, базовый тип записи и порядок. Название уникально внутри рабочего пространства, но может повторяться в разных командах.

### `collection_stages`

Хранит отображаемое название, категорию, цвет и порядок. Категория ограничена значениями:

- `backlog`;
- `active`;
- `review`;
- `done`.

Отображаемое название свободно, а категория даёт общей платформе стабильную семантику.

### `collection_fields`

Хранит стабильный ключ, имя, тип, обязательность, видимость на карточке и порядок. Ключ и имя уникальны внутри доски.

### `collection_field_options`

Хранит варианты полей `select` и `multi_select`, их цвет и порядок. В карточке сохраняется ID варианта, поэтому переименование варианта в будущем не потребует переписывать все записи.

### `record_field_values`

Связывает карточку и поле, хранит JSON-значение, автора последнего изменения и время. Составной первичный ключ запрещает несколько конкурирующих значений одного поля в одной карточке.

## Проверка значений

Сервер нормализует значения по типу:

- числа и суммы принимают JSON number;
- checkbox принимает boolean;
- пользователь должен быть активным участником команды карточки;
- relation должна указывать на карточку той же команды;
- select принимает только активный option ID своего поля;
- multi-select удаляет повторы и отклоняет чужие варианты;
- даты проверяются как ISO-значения;
- URL, email и телефон сохраняются строками после ограничения длины;
- обязательное поле нельзя очистить.

Frontend не является границей доверия: все ограничения повторяются на сервере.

## Сопоставление этапа и общего статуса

При перемещении карточки сервер устанавливает:

| Категория этапа | Общий статус |
| --- | --- |
| `backlog` | `planned` |
| `active` | `in_progress` |
| `review` | `review` |
| `done` | `completed` |

Для `done` также устанавливаются `progress = 100` и `completed_at`. При возврате завершённой карточки из `done` снимается `completed_at`; автоматические 100% сбрасываются, чтобы карточка снова считалась активной.

## HTTP-контракт

- `POST /api/workspaces` — создать команду;
- `GET /api/collections` — получить доски активной команды;
- `POST /api/collections` — создать доску и четыре стандартных этапа;
- `PATCH /api/collections/{id}` — изменить название, описание и название карточки;
- `POST /api/collections/{id}/stages` — добавить этап;
- `PATCH /api/collections/{id}/stages/{stageId}` — изменить этап;
- `POST /api/collections/{id}/fields` — добавить поле и варианты;
- `PATCH /api/collections/{id}/fields/{fieldId}` — изменить название, обязательность и видимость;
- `PUT /api/records/{id}/stage` — переместить карточку;
- `PUT /api/records/{id}/custom-fields` — сохранить пользовательские значения.

Существующий `POST /api/records` принимает `collectionId`, `stageId` и `customFields`, но самостоятельно проверяет их принадлежность активной команде.

## Границы чтения

Выпуск добавляет scoping по `workspace_id` для:

- list/get records;
- activity;
- search;
- graph;
- team capacity и quality;
- planning cycles;
- saved views;
- team chat;
- pending questions;
- пользовательского списка;
- CSV/JSON export.

Дочерние сущности экспортируются через JOIN с `records` активной команды. JSON export имеет `schemaVersion = 11`, добавляет `workspaceId` и включает схему коллекций. Скачивание вложения сначала разрешает родительскую карточку через тот же workspace-контекст.

## Обратная совместимость

- существующие карточки получают `workspace_id = 'bizflow-team'`;
- существующие сохранённые представления, циклы, чаты и события получают ту же команду;
- доска для старых карточек не назначается;
- старые URL карточек продолжают работать внутри исторической команды;
- откат бинарника возможен, потому что новые поля имеют безопасные значения по умолчанию, а новые таблицы старым кодом не используются.

После production-миграции нельзя возвращать backup без отдельного подтверждения: это потеряет карточки и настройки, созданные пользователями после выпуска.

## Индексы

Добавлены индексы по рабочему пространству и состоянию карточки, коллекции и этапу, спискам коллекций, этапов, полей, значений, истории, циклам, чатам и представлениям. Их назначение — сохранять фильтрацию по границе команды до сортировки и не сканировать данные остальных пространств.

## Инварианты дальнейшей разработки

1. Новый командный объект обязан иметь прямой `workspace_id` или проверяемую цепочку FK до объекта с `workspace_id`.
2. Endpoint, принимающий ID карточки или файла, обязан проверить доступ через активную команду.
3. Нельзя возвращать глобальный список пользователей как список возможных ответственных.
4. Экспорт не может использовать `SELECT *` без workspace-ограничения.
5. Тип заполненного пользовательского поля нельзя менять без явной миграции данных.
6. Финальный этап обязан синхронизироваться с общей семантикой завершения.
7. UI может скрыть действие по роли, но сервер всё равно проверяет роль.
8. Новая предметная CRM-функция сначала рассматривается как настраиваемое поле, этап или представление; отдельный hardcoded модуль создаётся только при наличии уникального поведения.

## Проверки

`workspace_crm_test.go` проверяет изоляцию, роли, изменение схемы, пользовательские значения, перенос этапа, запрещённое назначение и export. `workspace_crm_seed_test.go` дважды запускает seed первой CRM и подтверждает отсутствие дубликатов, точные количества сущностей и валидный JSON значений.

## Уточнения по итогам предрелизной проверки

1. Если ключ поля не задан API-клиентом, сервер строит его из названия. При совпадении добавляется стабильный суффикс из ID поля. Это особенно важно для кириллических названий: техническая коллизия не мешает создать второе поле с другим отображаемым именем.
2. Поле `date` принимает `YYYY-MM-DD`, а `datetime` — RFC 3339. Пустая строка считается очисткой необязательного поля.
3. `multi_select` удаляет повторы, сохраняя порядок первого вхождения.
4. Аудит качества не помечает карточку как `orphan`, если она входит в коллекцию. Коллекция сама задаёт место карточки в процессе. Для знаний и обычных карточек вне досок прежнее правило родителя или смысловой связи сохранено.
5. Интеграционный тест дополнительно проверяет отклонение неверной даты, сохранение верной, дедупликацию multi-select и отсутствие ложной проблемы `orphan`.
6. При создании карточки любой ID поля, которого нет в активной схеме доски, отклоняется как ошибка. Сервер не игнорирует неизвестную колонку, иначе импорт мог бы завершиться с незаметной потерей данных.

## Уточнение обратной совместимости после production-импорта

До появления записей в новом workspace предыдущий binary технически может открыть БД: добавленные поля и таблицы ему не мешают. После создания второй команды и её карточек обычный rollback только binary запрещён: старые запросы не знают о `workspace_id` и могут смешать данные. Предпочтителен forward-fix; аварийное возвращение старого binary возможно только в режиме обслуживания вместе с докомандным backup и осознанной потерей всех послерелизных изменений.

## Жизненный цикл схемы — 04.09.2026

По новому прямому запросу пользователя реализован следующий этап конструктора:
поля и колонки можно удалять с восстановлением и переставлять. Это дополняет
описанную выше модель, а не отменяет прежние этапы. Физического удаления значений
нет: удалённое обязательное поле перестаёт требоваться, а после восстановления
возвращается с тем же ID. Карточки удаляемой колонки переводятся в другую
колонку той же доски без изменения типа и состояния.

Общая доска состояний настраивается отдельно как личное представление: скрытие
колонки не меняет схему команды. Причина разделения — прежняя кнопка «Поля и
этапы» в общей очереди открывала настройки другой доски и создавала неверное
ожидание удаления системных состояний. Полные сценарии, API, проверки и границы
этапа: [управление схемой и длинная очередь](CONSTRUCTOR_AND_BOUNDED_WORK_2026_09_04.md).
