# Установка на телефон и безопасный быстрый запуск

Дата: 14.09.2026. Основание — новый запрос пользователя о мобильных уведомлениях,
виджетах главного экрана и быстром доступе к заметкам. Пользователь сам собирает
свой набор в конструкторе; этот этап не создаёт специальную страницу в его
аккаунте и не подменяет настройку, доступную остальным пользователям.

Документ описывает web-этап установки и навигации. Он дополняет
[единые настройки](UNIFIED_SETTINGS_2026_09_10.md),
[очередь новых записей](OFFLINE_OUTBOX_CONTRACT_2026_09_03.md) и
[мобильную оболочку](MOBILE_SHELL_2026_09_14.md). Исторические решения, в том числе
ранние планы APK, остаются в прежних документах. Их новая граница: APK не нужен
как предварительный этап для установки поддерживаемой PWA и её быстрых ссылок.

## Что было до изменения

В `manifest.webmanifest` уже были имя, постоянный `id`, иконки и `display:
standalone`, но отсутствовали `shortcuts`. Отдельного понятного места с
инструкциями установки и быстрыми ссылками не было. Вход в личный редактор
заметки существовал внутри приложения, однако системная команда не могла
запустить его после авторизации. Обычная навигация сохраняла личные/командные
контексты и локальные черновики; переписывать её отдельным мобильным редактором
не требовалось.

## Единое место в интерфейсе

В каталоге `settings-hub.js` добавлена одна строка:
**Настройки → Личные настройки → На телефоне**. Она доступна участнику команды
без административных прав: установка относится к его устройству. Нет новой
постоянной строки бокового меню, рекламного баннера или автоматического окна
установки при входе.

`mobile-access.js` создаёт свой диалог до подключения общих обработчиков окон.
Он использует `openModal`/`requestDialogClose`, привычный заголовок с × и
палитру приложения. Отдельный `mobile-access.css` ограничивает стили этим
диалогом. На узком экране есть одна прокрутка содержимого; полоса скрывается
визуально, прокрутка сохраняется. Кнопки не меньше 44 px, подписи переносятся,
колонка быстрых действий не имеет фиксированной минимальной ширины. Обновление
состояния установки сохраняет раскрытые инструкции, прокрутку и фокус доступной
кнопки, если она остаётся в новом состоянии.

Раздел содержит:

- состояние текущего окна и сетевой индикатор браузера;
- кнопку установки только при полученном событии браузера;
- сворачиваемые инструкции iPhone/iPad и Android;
- четыре быстрые ссылки: новая заметка, мои заметки, новое дело, сегодня;
- копирование этих ссылок для собственного ярлыка, с ручным выделением URL,
  если Clipboard API недоступен;
- переход в существующий единый раздел уведомлений и напоминаний;
- явное объяснение различия ярлыков и живых системных виджетов.

## Состояния установки и уведомлений

Режим отдельного приложения определяется через `display-mode: standalone` и
совместимый признак `navigator.standalone`. Обычная вкладка называется
«Открыто в браузере»: отсутствие install prompt не доказывает, что приложение
нигде не установлено. Событие `appinstalled` даёт состояние «Установка
подтверждена»; физическое появление значка проверяется отдельно.

`beforeinstallprompt` сохраняется в памяти и вызывается один раз по кнопке
«Установить Tessavie». Автоматического `prompt()` при посещении нет. Отказ или
ошибка не запускают повтор по таймеру: остаются инструкции браузера. Поздний
ответ после смены аккаунта или закрытия окна не перерисовывает новую сессию
настроек. Обработка `appinstalled` и состояния сети не меняет пользовательские
страницы.

Модуль только читает `Notification.permission`. Он не вызывает
`Notification.requestPermission`, `PushManager.subscribe` и не управляет
серверной подпиской. Строка «Браузер разрешает уведомления» не называется
подключённой доставкой. Настоящие состояния per-device регистрации и проверка
отправки относятся к модулю уведомлений в существующем разделе напоминаний.

Индикатор «Браузер в сети» — значение `navigator.onLine`, а не доказательство
доступности сервера или доставки Web Push.

## Контракт быстрого запуска

Постоянные `manifest.id`, `scope` и `start_url` оставлены `/`. Обычная иконка
Tessavie сохраняет прежний сценарий восстановления рабочего экрана. Новые
manifest shortcuts перечислены в порядке: заметка, дело, сегодня. Они используют
существующую PNG-иконку бренда, не требуют пользовательских ID и не меняют наборы.

Допускаются только следующие URL на текущем origin:

| URL | Действие |
| --- | --- |
| `/?launch=note` | Личный раздел заметок и обычный редактор новой заметки |
| `/?launch=notes` | Личная библиотека заметок |
| `/?launch=plan` | Личные дела и обычный редактор нового дела/события |
| `/?launch=today` | Личный экран «Сегодня» |
| `/?launch=notifications` | Общий аккаунтный inbox уведомлений |

`mobileLaunchAction` отклоняет другой origin, credentials в URL, иной путь,
непустой hash, неизвестное действие, повторный `launch` и любые дополнительные
параметры. Нельзя передать приватный текст, ID записи, произвольный redirect или
одновременно выполнить приглашение/установку набора. Обычные `invite` и
`interface-preset` продолжают обрабатываться своими существующими путями;
мобильный обработчик не удаляет их из смешанного невалидного URL.

Намерение находится только в памяти страницы до авторизации и готовности
данных. Пока открыт вход, оно не запускает редактор. После bootstrap либо
успешного login выполняется один раз, а параметр `launch` удаляется через
`history.replaceState` с сохранением остального history state. Обновление
страницы после выполнения не создаёт второй редактор. Сброс уже известного
аккаунта отменяет его ожидающее намерение; оно не переходит следующему
пользователю общего браузера.

Быстрый запуск вызывает обычные `navigateToView`, `loadPersonal` и
`openPersonalEditor`. Новая пустая запись автоматически не отправляется на
сервер. Черновик новой заметки/дела восстанавливается существующей системой;
сохранение идёт через прежнюю очередь. Во время холодного автономного старта
действует существующий отдельный offline-экран: этот этап не заявляет новый
режим авторизации или мгновенный offline-launch поверх него.

## Живая вкладка и клик по push

По согласованию с серверным этапом `/api/notifications/inbox` объединяет
доступные личные и командные уведомления аккаунта. Поэтому
`launch=notifications` не переключает workspace заранее. При открытии
конкретного уведомления существующий обработчик выбирает контекст его источника.

Для уже открытого клиента service worker передаёт только:

```json
{"type":"tessavie-open-notifications"}
```

Модуль принимает это сообщение через `navigator.serviceWorker`, проверяя
`event.source.scriptURL`: тот же origin и путь `/sw.js`. Сообщения другого
источника и произвольные типы игнорируются. В сообщении нет адреса назначения,
названия дела или ID. При отсутствии авторизации обработка ждёт входа и готовности
данных, не раскрывая содержимое уведомления на экране входа.

Живой клиент не использует `location.reload`/`navigate` для такого клика.
`runMobileLaunch` вызывает общий механизм закрытия диалогов. Ранее
`leaveSettingsFor` закрывал только окна над центром настроек; теперь у него есть
явный необязательный параметр `closeAll`, которым пользуется мобильный запуск.
Поведение прежних вызовов не изменено. Новый путь:

1. Сохраняет черновики через существующий обработчик закрытия. Ошибка локального
   хранилища оставляет форму открытой и останавливает переход.
2. Дожидается уже поставленного в очередь browser Back для закрытого overlay,
   затем закрывает следующий overlay. Навигация не обгоняет history-событие.
3. Проверяет аккаунт, workspace, исходный экран, поколение контекста и поколение
   маршрута. Чужой поздний ответ не закрывает новую форму и не открывает старый
   редактор поверх выбранной пользователем страницы.
4. После перехода и чтения личных данных снова проверяет аккаунт, workspace и
   маршрут перед открытием редактора.

Повторное сообщение во время обработки одного запуска ожидает завершения,
не открывая два окна одновременно. Отказ сохранения черновика не считается
успешным переходом.

## Ярлыки и живые виджеты

Ярлык — команда открытия. В поддерживаемой системе удержание значка PWA может
показать manifest shortcuts. Для iPhone описано создание своей команды открытия
URL в «Быстрых командах» и размещение её на экране «Домой». URL одинаково работают
у пользователей платформы и не содержат ссылок на персональный набор автора.

Живой WidgetKit/Glance виджет с обновляемым содержимым Tessavie этим этапом не
реализован и не называется готовым. Его настройка из конструктора, список
поддерживаемых источников/действий, расписание обновления и очистка приватного
снимка при выходе составляют отдельную planned-задачу. Наличие кнопки запуска в
системном виджете «Быстрых команд» тоже не доказывает живой виджет данных Tessavie.

## Проверки web-этапа

Новый `web/mobile-access.test.cjs` содержит 13 проверок:

1. Строгий allowlist и отклонение неоднозначных/чужих URL.
2. Сохранение identity/start_url/scope и три manifest shortcuts.
3. Один вход личных настроек, доступный обычному участнику.
4. Ожидание авторизации/данных и однократное потребление URL.
5. Сброс ожидающего запуска при смене известного аккаунта.
6. Проверка источника SW и ожидание входа для inbox.
7. Install prompt только от события браузера и только по пользовательской кнопке.
8. Позднее завершение install prompt после смены аккаунта.
9. Честные подписи режима, разрешения и состояния живых виджетов.
10. Ручное копирование URL и стандартное поведение Ctrl/Cmd-клика ссылки.
11. Реальный `runMobileLaunch`: личный редактор и inbox без смены workspace.
12. Отказ закрытия/загрузки и защита от позднего ответа другого контекста.
13. Реальный общий обработчик overlay: отказ сохранения черновика и ожидание
    history Back до перехода.

Профильный запуск вместе с settings, personal-plan references и calendar lifecycle:
**49/49 PASS**. Полный `node --test web/*.test.cjs` перед последней добавленной
проверкой входа настроек: **538/538 PASS**. После этой добавленной проверки
профильный набор повторён, синтаксис runtime и `git diff --check` прошли.
Итоговый общий запуск выпуска и браузерная приёмка фиксируются root отдельно.

Физические iPhone/Android, системная установка, клавиатура телефона и доставка
на заблокированный экран этими Node-проверками не объявляются проверенными.
Версия ресурсов: `20260914-mobile-access-1`. Встраивание файлов в embedded assets,

Подготовлен `deploy/upsert-mobile-access-tasks-20260914.py`. Без `--apply` он
только читает task metadata через краткоживущую операторскую сессию; сама сессия
всегда удаляется. С `--apply` создаёт недостающие задачи по устойчивым маркерам:

| Маркер | Статус при создании | Родитель |

| `request:web-push-delivery-20260914` | in_progress | `78d357246455a37e129e689c3a7e9d9c` |

Описание родительских задач только дополняется уточнением нового запроса. Их
статусы, названия, ответственные и прежняя история сохраняются. В native-план
`88c24efba689dd1d77282b17bda30ec7` добавляется исследовательское уточнение о PWA
и нативных системных возможностях; готовность native не утверждается.

Полнота API-выдачи задач сверяется с SQL count до и после. Проверяются проект
`bizflow-team`, активный оператор `artkozk/1`, уникальность scope-маркеров и
родителей; creation uses idempotency key, append uses expectedUpdatedAt. Receipt
содержит только метаданные и пишется в `/tmp/mobile-access-tasks-created.json`.
Тексты личных записей, push endpoints, ключи и токены в него не включаются.

Локальная проверка скрипта с подставными API/DB подтвердила review без записи
задач, создание четырёх задач, четыре append-only PATCH, идемпотентный повтор,
отказ при неполной выдаче и очистку сессии. На момент подготовки этого документа
автор web-этапа не запускал скрипт на сервере. Фактические ID новых задач и
production receipt добавляются после выполнения root.

### Уточнение типов родителей после первой проверки на сервере

Первый запуск root остановился до записи задач на проверке типа родителя:
`17b1c09b1f9d54518a4459e57715cff1` — сущность **goal**, а не task. Остальные три
записи, дополняемые скриптом, являются task. Прежнее обобщение «родительские
задачи» выше обозначает родительские записи и не меняет их настоящий тип.

В скрипте добавлена точная карта `PARENT_TYPES` по четырём ID. Проверка не
ослаблена до произвольной сущности: сохраняются ожидаемый тип и workspace.
Полная выдача и SQL count по-прежнему сравниваются только для type=task; goal
читается отдельно как родитель. Повторный локальный mock прогон со смешанными
типами подтвердил dry review, четыре create, четыре append-only PATCH,
сохранение исходных типов/статусов, идемпотентный повтор, отказ при неполной
выдаче и неверном типе, очистку краткоживущей сессии. Повторный production-запуск
и его receipt остаются у root.
