# Открытие приложения и независимость домашних копий — 14.09.2026

## Обращение и проверенная граница хранения

Пользователь прислал экран «Работа без подключения» и уточнил: домашний сервер
должен содержать только резервные копии и данные, не требующие быстрого доступа.
Действующая схема проверена непосредственно на VPS 14.09 в 05:38 UTC:

- Процесс business-control работает с 03:16:52 UTC, PID 870192, NRestarts=0.
- Рабочие SQLite и uploads находятся в /var/lib/business-control на локальном
  ext4 /dev/vda1. Символического переноса на домашний том нет.
- В конфигурации приложения и его systemd unit нет адреса домашнего узла.
  В Requires/Wants/BindsTo нет домашнего хранилища и службы копирования.
- Свободно около 2,14 GiB диска и 655 MiB MemAvailable. Резервная служба
  закончила работу успешно в 05:21 UTC; приложение она не перезапускала.
- В 05:33 UTC, соответствующие времени 08:33 на снимке, журнал nginx
  содержит четыре ответа 200 на главную для Android. В рассмотренных логах
  за 05:20–05:39 запрос /api/me от Android не обнаружен. IP, cookie, query
  и содержимое пользовательских данных в отчёт не передаются.

Дома находятся только готовые зашифрованные архивы. Приложение не читает
оттуда рабочие записи и вложения и не ждёт домашнюю машину при запросах.
Домашний клиент сам получает копии с VPS; его остановка прерывает только
дополнительное копирование. Архивные пользовательские записи автоматически
не переносились. Даже закрытая задача или старый файл могут понадобиться
интерфейсу: их возраст сам по себе не считается разрешением на удаление с VPS.
Новый запрос подтверждает эту границу; прежние документы хранения сохранены.

## Воспроизведённая ошибка клиента

Экран на снимке создаёт web/outbox-ui.js; он существовал до подключения
домашнего сервера. В bootstrap приложения выполнялся ранний выход:
при navigator.onLine=false и наличии локального аккаунта сразу показывался
автономный экран, без запроса /api/me. Кнопка «Открыть платформу» перезагружала
страницу и попадала в тот же ранний выход.

В тестовом браузере с реальным доступным сервером и принудительным ложным
флагом onLine прежняя сборка воспроизвела тот же экран: запросов /api/me — 0.
Точный сетевой статус физического телефона недоступен. Логи и воспроизведение
подтверждают дефект, но не доказывают, чем именно был вызван флаг на телефоне;
наличие значка VPN не является установленной причиной.

## Минимальное исправление

Из bootstrap убран только ранний выход по браузерному признаку сети.
Теперь сначала выполняется существующий запрос /api/me. Успешный ответ
открывает приложение; настоящий обрыв оставляет автономную очередь;
401/403 приводят к авторизации. Существующие ограничения времени и повтор
чтения сохраняются. Кнопка повторного открытия теперь действительно проверяет
сервер даже при старом неверном флаге браузера.

Версия основного app.js и имя кеша обновлены на 20260914-offline-recovery-1.
Остальные неизменённые модули сохраняют версии personal-references.
Автоматическая перезагрузка поверх незавершённого текста не добавлена.
IndexedDB, локальная очередь и черновики не очищаются. Данные сайта не требуется
удалять для получения исправления; достаточно обычного повторного открытия.

   Восстановление сети и нажатие «Открыть платформу» вернули приложение.

   Удаление тестовой cookie привело к форме входа, не к ложному offline.

   Service worker в этой браузерной проверке заблокирован: проверяется именно
   открытие сессии; кеширование отдельно покрыто Node и embedded-assets.
   Физический Android пользователя в этой среде не проверялся.

## Порядок выпуска и сохранность

Кандидат готовится из отдельного дерева от371c5d7. Параллельная незавершённая
мобильная функциональность в выпуск не включается. Linux-бинарник собирается
локально; каждый Go/SQL/web сборочный вход сопоставляется с исходным commit.
На VPS используется deploy/deploy-offline-recovery-20260914.sh, основанный
на штатном проверенном выпуске personal-references:

1. Общая блокировка деплоя и проверка предыдущего release 33b926b и SHA.
2. Резервные SQLite/uploads/env/nginx на том же VPS; проверка целостности.
3. Пробный запуск кандидата и прежнего бинарника на копии; сравнение схемы
   070 и значений всех 127 таблиц существующим валидатором.
4. Короткая остановка приложения, дополнительная копия непосредственно перед
   переключением, атомарная замена current и запуск. Домашний сервер в этом
   процессе не участвует. Данные при возможном откате не заменяются backup.
5. Проверки HTTPS, новой версии app.js/SW, API, службы и целостности после
   переключения. Сбой проверок возвращает совместимый прежний бинарник;
   это вернёт прежнюю ошибку браузерного offline, но сохранит пользовательские
   данные и ранее выпущенное поведение личных связей.

Итоговые commit, SHA, backup и фактическое завершение добавляются ниже после
выпуска. Этот раздел описывает подготовленный проверяемый порядок, а не
объявляет ещё не выполненное переключение завершённым.
