# Безопасная смена типа заполненного поля — 14.09.2026

Этот этап продолжает зарегистрированную задачу
`2092665a817cc23073154bc1adf06377` и сценарий SC-73 из
`CONSTRUCTOR_FIELD_DEFAULTS_2026_09_07.md`. Исторический контракт начальных
значений сохраняется: он описывал выпуск, в котором смена типа отсутствовала.
Теперь вводится ограниченный, проверяемый сценарий преобразования. Общая цель
произвольного конструктора данных этим этапом не закрывается.

## Зачем это нужно

Пользователь должен самостоятельно менять структуру своего процесса, даже если
карточки уже заполнены. Например, поле «Услуга» с одним вариантом превращается
в набор услуг; короткое примечание становится многострочным; обычное число
показывается денежной суммой. Не нужно создавать новое поле и вручную переносить
каждую карточку. При этом выбор нового типа не даёт права незаметно отбросить
второй выбранный вариант или округлить число.

В незавершённом локальном прототипе до этого этапа проверка выполнялась вне
транзакции применения, учитывались только карточки, остающиеся на доске,
проверка числа затронутых строк отсутствовала, а исходные значения не попадали
в историю. Прототип не был включён в выпуск мобильного меню `b66b33c`.
Текущая реализация заменяет эти неполные механизмы, причины перечислены ниже.

## Допустимые преобразования

| Исходный тип | Новый тип | Что происходит со значением |
| --- | --- | --- |
| `text` | `long_text` | Сохранённый JSON текста остаётся байт в байт прежним. |
| `long_text` | `text` | Содержимое, включая переносы строки, сохраняется. |
| `number` | `money` | Меняется представление, точное сохранённое число остаётся прежним. |
| `money` | `number` | Денежное представление становится числовым без пересчёта суммы. |
| `select` | `multi_select` | ID варианта превращается в список из одного ID; пустая строка — в пустой список. |
| `multi_select` | `select` | Пустой список становится пустой строкой; один ID становится строкой. Два и более элемента блокируют операцию. |

Явный `null` сохраняется во всех парах, включая очищенное начальное значение.
Отсутствующая строка начального значения остаётся отсутствующей. При изменении
числовых типов значение не проходит цикл float → JSON, поэтому, например,
`9007199254740993` не превращается в `9007199254740992`. Браузер получает также
точные строки для предпросмотра, чтобы его `JSON.parse` не исказил большое число.

Каждое сохранённое значение проверяется на валидный JSON и исходный тип.
Объект вместо текста, строка вместо числа, `[null]` вместо списка ID и подобные
повреждения останавливают преобразование. Неизвестные пары, например
дата → дата со временем или текст → число, не разрешены. Для них нужен отдельный
контракт явного сопоставления и разрешения ошибок. Повторная установка текущего
типа отклоняется и не используется как обход проверки предпросмотра.

## HTTP-контракт и последовательность

1. Авторизованный владелец или администратор открывает поле нужной доски.
   Участник проекта не может менять схему. Чужой проект или поле другой доски
   недоступны; архивное поле нельзя преобразовывать до восстановления.
2. `POST /api/collections/{id}/fields/{fieldId}/conversion-preview` с
   `{"fieldType":"multi_select"}` читает единую транзакционную копию состояния.
   Запрос не меняет карточки, определения, начальные значения и историю.
3. Ответ включает `fieldId`, `from`, `to`, `affected` (число сохранённых значений),
   `changed` (число изменивших JSON-представление значений), `archived`, `detached`,
   `defaultBefore`, `defaultAfter`, `defaultChanged` и `conversionHash`.
   `archived` и `detached` — пересекающиеся подмножества `affected`, их не нужно
   прибавлять к общему числу.
4. В `examples` не более пяти примеров с `recordId`, `recordTitle`, `value`,
   `converted`, `valueRaw` и `convertedRaw`. Точные строки `defaultBeforeRaw` и
   `defaultAfterRaw` пусты при отсутствии настройки; явный null передаётся
   строкой `null`. Числовые примеры следует показывать через точные строки.
   Названия вариантов интерфейс получает из существующего справочника поля;
   стабильные ID вариантов не меняются.
5. `PATCH /api/collections/{id}/fields/{fieldId}` передаёт `name`, `required`,
   `showOnCard`, `fieldType`, `expectedUpdatedAt` и `conversionHash`.
   Версия и предпросмотр обязательны. В этом запросе нельзя одновременно менять
   `options` или `defaultValue`: сначала завершается проверенная смена типа,
   затем отдельно редактируется справочник или начальное значение. Это позволяет
   явно проверить две разные операции и не интерпретировать новый default по
   старому типу.
6. Сервер повторно читает данные внутри транзакции применения и сравнивает хеш
   и версию. При изменении схемы, справочника, default, значения, состава или
   версии карточек возвращается 409. Человек должен снова увидеть актуальный
   предпросмотр; прежний токен нельзя применять молча.
7. Успешный PATCH возвращает актуальный `CollectionField` с новой версией и
   преобразованным default. Общий формат обычного редактирования поля сохраняется.

Несовместимое или повреждённое значение возвращает 400 с пояснением и названием
карточки текущего проекта, без вывода её сырых данных. Отсутствующее/архивное поле
возвращает 404. Ошибка сохранения истории или значения отменяет всю транзакцию.

## Какие данные входят в операцию

Читаются все карточки текущей доски и все сохранённые строки этого поля в текущем
проекте, включая архивные карточки и ранее отсоединённые от доски. Иначе скрытый
старый JSON мог бы позже вернуться с уже неподходящим типом. Карточки без значения
не получают искусственного заполнения, но их `updated_at` меняется вместе со
схемой: открытая ранее форма должна заметить устаревший формат.

Если повреждённая связь указывает на строку поля в другом проекте или на
отсутствующую карточку, операция блокируется общей ошибкой целостности. Значение,
ID и название чужой карточки не включаются в ответ и не изменяются.

Хеш строится по JSON с явными полями: проект, доска, новый тип, определение поля,
справочник вариантов со статусами, наличие/значение/версия default и полный
набор карточек со значениями и версиями. Строки сортируются SQL по стабильному
ID. Разделители внутри пользовательских значений не могут склеить два разных
состояния в одинаковую последовательность. Хеш — проверка актуальности, а не
замена авторизации или секретный токен.

В применении нет запросов через внешнее соединение между чтением состояния и
записью. SQLite-транзакция охватывает схему, значения, версии карточек, default
и историю. Каждый условный UPDATE проверяет ровно одну затронутую строку.
Если строка исчезла или триггер отклонил запись, ранее сделанные изменения
откатываются. Новый JSON не может частично сохраниться под старым типом.

## История и открытые черновики

В историю каждой карточки с сохранённым значением добавляется событие
`field_type_converted`: ID/название поля, исходный и новый тип, точные строки
`beforeRaw`/`afterRaw`, хеш операции. Отдельное событие доски сохраняет счётчики
и исходный/новый JSON default вместе с признаком наличия настройки. Ранее
записанные события не обновляются и не удаляются. Автоматической кнопки отката
этим этапом не вводится: обратная совместимая смена типа тоже требует нового
предпросмотра и сохраняет собственную историю.

Существующий API сохранения полей карточки уже требует её `expectedUpdatedAt`.
После смены типа версии всех карточек доски обновлены. Дополнительно обработчик
проверяет версии прочитанных определений уже внутри своей транзакции: изменение
схемы между загрузкой полей и сохранением приводит к 409. Черновик нельзя
автоматически повторно отправлять, подменив версию актуальной. Для создания новой
карточки действуют текущие правила типов; сохранённое значение старого формата
должно быть пересмотрено пользователем. Поведение браузерных черновиков и
фактические проверки интерфейса фиксируются корневой задачей в отчёте выпуска.

## Проверенные серверные сценарии

Команда `go test ./internal/app -run 'TestFieldConversion|TestCollectionFieldTypeConversion' -count=1`
прошла 14.09.2026 за 3.857 s после добавления проверок пустого и архивного поля.
Отдельно перед последним расширением прошли проверки defaults и конфликтов
карточек вместе с этим набором за 4.894 s. Сценарии используют новую локальную
базу с синтетическими аккаунтами и настоящие HTTP-обработчики:

- Все разрешённые пары, оба направления; точный большой integer, экспоненциальное
  число, переносы текста, пустые значения и явный null.
- Предпросмотр без записи; отсутствие искусственного default и без потери
  стабильных ID вариантов.
- Преобразование живой, архивной и отсоединённой карточки; новые версии пустых
  карточек; отказ старой форме с прежней версией.
- История исходных и преобразованных JSON; обратная смена типа добавляет событие,
  не переписывает прежнее.
- Изменение значения даже без обновления времени, добавление/удаление строки,
  default, справочника и схемы между preview/apply; все старые токены отклонены.
- Несколько выбранных вариантов, повреждённые типы и default; 0 строк UPDATE,
  принудительная ошибка записи истории — без частичных изменений.
- Права owner/admin/member/outsider, другая доска, чужое личное пространство,
  архив/восстановление, обязательность версии/хеша, запрет одновременного default
  или справочника и запрет смены на тот же тип.

Полный прогон приложения, браузерный сценарий и production-публикация не
подменяются этими узкими тестами. Их результаты и SHA фиксируются отдельно
после выполнения. Миграция схемы этому этапу не требуется.

## Дополнение после проверки остальных путей записи

При повторном чтении создания карточки найдено отдельное окно гонки: обработчик
мог загрузить и нормализовать старый тип, затем начать транзакцию уже после
завершившегося преобразования и вставить прежний JSON. Так же устроено добавление
существующей карточки на доску. Поэтому общий `collectionFieldSnapshotMatches`
теперь вызывается внутри транзакций создания, изменения полей и добавления на
доску, до их первой записи. Он сравнивает весь набор активных полей, типы и
версии и проверяет, что доска активна. Даже добавление нового обязательного поля
между чтением и записью приводит к конфликту. Действия страниц уже читают
определения в своей транзакции с блокировкой и отдельным хешем схемы.

Дополнительный тест сохраняет старое определение, проводит преобразование через
HTTP и проверяет его отклонение транзакционным охранным условием. Настоящие HTTP
запросы создания и добавления со старым scalar-значением после перехода к списку
отклонены без подстановки default; актуальный список сохраняется. Это проверка
охраны снимка и обработчиков, а не искусственно заявленная проверка аппаратной
параллельности. Расширенная команда с defaults, конфликтами и присоединением
карточек прошла за 5.732 s. Всего добавлено семь тестов верхнего уровня, часть
с отдельными подслучаями.
