# Восстановление Gemini и резервирование proxy-маршрута

Дата: 20 августа 2026 года.

## Назначение

Документ фиксирует причину отказа Gemini, выполненное аварийное восстановление и новый постоянный контракт резервирования внешнего AI. Исторические инструкции о Developer API и одном `AI_PROXY_URL` не удаляются: они описывают исходное состояние, от которого выполнена миграция.

## Симптом

Пользователь видел сообщение о недоступности внешнего AI, а карточки получали локальный эвристический разбор. Основной `/api/health` продолжал отвечать `ok`, потому что база и приложение были исправны. Это ожидаемое разделение: отказ внешнего AI не должен останавливать задачи, решения и историю проекта.

## Подтверждённая причина

В production были одновременно подтверждены:

1. `GEMINI_API_KEY` задан в root-only environment;
2. модель остаётся `gemini-2.5-flash`;
3. базовый URL остаётся Gemini Developer API;
4. `business-control` работает и видит SQLite;
5. журнал от 17–18 августа содержит `proxyconnect tcp ... connection refused`;
6. независимый server-side запрос через старый proxy возвращает HTTP `000` и transport error;
7. тот же Gemini key, model и payload через резервный proxy возвращают HTTP `200` и текстовую часть ответа.

Следовательно, отказал не Gemini key и не модель, а единственный сетевой proxy. Локальная эвристика включилась согласно существующему safety-контракту.

## Аварийное восстановление

1. Создана root-only копия `/etc/business-control.env` до изменения.
2. `AI_PROXY_URL` переключён на проверенный маршрут из ранее согласованного закрытого пула.
3. Права environment оставлены `0600`.
4. `business-control` перезапущен без миграции и изменения SQLite.
5. Общий доменный health повторно проверен.
6. Для точной проверки создана краткоживущая серверная сессия диагностики, вызван настоящий `/api/ai/health`, после чего сессия физически удалена.
7. Endpoint вернул `configured=true`, `providerAvailable=true`, `provider=gemini`, `model=gemini-2.5-flash`, `route=proxy`, `source=gemini`.

Ключ и proxy-credentials не выводились в отчёт и не добавлялись в Git.

## Постоянное исправление

### Конфигурация

- `AI_PROXY_URL` остаётся первым маршрутом и обеспечивает обратную совместимость;
- `AI_PROXY_URLS` содержит дополнительные маршруты, разделённые запятой, точкой с запятой либо переводом строки;
- пустые элементы и дубликаты удаляются с сохранением исходного порядка;
- при отсутствии proxy создаётся прежний direct-client;
- при наличии хотя бы одного proxy direct-client не создаётся.

### Выполнение запроса

1. Сервер начинает с последнего успешно работавшего маршрута.
2. Каждый retry получает новый body через `Request.GetBody`; частично отправленное тело не переиспользуется.
3. Следующий proxy используется при transport error или HTTP `407`, `502`, `503`, `504`.
4. Ответы `400`, `401`, `403`, `429` и другие предметные ошибки не маскируются ротацией: их должен обработать AI provider contract.
5. После успешного ответа индекс маршрута атомарно запоминается, поэтому мёртвый основной proxy не добавляет задержку к каждому следующему запросу.
6. Если все proxy отказали, сервер возвращает агрегированную transport error и включает локальный анализ. Прямой запрос не выполняется.

Такое поведение выбрано потому, что доступность Gemini важна, но не может быть достигнута ценой скрытого обхода согласованного конфиденциального маршрута.

## Проверки кода

- primary proxy остаётся первым, backup-список дедуплицируется;
- ответ `502` от первого proxy приводит к вызову второго;
- второй успешный proxy используется первым при следующем запросе;
- при двух неработающих proxy тестовый direct provider не получает ни одного запроса;
- некорректный proxy по-прежнему закрывает транспорт и не включает direct fallback;
- полный `go test ./...` и `go vet ./...` обязательны.

Во время прогона обнаружена календарная хрупкость старой workflow-фикстуры: дедлайн был жёстко задан на 20 августа 2026 года, и в этот день тест получил дополнительное уведомление. Дата фикстуры перенесена в далёкое будущее; предметная проверка преобразования задачи в вопросы не изменилась.

## Production rollout

Перед переключением binary необходимо:

1. сделать SQLite backup и проверить `integrity_check`/`foreign_key_check`;
2. собрать Linux amd64 binary и сверить SHA-256;
3. установить новый release в отдельный каталог;
4. проверить владельца и execute-права от имени `business-control`;
5. атомарно переключить `/opt/business-control/current`;
6. добавить в root-only environment минимум два предварительно проверенных маршрута через `AI_PROXY_URLS`;
7. перезапустить сервис;
8. проверить общий health и авторизованный `/api/ai/health`;
9. проверить, что API сообщает только число маршрутов, но не адреса и credentials;
10. удалить временную диагностическую сессию.

## Rollback

1. Вернуть предыдущий release symlink.
2. Вернуть backup `/etc/business-control.env`, если ошибка относится к конфигурации.
3. Перезапустить `business-control`.
4. Проверить общий health.
5. Проверить AI endpoint: допустим честный локальный fallback, но недопустима ложная маркировка ответа как Gemini.

## Остаточный риск

Proxy из внешнего пула может прекратить работу без предупреждения. Failover снижает влияние единичного отказа, но не заменяет мониторинг. Следующее инфраструктурное улучшение: периодический server-side health-check с уведомлением основателей, если количество доступных маршрутов стало меньше двух. Автоматически добавлять неизвестные публичные proxy запрещено.
