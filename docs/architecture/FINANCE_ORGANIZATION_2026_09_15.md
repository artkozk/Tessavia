# Группы и связи финансовых операций — 15.09.2026

## Зачем добавлены группы и связи

Финансовый регистр должен помогать пользователю вести собственные сценарии,
а не ограничивать их предустановленными статьями. Например, доход и несколько
расходов на разработку логотипа можно собрать в группу «Разработка» и связать
с конкретной целью или карточкой работы. Эти дополнительные признаки не
означают перевод денег, распределение на новые счета либо смену владельца.

Контракт дополняет [личные финансы](PERSONAL_FINANCE_2026_09_12.md),
[расходы](FINANCE_EXPENSES_2026_09_14.md) и
[финансы команды](WORKSPACE_FINANCE_2026_09_15.md). Их исторические решения
сохранены. Пользовательские группы отличаются от счетов: счёт участвует
в расчёте остатка, группа служит для организации операций. Источник дохода
по-прежнему определяет правила распределения; связь с целью либо карточкой
только показывает назначение операции.

## Поведение и область данных

Каждая операция может иметь одну необязательную группу и до десяти
необязательных связей. По умолчанию группы и связи отсутствуют; готовые
названия, личные категории и чужие карточки в команду не подставляются.
Одна группа может объединять и доходы, и расходы.

В личных финансах справочник групп принадлежит пользователю из сессии.
Доступны ссылки на его собственные личные цели (`personal_goal`) и дела
(`personal_plan`). Произвольный заголовок проекта не меняет эту область.

В командных финансах группы принадлежат фактическому проекту-источнику
регистра. Ссылки ведут на карточки (`record`) только этого же проекта,
включая карточки типа `goal`. При явном подключении A в B показываются
группы и связи A. B не получает копию данных и не создаёт новые права.
Действующий участник может читать; изменение доступно владельцу или
администратору собственного регистра. Подключённый регистр остаётся
доступен из другого проекта только для просмотра.

Архивирование группы сохраняет все прежние операции и их принадлежность.
Нельзя выбрать архивную группу для новой операции; можно сохранить её на
ранее созданной операции при исправлении примечания или суммы. Переименование
группы обновляет её название в истории. Группировка выполняется по ID,
поэтому одинаковые названия двух групп не объединяют их автоматически.
Физическое удаление групп через API не предусмотрено: архивирование позволяет
позднее восстановить прежнюю группу без потери истории.

## API групп

Оба префикса `/api/personal/finance` и `/api/workspace/finance` поддерживают
одинаковую форму данных. Командный вариант дополнительно применяет существующие
проверки членства, источника и ревизии настройки.

| Метод и путь после префикса | Тело и результат |
| --- | --- |
| `GET` основного отчёта | Дополнительно `categories: [{id,name,archived,revision}]`, включая архивные группы |
| `POST /categories` | `{name, archived?}`; ответ 201 с созданной группой |
| `PUT /categories/{id}` | `{name, archived, expectedRevision}`; ответ 200 с новой ревизией |

Название после обрезки пробелов содержит от 1 до 120 символов Unicode.
Начальная ревизия группы равна 1. Конфликт при редактировании возвращает 409;
ID группы другого владельца либо проекта возвращает 404. Переименование,
архивирование и восстановление проходят через один обработчик обновления.
Создание группы не имеет отдельной квитанции `clientRequestId`: интерфейс
при неопределённом результате перечитывает справочник и не повторяет создание
вслепую. Суммы операций не зависят от результата этого справочника.

## API операции и совместимость

Доход и расход дополняются полями `categoryId`, `categoryName`, `links`.
Пустые дополнительные поля могут отсутствовать в JSON; клиент трактует их
как пустую группу и пустой список. Название группы читается из текущего
справочника, названия целей и карточек — из текущих доступных записей.

Запросы `POST/PUT /entries` и `POST/PUT /expenses` принимают:

```json
{
  "categoryId": "идентификатор группы",
  "expectedCategoryRevision": 1,
  "links": [{"kind": "personal_goal", "id": "идентификатор цели"}]
}
```

Это дополнение к прежним обязательным полям операции, а не самостоятельное
тело запроса. Для новой выбранной группы требуется актуальная ревизия.
Если операция уже относилась к этой группе, сохранение прежнего ID допустимо
после переименования или архивирования группы: изменение других полей
операции не должно принудительно менять её назначение.

При обновлении отсутствие `categoryId` сохраняет прежнюю группу, пустая
строка снимает её. Отсутствие `links` сохраняет прежние связи, явный `[]`
снимает все связи. Это позволяет старым формам и сохранённым запросам
продолжить работу без потери новых признаков. JSON `null` для этих двух
необязательных полей трактуется как отсутствие поля.

Прежние `expectedRevision` операции и ревизии счёта/источника дохода
сохраняют свой смысл. Изменение операции, её метаданных и квитанции
повторного запроса выполняется в одной транзакции. Неудачная проверка группы
или связи не оставляет доход, расход, квитанцию либо частично сохранённые
метаданные. Отмена и восстановление операции сохраняют группу и связи.

В командных изменениях обязательны `X-Workspace-ID`, `X-Finance-Source` и
`X-Finance-Revision`. Старая форма после изменения источника получает 409,
в том числе при редактировании справочника групп. Подключённый источник
другого проекта нельзя изменить из принимающего проекта.

Новые поля ввода отмечены `omitempty` и отсутствуют в каноническом JSON
старого запроса, который их не передавал. Это необходимо для сохранения
старых `payload_hash` и повторного получения прежней операции вместо
ошибочного конфликта либо дубликата. Изменение явно переданных группы или
связей при повторе одного ключа считается изменением содержимого запроса.

## Поиск и защита связанных записей

`GET /link-targets?q=&kind=&limit=30` возвращает `{items,hasMore}`.
Длина поиска ограничена 120 символами, предел выдачи — от 1 до 100.
Каждый элемент имеет `{kind,id,title,available}`; командная карточка также
содержит `workspaceId` и `recordType`. Поиск работает без учёта регистра,
включая кириллицу. SQLite по умолчанию приводит регистр только ASCII,
поэтому сравнение заголовков выполняется в Go после ограничения области
SQL-запросом. В памяти остаётся только ограниченная выдача; для большого
числа совпадений клиент уточняет текст поиска. Курсорная пагинация пока
не добавлена. Архивные записи не предлагаются как новые связи.

Сервер не принимает произвольный SQL, имя таблицы, владельца, адрес ресурса
или сохранённое пользователем название ссылки. Разрешены только три
описанных типа. Повторяющиеся связи, пустые ID, ID длиннее 128 байт и
массивы более десяти элементов отклоняются. Командная карточка из другого
проекта, личная цель другого пользователя и несовместимый тип возвращают
ошибку до изменения операции.

Заголовки связанных записей не хранятся в финансовом снимке. При каждом
чтении они разрешаются повторно в текущей области данных. После перемещения
карточки в другой проект, смены владельца личной цели либо удаления записи
ответ содержит только `{kind,id,title:"Связь недоступна",available:false}`.
Старый заголовок, новый заголовок, проект и тип карточки при этом не выдаются.
Идентификатор сохраняется, чтобы пользователь мог явно убрать прежнюю связь.
Утрата членства исходного проекта запрещает весь финансовый ответ согласно
командному контракту; существующая ссылка не обходит эту проверку.

Ранее сохранённую недоступную связь разрешено оставить при исправлении
другой части операции. Новое назначение такой связи запрещено. Архивная,
но по-прежнему доступная владельцу запись сохраняет заголовок и получает
`archived:true`; она также может остаться в истории, но не назначается заново.
Эти правила предотвращают ситуацию, когда изменение примечания требует
удалить часть прежней истории, и одновременно не восстанавливают доступ.

## Хранение и миграция 075

`075_finance_organization.sql` создаёт четыре пустые таблицы:
`personal_finance_categories`, `workspace_finance_categories`,
`personal_finance_organization`, `workspace_finance_organization`.
Количество прикладных таблиц увеличивается с 139 до 143. Изменений колонок,
перезаписи старых строк, переноса личных данных и предварительного заполнения
нет. Миграции 001–074 сохраняются без изменений.

Метаданные отделены от исходных финансовых таблиц, чтобы сохранить денежные
строки и старые квитанции запросов в точности. Ключ метаданных состоит из
области, типа `income|expense` и ID операции. Составной внешний ключ удерживает
группу в той же области. Триггеры вставки и обновления проверяют существование
операции соответствующего типа и владельца/проекта. `links_json` содержит
только `{kind,id}`; SQL CHECK требует корректный JSON-массив до десяти записей.
Более подробная проверка типов и доступа выполняется обработчиком API.

Общий финансовый адаптер использует только жёсткий список имён таблиц.
Запросы к целям и карточкам выполняются через исходную SQL-транзакцию с
явным условием владельца/проекта, чтобы замена финансового `owner_id`
на `workspace_id` не затронула таблицы другого назначения.

Отчёт считывает метаданные только своих уже выбранных операций порциями
до 400 ID. Каждая уникальная связанная запись разрешается один раз на отчёт
после закрытия курсора метаданных. Остатки по-прежнему рассчитываются
накопительно до выбранной конечной даты; доходы и расходы в списке относятся
к выбранному периоду. Группы и связи в этот расчёт не вмешиваются.

## Проверки и границы готовности

В `finance_organization_test.go` проверяются личные и командные категории,
доходы и расходы с назначением, сохранение исходных сумм и распределений,
редактирование старым клиентом, явное снятие признаков, архивирование и
переименование, конфликты ревизий, чужие группы, чужие и перемещённые связи,
поиск кириллицей, архив целей, пределы и ограничения БД.

Миграционный тест создаёт настоящую схему 001–074 с личными и командными
операциями. Он сравнивает каждую старую таблицу и определение схемы до и
после 075, проверяет четыре пустые новые таблицы, затем повторяет прежние
личные/командные запросы дохода и расхода. Дополнительно SHA256 сохранённых
личных квитанций сравнивается с буквально заданным старым каноническим JSON.
Повтор возвращает прежний ID и не меняет операцию.

Матрица `TestWorkspaceFinanceAllWritesRespectScopeRoleAndStaleForms`
дополнена обоими методами категорий: обычный участник, устаревшая форма,
отсутствующие заголовки и подключённый регистр не позволяют запись.
Поиск целей также проверяется после отзыва членства и с устаревшим источником.
Точный общий прогон, браузерная проверка и факт публикации относятся к
операционному отчёту соответствующего выпуска. Наличие этого контракта
само по себе не означает завершение деплоя или проверку физического телефона.

### Дополнение: переходы при медленном ответе

При независимом просмотре интеграции обнаружены два случая, когда проверка
одного владельца и команды была недостаточной. Пользователь мог нажать
«Доход» в блоке и перейти на другую страницу той же команды до загрузки
счетов; прежняя форма тогда открывалась поверх нового маршрута. Аналогично
загрузка личной цели по финансовой связи могла закончиться после перехода
пользователя на другую вкладку. Сами деньги автоматически не изменялись,
но такой перехват интерфейса противоречил ожидаемому поведению.

Теперь действие блока удерживает владельца, проект, страницу, личную вкладку
и поколения навигации/контекста. Проверка передаётся до открытия формы,
включая ожидание подтверждения несохранённого редактора. Переход по связи
сначала проверяет исходный маршрут перед закрытием окон, затем фиксирует
целевой маршрут и проверяет его после загрузки данных. Запоздалое действие
не открывает редактор на другой странице. Ошибка действующего перехода
остаётся видимой после закрытия финансов; ошибка прежнего аккаунта не
показывается новому пользователю.

Проверки `web/finance-navigation.test.cjs` исполняют реальные callback-функции
с задержанными ответами, сменой вкладки, маршрута, проекта и аккаунта.
Они также проверяют успешное открытие личного дела/командной карточки без
создания финансовых операций. Вместе с `personal-finance.test.cjs` после
этой доработки прошли 53 проверки. Общий итог браузерных тестов фиксируется
в отчёте выпуска после финального обновления ресурсов.
