## Воспроизведённые дефекты

### 1. Старая вкладка перезаписывает свежий текст личной заметки — высокий приоритет

Шаги: создать заметку с текстом `original`; открыть её в двух контекстах;
из первого сохранить новый текст; во втором поменять только название и сохранить
форму, всё ещё содержащую старый текст. Второе сохранение возвращает HTTP 200,
в базе снова оказывается `original`. Более свежий текст заменён без конфликта.
Это воспроизведение на синтетической БД, не заявление о найденной потере
конкретной пользовательской заметки на рабочем сервере.

Причина: `internal/app/personal.go:396–423` обновляет всю заметку по ID и владельцу
без сравнения версии. В `web/app.js:2397` форма заметки не передаёт
`expectedUpdatedAt`, хотя соседняя форма личного плана уже делает это.
Таким образом, похожие редакторы дают разные гарантии сохранности.

Требуемое исправление: версия в запросе и атомарная проверка при записи,
понятное разрешение конфликта с сохранением обоих текстов и текущего черновика.
Проверка готовности: два устройства/вкладки, переставленные ответы, изменение
только названия, изменение даты, потеря ответа и повторное открытие редактора.
Добавление локального автосохранения само по себе этот дефект не исправляет.

Контроль приватности выполнен отдельно: попытка другого участника изменить
эту личную заметку возвращает 404. Дефект относится к конкурирующим правкам
одного владельца, а не к доступу партнёра к его личным данным.

### 2. Ответ предыдущего проекта подменяет текущий список — высокий приоритет

Выполнен код `loadData` с управляемым порядком ответов. Загрузка A задержана;
затем выбран и полностью загружен B; после этого завершена загрузка A.
Результат: `activeProject=B`, но `displayedRecord=A-record`.

Причина: `web/app.js:1086–1115` применяет результат общей загрузки через
`Object.assign(state, ...)` без проверки проекта, пользователя или поколения
запроса. Защита, уже имеющаяся у `syncProjectChanges`, не распространяется
на начальную загрузку. Это смешение состояния интерфейса между двумя проектами,
к которым пользователь уже имеет доступ; обход серверных прав не доказан.

Дополнительный сценарий: при выборе B один из 14 запросов, например чат,
завершается ошибкой. `switchWorkspace` уже меняет активный ID и локальную
настройку, но новая общая загрузка не применяется. Получено:
`activeProject=B`, `retainedRecord=A-old`.

Требуемое исправление: общий контроль поколения загрузки и явное согласованное
состояние перехода; результат A не может применяться после выбора B. Основные
данные должны иметь собственную ошибку/повтор и не зависеть от успешного ответа
всех вспомогательных модулей. Проверить A→B→A, две команды, переход при обрыве,
выход/новый вход во время загрузки, создание записи после неудачного перехода.

### 3. Сбой загрузки ошибочно воспринимается как необходимость входа — высокий приоритет

Выполнен `bootstrap`: `/api/me` успешно возвращает пользователя, но последующая
загрузка данных выдаёт временную ошибку 502. Результат: форма входа показана,
хотя аутентифицированный пользователь уже получен. Серверная сессия в этом
сценарии не отзывается; некорректно меняется экран приложения.

Причина: `web/app.js:1061–1083` вызывает `showAuth()` при любом исключении,
объединяя недействительную сессию, сетевой сбой и ошибку одного модуля.

Ещё один воспроизведённый вариант: неверный текущий пароль при его смене.
Сервер (`internal/app/server.go:468`) возвращает 401 с ошибкой поля, а общий
клиентский `api()` показывает вход для любого 401 вне `/api/auth/`.
Форма профиля закрывается вместо возможности исправить введённый пароль.

Требуемое исправление: различать истёкшую сессию, ошибку подтверждения пароля
и недоступность данных; сохранять рабочий экран/черновик и давать повторить
неудачную загрузку. Проверить обе ошибки и настоящий отзыв сессии отдельно.

### 4. Выдача карточек неполная при росте проекта — высокий приоритет до импорта

Создано 501 синтетическая карточка одного проекта. `GET /api/records` возвращает
500; отсутствующая в списке карточка открывается отдельным GET с HTTP 200.
Данные остаются в базе, но общий список не представляет весь проект.

Причина: `internal/app/server.go:750`, `LIMIT 500` без следующей страницы;
клиентская загрузка принимает массив за полную коллекцию. В синхронизации
(`internal/app/productivity.go:297`) тоже есть предел, который необходимо
согласовать с продолжением выдачи и устойчивым курсором.

Требуемое исправление: полноценная пагинация и согласование поиска, счётчиков,
досок, календаря и карты. Проверить одинаковые даты/версии, изменения между
страницами и отсутствие пропусков/дублей. Увеличение одной константы переносит
проблему, не выполняет критерии. На рабочем сервере текущий максимум — 168.

### 5. Два мнения превращаются в одну оценку — высокий приоритет для совместных решений

Два разных аккаунта последовательно оценивают одну идею по одному критерию:
первый ставит 9, второй 2. В текущей таблице остаётся одна строка, значение 2
и автор второго участника. HTTP-запросы успешны; отдельной оценки первого
участника в текущем наборе оценок больше нет. История событий не равна
представлению независимых действующих оценок.

Причина: `internal/app/server.go:2152`, конфликт уникальности
`(record_id, criterion_id)` обновляет и значение, и `evaluated_by`.

Требуемое исправление: независимая оценка каждого участника и явно определённый
общий результат. Сохранить реально существующие данные с авторами; не выдумывать
утраченные значения. Проверка: два аккаунта, одновременные правки, отсутствие
оценки отдельно от нуля и понятное отображение индивидуальных мнений.

### 6. Перестроение карты одного проекта сбрасывает раскладки других — обычный приоритет

Выполнены реальные функции хранения координат: сохранён узел A; выбран B;
вызван сброс расположения; снова открыт A. Сохранённых координат A больше нет.
Кнопка `graph-relayout` действительно вызывает проверенную `clearGraphPositions`.

Причина: `web/app.js:4335–4352`: общий ключ localStorage содержит аккаунт,
но не проект. Сброс удаляет весь ключ; координаты разных проектов до сброса
могут сосуществовать за счёт разных ID узлов, поэтому утверждать постоянное
перемешивание всех координат было бы неверно. Серверной синхронизации раскладок нет.

Требуемое исправление: ключи по аккаунту/проекту/виду, безопасный перенос прежних
координат и отдельное решение синхронизации устройств. Проверка сброса в B
обязана сохранить раскладку A и смысл связей в обоих проектах.

## Дополнительные несогласованности, подтверждённые чтением кода

- `internal/app/chat.go:528`: реакция длиннее восьми Unicode-кодов отвергается,
  хотя один составной эмодзи может быть длиннее. Это прежний подтверждённый
  разрыв; в текущем прогоне отправка реакции на рабочем сервере не выполнялась.
- `personal.go:249` считает серии привычек по соседним календарным дням без
  параметра режима привычки. Для режима «по будням»/недельной цели такой
  показатель требует другой семантики: пропуск предусмотренного выходного
  нельзя автоматически считать невыполнением расписания. Полная проверка
  календарных границ в этом прогоне не проводилась.
- День/неделя в ряде серверных расчётов закреплены за Europe/Moscow
  (`personal.go:890`, `productivity.go:54`, `workflow.go:994`). До поддержки других
  зон необходимо определить единый контракт; это не доказательство ошибки
  каждого текущего события пользователя, находящегося в Москве.

## Незавершённые сценарии, которые нельзя называть готовыми

Самостоятельное восстановление забытого пароля и доставка почты не закончены.
Смена известного пароля в профиле — отдельный уже существующий сценарий.
Открытая регистрация без обязательного кода остаётся решением пользователя;
аудит не предлагает отменять её.

Локальные черновики не являются полноценной очередью работы без сети.
Задача офлайн-сохранения остаётся planned; нужно проверить повтор отправки,
неопределённый результат записи и конфликты на настоящих телефонах.

Backup-сервис работает и его скрипт проверяет расшифровку, контрольные суммы
и целостность SQLite. Полный запуск приложения после восстановления БД и
вложений в изолированном окружении этим аудитом не выполнялся. Нельзя говорить,
что копий нет или что они заведомо неисправны. Нельзя также считать успешный
таймер полной репетицией аварийного восстановления.

## Воспроизводимость и ограничения

Проверки backend запускают настоящий HTTP-сервер Go с миграциями на временной
синтетической SQLite. Два тестовых аккаунта получают доступ к одному тестовому
проекту штатным тестовым helper. 501 запись не создавалась в production.
Frontend-проверки исполняют выбранные функции текущего `app.js` в Node VM
с управляемыми ответами и задержками, а не копию алгоритма. Это проверка
асинхронной логики; визуальная/физическая мобильная приёмка не проводилась.

Диагностические исходники сохранены в `docs/verification`:

- `TESSAVIE_STABILITY_2026_09_03.client.cjs`
- `TESSAVIE_STABILITY_2026_09_03.backend.go.txt`

## Очередь и связь с существующими задачами

и правильное различение ошибок входа/загрузки. Эти дефекты мешают текущей работе
даже при маленькой базе. Затем — независимость оценок и полная выдача карточек
до использования больших клиентских проектов. После этого — изоляция раскладок,
