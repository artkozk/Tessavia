Tessavia. Оно не является отчётом о реализации, проверкой на физических

Рассмотрены только первичные источники владельцев платформ: Apple Developer,
WebKit, Android Developers и Capacitor. Ссылки и ограничения проверены
14.09.2026. Версии библиотек, правила распространения и доступность новых API
нужно повторно сверять перед сборкой. Исторические решения не удаляются.

Прочитаны README, реестр требований от 02.09.2026 и контракты
`REMINDER_DELIVERY_2026_09_04.md`, `OFFLINE_OUTBOX_CONTRACT_2026_09_03.md`.

## Рекомендуемое решение

Сохранить веб-приложение, конструктор, наборы и единый сервер. Развивать два
связанных этапа: сначала удобная установка PWA, Web Push и быстрый вход в
заметку; затем мобильная оболочка с настоящими виджетами и системными действиями.
Уведомления iPhone не нужно ставить в зависимость от выпуска приложения в
магазине: WebKit поддерживает Web Push установленного Home Screen веб-приложения
начиная с iOS/iPadOS 16.4. Установка и запрос разрешения — реальные необходимые
действия пользователя. [WebKit: Web Push for Web Apps on iOS and iPadOS](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).

Capacitor подходит как кандидат для оболочки: его можно добавить в существующий
JavaScript-проект, сохранив веб-ресурсы и дополнив их нативными интеграциями.
Это рекомендация по соответствию нашей архитектуре, а не результат уже
выполненной мобильной сборки. [Capacitor: Installing Capacitor](https://capacitorjs.com/docs/getting-started),
[Capacitor: Native Runtime for Web Apps](https://capacitorjs.com/docs).

Настоящий виджет требует отдельного небольшого отображения на WidgetKit/SwiftUI
и Android App Widgets/Glance. Вывод из официальных моделей платформ: перенос
страницы HTML в оболочку сам по себе не создаёт виджет на домашнем экране.
Сохраняем общие данные и действия конструктора; отображение вне приложения
подстраиваем под возможности ОС. [Apple: Creating a widget extension](https://developer.apple.com/documentation/widgetkit/creating-a-widget-extension),
[Android: Create an app widget with Glance](https://developer.android.com/develop/ui/compose/glance/create-app-widget).

## iPhone: установка и Web Push

Установленное Home Screen приложение может запросить разрешение на уведомления
после прямого действия, например нажатия «Включить уведомления». Уведомления
появляются на экране блокировки и в системном центре уведомлений; пользователь
управляет ими и режимами Focus в настройках ОС. Для standards-based Web Push
не нужна подписка Apple Developer Program. Это не означает отсутствия нашего
сервера отправки и обработки подписок. [WebKit: Web Push on iOS and iPadOS](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/),
[Apple: Sending web push notifications](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers).

Для старых поддерживаемых iOS следует сохранять корректный manifest, иконки и
standalone-режим. В iOS/iPadOS 26 установка изменилась: по умолчанию любой сайт,
добавленный на Home Screen, открывается как веб-приложение, а пользователь
может отключить «Open as Web App». Поэтому нельзя показывать одну устаревшую
инструкцию для всех версий. Manifest продолжает давать полезные метаданные.
[WebKit: WebKit Features in Safari 26.0 — Every site can be a web app](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/#every-site-can-be-a-web-app-on-ios-and-ipados).

WebKit требует видимого результата push. Нельзя использовать скрытые push как
постоянный фоновый процесс для опроса задач или обновления виджета: отсутствие
видимого уведомления при обычном push может привести к отзыву подписки.
Declarative Web Push, описанный для iOS/iPadOS 18.4 и более новых систем,
добавляет декларативное содержимое и видимый fallback; он не снимает это
ограничение. Базовый совместимый путь должен работать без предположения,
что расширение поддерживается каждым браузером. [WebKit: Meet Declarative Web Push](https://webkit.org/blog/16535/meet-declarative-web-push/).

Предлагаемый UX Tessavia: один раздел «Настройки → Устройства и уведомления».
В нём отдельно отображать установку, системное разрешение, подписку этого
устройства, категории и результат тестового уведомления. Отказ пользователя
оставляет работу сайта доступной. Не просить разрешение при первом заходе
без контекста и не показывать «Включено», если есть лишь внутренняя настройка
сайта, но нет действующей подписки.

## iPhone: настоящий виджет и его пределы

WidgetKit использует расширение приложения и поддерживаемые SwiftUI views.
Виджет представляет подготовленные системой снимки; он не выполняет наш
JavaScript постоянно и не является произвольным WebView. Обычный текстовый
ввод и прокрутка длинного документа не составляют модель iOS-виджета.
Поэтому ввод новой заметки следует открывать в приложении, а в виджете
оставлять обзор и короткие действия. [Apple: Creating a widget extension](https://developer.apple.com/documentation/widgetkit/creating-a-widget-extension).

Для интерактивных виджетов подходят Button/Toggle с App Intent: например,
«Привычка выполнена», «Глава прочитана». Для конфигурируемых виджетов начиная
с iOS 17 используется WidgetConfigurationIntent; поддержка более ранних ОС
требует отдельного пути совместимости. Выбор личной страницы или блока может
стать параметром виджета. [Apple: Bring widgets to life](https://developer.apple.com/videos/play/wwdc2023/10028/),
[Apple: Making a configurable widget](https://developer.apple.com/documentation/widgetkit/making-a-configurable-widget).

Обновления строятся на timeline и запросах перезагрузки. ОС распределяет
бюджет: Apple приводит ориентир 40–70 фоновых обновлений за день для часто
просматриваемого виджета. Это не SLA и не таймер с гарантированной точностью.
Смена дня или ближайшего события может быть заранее заложена в timeline.
[Apple: Keeping a widget up to date](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date).

Нельзя описывать актуальный WidgetKit как систему «только с таймером»:
официальная документация также содержит WidgetKit push через APNs. Для этого
нужны отдельные widget tokens, capability и обработчик WidgetPushHandler;
системный бюджет и доставка при подходящих условиях сохраняются. Это
дополнение к timeline, а не гарантия мгновенного обновления. API нового
поколения следует включать с проверкой доступности SDK/ОС, сохранив timeline
для более старых устройств. [Apple: Updating widgets with WidgetKit push notifications](https://developer.apple.com/documentation/widgetkit/updating-widgets-with-widgetkit-push-notifications),
[Apple: What’s new in widgets, WWDC25](https://developer.apple.com/videos/play/wwdc2025/278/).

Предлагаемый нативный слой хранит небольшой снимок данных для виджета вместе
с приложением в App Group и обновляет его после подтверждённого изменения.
Apple описывает совместный контейнер как способ передачи данных между
приложением и расширением. Наша идентификация владельца, TTL снимка и очистка
при выходе должны быть частью собственного контракта, а не предположением
о доступе виджета к cookie браузера. [Apple: Developing a WidgetKit strategy](https://developer.apple.com/documentation/widgetkit/developing-a-widgetkit-strategy).

## Android: виджет, ярлыки и фоновое выполнение

Android App Widgets/Glance дают отображение в launcher. Glance использует
Compose-подобную модель, но ограничен AppWidgets и RemoteViews: это другой
набор элементов, чем полноэкранный Compose, и тем более не DOM/CSS. Можно
сделать список ближайших дел, кнопки и прогресс, но не обещать произвольную
веб-страницу один к одному. [Android: Create an app widget with Glance](https://developer.android.com/develop/ui/compose/glance/create-app-widget).

Виджеты должны адаптироваться к доступному размеру и настройке пользователя.
Жесты ограничены контекстом домашнего экрана; например, горизонтальное
перелистывание уже принадлежит launcher. Конфигурация может выбирать источник
данных, а не создавать отдельный жёсткий виджет под каждого клиента.
[Android: App widgets overview](https://developer.android.com/develop/ui/views/appwidgets/overview).

Нативный pinned shortcut — отдельная иконка запуска действия, а не живой
виджет. Android поддерживает его начиная с API26 на совместимых launcher;
прикрепление требует пользовательского подтверждения. Для «Новая заметка»
это полезный облегчённый вход, но нельзя выдавать его за просмотр задач на
домашнем экране. [Android: Create shortcuts](https://developer.android.com/develop/ui/compose/system/shortcuts/creating-shortcuts).

Glance можно обновлять после действий/изменений данных; периодический
`updatePeriodMillis` ограничен интервалом не чаще 30 минут. Для другой
периодической работы применим WorkManager с минимальным интервалом 15 минут,
при этом фактический запуск не равен точному расписанию. Не проектировать
ежеминутный опрос сервера в фоне. [Android: Manage and update GlanceAppWidget](https://developer.android.com/develop/ui/compose/glance/glance-app-widget),
[Android: Define work requests](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work).

Doze и App Standby откладывают фоновую сеть и задачи. Факт установки APK не
даёт бесконечного фонового исполнения. На Android13+ нативное приложение
запрашивает POST_NOTIFICATIONS; системный отказ надо учитывать отдельно от
подписки внутри Tessavia. Для PWA проверяются доступность веб-API и разрешения
конкретного браузера; нативное разрешение не является JavaScript API сайта.
[Android: Optimize for Doze and App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby),
[Android: Notification runtime permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission).

## Capacitor: что сохраняется и что придётся добавить

Сохраняем общий интерфейс конструктора, формы, доменные правила и API.
Для упаковки нужны отдельный каталог готовых веб-ресурсов и нативные проекты.
Capacitor предоставляет мост JavaScript ↔ native и допускает собственные
плагины; виджеты остаются нативными модулями, которые читают общие данные.
Не требуется переход всего frontend на React/Flutter только ради оболочки.
[Capacitor: Installing Capacitor](https://capacitorjs.com/docs/getting-started),
[Capacitor: Creating plugins](https://capacitorjs.com/docs/plugins/creating-plugins).

Официальный Push Notifications plugin использует FCM на Android и требует
настройки iOS push. Он не реализует iOS silent push; на Android data-only
событие не вызовет JavaScript callback после уничтожения приложения без
дополнительного нативного сервиса. Поэтому обработка виджета не должна
зависеть от работающего WebView. [Capacitor: Push Notifications](https://capacitorjs.com/docs/apis/push-notifications).

Нативные локальные уведомления и серверные push — разные механизмы. Первые
могут планироваться на устройстве, но требуют отдельной сверки разрешений
и правил exact alarms на Android. Они полезны для заранее известных личных
напоминаний, однако при переносе события с другого устройства нужно уметь
отменить старое расписание и не прислать дубль. [Capacitor: Local Notifications](https://capacitorjs.com/docs/apis/local-notifications).

Даже нативный silent push iOS не гарантирован и может быть ограничен ОС.
Apple рекомендует не пытаться отправлять больше двух-трёх фоновых
уведомлений в час. На нём нельзя строить обещание постоянной синхронизации
или точного будильника. [Apple: Pushing background updates to your app](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app).

## Как сохранить гибкость конструктора

Ниже — предлагаемый контракт, ещё не реализованная схема или API. Имена полей
иллюстрируют ответственность и не объявляют существующие endpoints.

1. Пользователь собирает страницу обычным конструктором и выбирает, какую
   её часть вывести в виджет: задачи, привычки, чтение, итог таблицы или
   кнопку создания записи. Источник определяется настройкой, а не username
   владельца и не специально написанным для него экраном.
2. Конфигурация виджета содержит версию, ссылку на страницу/блок, фильтр,
   выбранные поля, допустимые действия и оформление. Несколько экземпляров
   могут смотреть на разные наборы одного пользователя.
3. Общий слой создаёт компактную модель отображения: текст, значение,
   прогресс, список, кнопка, отметка, ссылка. Веб-превью и нативные renderer
   используют одну смысловую модель. Произвольный пользовательский JS не
   становится кодом расширения ОС.
4. Для неподдерживаемой части конструктора показывается объяснение и переход
   на полную страницу; выбранная конфигурация не теряется. Нельзя молча
   удалить формулу, действие или поле при экспорте в виджет.
5. Шаблон набора переносит конфигурацию, но не приватный снимок, токены,
   чужие отметки или исходные ID аккаунта. При установке набора пользователь
   привязывает собственные источники, а ссылки переназначаются проверяемо.
6. Новая запись или отметка выполняется через те же серверные правила
   владельца, прав, версий и повторов, что в веб-приложении. Нативный экран
   не получает отдельный обход валидации и не пишет напрямую в серверную БД.

Именно такая модель позволяет показать инвестору воспроизводимый сценарий:
он сам собирает набор и назначает его источником виджета. Отдельная жёстко
запрограммированная «читалка пользователя» этого критерия не выполняет.

Оформление сохраняет читаемость, характерные цвета и простые подписи Tessavia.
Размеры и внешнее поведение зависят от ОС: нужны small/medium/large layouts,
длинный текст, увеличенный шрифт, светлый/тёмный/системно-тонированный вариант.
Их проверяют как отдельные представления, а не уменьшают всю веб-страницу до
маленького прямоугольника.

## Быстрая заметка: минимальный полезный сценарий

Сначала обеспечить маршрут «иконка/ссылка → одно поле текста → сохранено».
Кнопки быстрого доступа пользователь сам включает в настройках. Если папка
или набор не выбраны, запись попадает в личные входящие; обязательные
категории, результаты, исполнители и финансовые поля здесь не нужны.

При появлении native-слоя этот же сценарий вызывается из виджета или
системного действия. На iPhone виджет открывает ввод в приложении; обещать
полноценную клавиатуру прямо внутри WidgetKit не следует. Для голосового
ввода или системного «Поделиться» понадобятся отдельные сценарии приёмки;
их нельзя считать готовыми вследствие наличия текстовой формы.

Сохранение должно различать три состояния: записано на устройстве, отправляется,
подтверждено сервером. После offline или потерянного ответа повтор использует
тот же неизменный request ID и payload. Нельзя очищать текст до устойчивой
локальной записи, создавать вторую заметку при retry или отправлять черновик
пользователя A после переключения на B. Существующий веб-контракт outbox уже
описывает эти гарантии; для native-хранилища их надо сохранить и заново
проверить, а не считать автоматически перенесёнными из IndexedDB.

Набранная заметка с другого устройства появляется после подтверждённой
синхронизации. Отметка привычки должна задавать желаемое значение для
конкретного дня, например checked=true, а не выполнять безусловный toggle:
повтор потерянного запроса тогда не перевернёт результат обратно.

## Канал доставки и данные устройства

Предлагается один серверный источник событий и разные адаптеры доставки:
внутренние входящие, Web Push, native APNs/FCM. Это позволяет сохранить
тихие часы, часовой пояс, категории, актуальность события и подавление
повторов независимо от транспорта. Конкретная реализованность каждого
из этих правил определяется текущим аудитом кода.

Устройство/подписка связывается с владельцем и действующим согласием.
Веб-подписка, native token и WidgetKit token — разные регистрации.
При выходе, отзыве доступа, удалении устройства и смене токена нужна
явная деактивация. Удалённая ОС подписка не должна бесконечно получать retry.
На один физический телефон могут быть установлены и PWA, и приложение:
необходимо дать человеку выбор канала и исключить нежелательные дубли.

Внешний push по умолчанию нейтрален: без текста финансов, личного дневника
или Библии на заблокированном экране. Детали загружаются по авторизованному
переходу с повторной проверкой доступа. Это соответствует прежним требованиям
реестра к приватным push. Принятие сообщения push-провайдером не означает,
что человек его увидел или прочитал; эти состояния нельзя объединять.

Снимок виджета должен иметь дату обновления и состояние устаревания. После
offline показывается последняя известная информация, а не фиктивная свежая.
После выхода или отзыва доступа снимок очищается/скрывается. Финансовые суммы
и чувствительные названия выводятся только при явной настройке пользователя.

## APK, iOS-сборка и EXE

Android допускает распространение подписанного APK через собственный сайт,
но установка требует разрешения соответствующему источнику. Для публичного
выпуска нужны подпись, управление ключами, обновления и выбранный канал
дистрибуции. Наличие файла ещё не доказывает работоспособность виджета.
[Android: Alternative distribution options](https://developer.android.com/distribute/marketing-tools/alternative-distribution).

Условия распространения меняются: актуальная документация Android описывает
начало регионального внедрения developer verification 30.09.2026 в Бразилии,
Индонезии, Сингапуре и Таиланде, с расширением в 2027. Это не утверждение,
что на 14.09.2026 обычная установка уже запрещена во всём мире. Перед публичным
APK надо сверить актуальные условия целевых стран и выбранного канала.
[Android: Developer verification](https://developer.android.com/developer-verification/guides).

Для iOS нужен собственный подписанный проект; APK не является iPhone-сборкой.
Capacitor требует macOS и Xcode для iOS build. На текущей странице Capacitor8
указан минимум Xcode26.0; версию SDK надо закрепить при выборе toolchain.
Доступный сейчас Windows-компьютер не заменяет macOS-сборщик и физический iPhone.
[Capacitor: Environment Setup](https://capacitorjs.com/docs/getting-started/environment-setup).

Практический путь тестовой iOS-раздачи — TestFlight, затем App Store после
приёмки. Внешняя beta требует review; условия аккаунта проверяются отдельно.
Apple Developer Program сейчас указан как ежегодное членство $99, тогда как
Web Push такого членства не требует. Альтернативные региональные способы
iOS-дистрибуции в этом исследовании не оценивались.
[Apple: TestFlight](https://developer.apple.com/testflight/),
[Apple: Developer Program](https://developer.apple.com/programs/).

App Review 4.2 требует полезность сверх простой переупаковки сайта.
Нативный виджет, быстрый ввод, системные действия и качественная offline-работа
являются осмысленной целью оболочки; это не гарантия одобрения конкретной
сборки магазином. [Apple: App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/#minimum-functionality).

EXE относится к отдельному desktop-направлению. Он не создаёт Android/iOS
виджеты и не является условием Web Push на телефоне. В этом исследовании
не выбирались Windows-framework и установщик; общий сервер и веб-ядро
позволяют оставить эту задачу независимой от мобильной приёмки.

## Предлагаемая последовательность и критерии

Эти этапы являются планом для сверки с каноническими задачами, а не списком
уже созданных/выпущенных функций. Сроки и доступность устройств не выдумываются.

| Этап | Проверяемый результат | Что не считается доказательством |
| --- | --- | --- |
| 1. Установка и быстрый ввод | Пользователь устанавливает PWA, открывает свою заметку, сохраняет её offline и после возврата сети получает один серверный ID | Один скриншот иконки, ручная вставка строки в БД |
| 2. Web Push | На физическом Android и установленной iPhone PWA уведомление приходит при закрытом интерфейсе; отказ, отзыв и переход обрабатываются понятно | Работа только уведомлений внутри сайта или принятие push провайдером |
| 3. Native вертикальный сценарий | Сборка Android и сборка iOS входят в тот же аккаунт; пользователь выбирает свой блок, видит его в виджете и выполняет одно действие | Пустая оболочка, native-макет без сохранения, APK без iOS-проверки |
| 4. Конфигурируемые виджеты | Чужой пользователь сам создаёт/устанавливает набор и выбирает его источник без изменений разработчиком | Демонстрация только в пространстве автора |

Для каждого выпуска проверять как минимум:

1. Чистая установка, обновление существующего клиента, восстановление сессии
   и deep link после входа. Переход не должен отправлять в чужое пространство.
2. Разрешить/отказать/позже отозвать уведомления; выключить категорию и
   проверить реальные системные настройки отдельно от настроек сайта.
3. Закрытый интерфейс, перезагрузка телефона, offline, экономия энергии,
   Focus/Do Not Disturb и доступная версия ОС. Зафиксировать фактическую
   задержку доставки, не объявляя точное время гарантией.
4. Потерянный ответ после серверного успеха, повтор, два устройства и смена
   аккаунта: одна заметка/отметка, правильный владелец и сохранённый текст.
5. Виджет с разными источниками, скрытым/архивным блоком, отсутствующим
   доступом и удалённой конфигурацией. Никакой молчаливой замены на чужой набор.
6. Крупный шрифт, длинные русские названия, все поддерживаемые размеры,
   VoiceOver/TalkBack, тёмный и тонированный режим, реальная клавиатура.
7. Изменение с другого устройства, устаревший снимок, смена дня/часового
   пояса, logout и удаление приложения. Чувствительные данные не остаются
   видимыми в старом снимке после установленного протоколом отзыва.

Симулятор, browser viewport и автоматические проверки полезны, но не заменяют
физические устройства для системной доставки, launcher, фоновых ограничений
и поведения клавиатуры. Сейчас такие проверки данным документом не выполнены.

## Что необходимо выяснить до нативной реализации

- Реальные модели/версии Android и iPhone первых пользователей и доступные
  устройства для проверки; для iOS — доступ к macOS/Xcode и аккаунту публикации.
- Какие общие блоки дают максимальную пользу в первом виджете: день, привычки,
  чтение, быстрый ввод. Выбор должен оставаться пользовательским.
- Контракт мобильной авторизации, отзыва токенов и общих snapshots; сессия
  сайта не считается автоматически доступной native-расширению.
- Приёмка формул/связей конструктора и безопасное отображение неподдерживаемых
  частей, чтобы импорт набора не обещал функции, которых виджет не умеет.
- Фактическая готовность существующего outbox и канонического планировщика
  по текущему коду. Историческая документация даёт основу, но не заменяет аудит.

Проверка этого этапа ограничена первичными источниками, их сопоставлением с
запросом и документацией проекта. Приложения, push-подписки, платные аккаунты
и серверные задачи этим исследованием не создавались.

## Подключение Android-виджета через общий центр — реализация 14.09.2026

Следующий этап после исследования реализует ограниченный, проверяемый
сценарий системного виджета. Исторические абзацы выше описывают исходный
аудит и не заменяют результаты конкретного выпуска. Это дополнение не
объявляет готовыми приложение iOS, App Store/Google Play, редактирование
данных из виджета или перенос произвольного DOM конструктора на главный экран.

Единственный путь управления: **Настройки → Личные настройки → На телефоне**.
В существующем окне установки и ярлыков появилась область «Виджеты Android».
Боковое меню и обычные рабочие страницы дополнительных кнопок настройки
не получают. Пользователь выбирает сохранённый блок «Пункты и отметки» либо
«Прогресс» из своих доступных страниц текущего пространства; названия страниц
группируют список, а новый готовый набор для пользователя не создаётся.
Если блоков нет, окно объясняет, что сначала нужно сохранить такой блок в
конструкторе. Форма не предлагает фиктивный источник и не подставляет чужие
личные результаты.

Порядок подключения:

1. Пользователь скачивает предварительную Android-сборку Tessavie Widgets
   по `/downloads/tessavie-widgets-preview.apk` и добавляет виджет в launcher.
   Ссылка должна публиковаться вместе с проверенным APK до выпуска интерфейса;
   наличие ссылки в исходнике не доказывает доступность файла на сервере.
2. Выбирает страницу/блок, по желанию называет устройство и нажимает
   «Получить код подключения». До отправки явно показано, что блок и личные
   отметки будут видны на главном экране, доступ действует 90 дней и отзывается
   в том же окне.
3. `POST /api/me/widgets` возвращает одноразовый код на пять минут. Код
   показывается только в памяти открытого окна и копируется лишь по отдельному
   нажатию. В URL, журнал, localStorage и набор страницы он не записывается.
   Пользователь вставляет его в настройке Android-виджета.
4. «Доступ к виджетам» показывает выданные разрешения аккаунта из всех его
   пространств. Пустой `pairedAt` означает «Ожидает подключения», а не уже
   работающий телефон. Последующее подключение и последнее чтение различены.
   Выход из сайта не отзывает независимое разрешение; действие «Отключить»
   использует `DELETE /api/me/widgets/{id}`.

Виджет первого этапа читает результат выбранного блока, обновляет снимок и
открывает Tessavie. Изменение отметок остаётся в платформе. Сервер отказывает
отозванному устройству сразу; уже показанный локальный снимок очищается при
следующей проверке виджета, а не мгновенно на телефоне без сети. Окно для iPhone
сохраняет инструкцию PWA и ярлыков и прямо говорит, что системный виджет iOS
этим этапом не выпущен.

Клиентский контроллер `web/mobile-widgets.js` явно фиксирует пользователя,
пространство и страницу при открытии. Все запросы получают исходные
`X-Workspace-ID` и `X-Outbox-Owner`, поскольку общий клиент считает `/api/me/*`
областью аккаунта и сам не добавляет заголовок пространства. Ответ после
закрытия, смены аккаунта/пространства/страницы или повторного открытия окна
не перерисовывает новый контекст. Код и таймер очищаются при закрытии/выходе;
истёкший код нельзя скопировать. Сбой обновления списка не уничтожает уже
полученный код, а имя и выбор источника сохраняются при обновлении списка и
перерисовке окна установки. Старый ответ чтения списка не возвращает на экран
разрешение, которое пользователь уже отозвал.

У формы есть отдельные ошибки загрузки источников и подключений, доступный
повтор и ручное копирование при отказе Clipboard API. Запись не повторяется
автоматически после потери ответа: пользователь получает предупреждение о
возможном сохранении и проверяет список. Отключение блокирует повторные клики
до ответа и при неудаче оставляет разрешение видимым для явного повтора.
Локальные проверки клиента, APK, серверной части и фактическая публикация
фиксируются отдельно после выполнения; готовый текст окна не считается
проверкой физического Android-устройства.

Локальная клиентская проверка 14.09.2026: **41/41 Node-тестов** в
`mobile-widgets`, `mobile-access`, `settings-hub`, `settings-integration` и
`settings-module-paths` прошли без пропусков; `git diff --check` ошибок не
выявил. Новые проверки контроллера воспроизводят отложенные ответы после
закрытия/смены контекста, очистку секретного кода, срок действия, отказ
копирования, сохранность выбора и имени при повторной загрузке, независимость
кода от сбоя чтения списка, повторное нажатие, отзыв и старый ответ списка
после отзыва. Отдельно проверены три состояния разрешения и перерисовка
установочного окна без повторной выдачи. Эти результаты относятся к клиенту;
они не доказывают доставку снимка на физический телефон или публикацию APK.

При визуальной проверке выявлено, что общий выпадающий список платформы
показывает варианты без заголовков `optgroup`. Поэтому подпись каждого
варианта дополнена названием страницы: «Страница · Блок». Два одноимённых
трекера на разных страницах остаются различимыми в обычном и мобильном
выборе. После этой поправки тот же клиентский прогон: **42/42 теста прошли**,
включая отдельный случай одинаковых названий блоков у разных страниц.
